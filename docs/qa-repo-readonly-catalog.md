# QA 仓场景清单（只读）

> 平台读别人家的黑盒验收仓，把「场景清单 + 每个场景规划了哪些脚本」画成一页。
> **对该仓库永远只读**：只做 `clone --bare` / `fetch` / `git show` / `git grep`。

页面：项目内「测试设计 → QA 场景清单」（`/projects/:projectId/qa-catalog`）
配置：**就在这一页**，右上角「配置 QA 仓」。只填仓库地址，其余自动识别。

---

## 1. 为什么是只读，而且这条不能松

QA 仓（如 uag-qa）是**别人维护的仓库**，里面只有验收脚本，没有产品代码。清单文件是那个
仓库的**唯一索引**，也是 QA 自己的工作面：`check-coverage.sh` 会拿"清单标 ✅ 但没有脚本
声明这个 ID"当 BLOCK 拦下来。平台一旦往里写（补 ID、改状态列、塞 metadata 文件），
就等于替对方改了他的判据来源 —— 他的门禁会开始红，而红的原因在他仓库里查不到。

所以这条是硬约束，不是"当前还没做写回"：

- `app/services/qa_catalog.py` 里只允许出现 `show` / `ls-tree` / `rev-parse` / `log` / `grep` / `symbolic-ref` 这些读子命令；
- `backend/tests/test_qa_catalog_parse.py` 有两条封样，扫模块源码，出现 `push`/`commit`/`worktree`/
  `checkout` 之类的写子命令直接红；同一份文件里还有一组真 git 仓的解析/自动识别测试；
- `tests/api/projects/test_qa_catalog_config.py` 拿一个本地临时 git 仓当 QA 仓，把
  「保存配置 → 立刻按新配置读一次」整条跑通（本地路径 clone 不用网络，所以能进常规 CI）；
- 也**不要求对方仓库为我们改任何东西**：不加字段、不加文件、不加 CI 钩子。
  我们读的全是他本来就在维护的东西（清单表格 + 文件头注释）。

想让平台的用例流回 QA 仓？那是**另一件事**，得先跟仓库主人谈，不能从这个模块长出来。

## 2. 读什么

| 读 | 是什么 | 用途 |
|---|---|---|
| 清单文件（自动认出来，见 §3） | 场景的**分母**：该有哪些场景、P/R/层、状态 ✅⬜❌ | 覆盖率、缺口、优先级分布 |
| 用例脚本头部注释 | 场景的**分子**：`@scenario`（可多个）/ `@tier` / `@known-bug` | 每个场景挂了哪些脚本、哪些带着已知缺陷 |

两边**都读、都如实呈现**，不做"以清单为准"的抹平 —— 因为两边对不上才是最该看见的信息：

- **清单未对上**（`claimedButUncovered`）：状态标 ✅ 但没有任何脚本声明这个 ID。
- **孤儿脚本**（`orphanScripts`）：脚本声明了清单里不存在的 ID。

这两条正是 QA 自己 `check-coverage.sh` 会**直接 BLOCK** 的两项，所以页面把它们放在第三块
看板「清单可信吗」里，而不是藏在表格里的一个小黄标 —— 见 §5。

清单行长这样（列少了不会整份读不出来，按缺省补空）：

```
| ID | 场景 | P | R | 层 | 状 |
| SMK-01 | `GET /healthz` 返回 200 | P0 | 6 | smoke | ✅ |
| MCP-38 | HITL 挂起的调用事件也要带三段式操作人 | P1 | 6 | scenario | ✅ `@known-bug GL#531` |
```

脚本头长这样（`#` 和 `//` 两种注释都认，只扫前 25 行）：

```bash
# @scenario AUT-01 AUT-02 AUT-05     ← 第一个是主 ID，决定文件放哪个域目录
# @tier smoke
# @known-bug GL#531 审计记录各缺一半
```

域码不写死（别的项目有别的域码）：只要求「2–6 位大写字母 + 短横 + 2–3 位数字」，
域名从清单里的域码表读。`@scenario` 那行只取形如 ID 的 token，遇到第一个不像 ID 的就停 ——
行尾的中文说明（`← 第一个是主 ID`）否则会被当成场景 ID，在页面上变成一串假的孤儿脚本。

**模板文件不算用例**：`*.tmpl` / `*.example` 这类，或路径里有 `templates/` 的，
自动发现时跳过。uag-qa 的 `.claude/skills/qa-module/templates/case.sh.tmpl` 里写着占位的
`@scenario XXX-01`，算进来页面上就会多一条"声明了清单外 ID 的脚本"，看着像 QA 写错了。
真要把它当用例看，去高级里填 glob —— 填了就完全按 glob 来，不再自动排除。

## 3. 配置项

存在 `projects.qa_repo`（JSONB，迁移 `zzt0qarepo`）。**只有仓库地址是必填的**，
另外三项是「认错了才需要填」的覆盖项，弹窗里收在「高级」里：

| 字段 | 留空时 | 说明 |
|---|---|---|
| `url` | — | 唯一必填。**清空 url 并保存 = 取消配置**（服务端把整个 `qa_repo` 置 NULL） |
| `branch` | 跟仓库自己的默认分支（bare 仓的 HEAD） | 填了就必须命中，找不到直接报错 —— 悄悄回退 HEAD 等于拿别的分支的数据顶着你填的分支名显示 |
| `catalogPath` | 找**场景行最多**的那份 `.md`（≥5 行才算） | 不认文件名：别的 QA 仓不会也叫 `test-scenario-catalog.md`。README 里举两行例子不会被选中 |
| `caseGlobs` | `git grep -l @scenario` 捞所有声明了场景的文件 | 比配目录 glob 准：脚本挪目录不用改配置，也不会把没声明场景的支持库当用例。填了就只认这些 glob（`**` 跨目录、`*` 不跨） |

**别给这三项塞默认值。** `docs/test-scenario-catalog.md`、`api/**/*.sh` 是 uag-qa 一家的习惯，
写成默认值会让下一个 QA 仓在页面上报"没有这个文件"，而人根本没填过它 —— 那种错最难查。
页面顶部会显示这次是「自动识别」还是「配置指定」，认错了才知道要去高级里手填。

**配置维护在 QA 页，不在「编辑项目」弹窗**：这份配置只影响这一页、认错了也只在这一页报错，
改的人和看结果的人是同一个。附带的好处是权限对得上 —— `PUT /api/projects/{id}` 要系统 admin，
而 `PUT /api/projects/{id}/qa-catalog/config` 只要项目管理员，接自己项目的 QA 仓不用求平台管理员。

没配置时页面**只画表头** + 顶部一条提示，不是 404、不是空白页 —— "没配"和"配错了"是两件事，
页面必须能分得开。

本地缓存：`backend/.qa-repos/<project_id>.git`（bare，已进 `.gitignore`）。
`GET` 只读本地缓存不打远端；点「拉取最新」或刚保存完配置才 `fetch`。同一个 commit 不重复解析。
缓存按项目建，**换了仓库地址会先把旧缓存整个删掉**（不删的话 `ensure_bare_repo` 见 HEAD 还在
就直接复用，页面上地址已经改了、数据还是旧那家的）。

### 一个踩过的坑：`git grep` 的 ref 位置

```
git grep -c -E '<pat>' -- '*.md' HEAD    # ← HEAD 落在 pathspec 那侧，被当文件名找 → 0 命中
git grep -c -E '<pat>' HEAD -- '*.md'    # ← 对
```

写错了不会报错，只会"一条都没搜到"，表现成"这个仓库里没有场景清单"。
`_grep()` 现在把 ref 和 pathspec 分成两个参数，测试里用真仓库跑，锁住这个顺序。

## 4. 实测（UAG 项目，2026-08-26，commit dae9b4fc4）

357 行清单 / 24 个域 / 84 个用例脚本（清单路径和脚本范围都是自动识别出来的，配置里只填了仓库地址）：

- 分母 353（不含 4 条已废弃）：已覆盖 166、待补缺口 187
- P0 101/182（55%）、P1 60/145（41%）、P2 5/26（19%）
- **13 个「已覆盖」场景挂着 `@known-bug`**（GL#530/531/532/534）—— 13 条全都在已覆盖那边，
  也就是 47% 这个数字里含着 13 条**已知是红的**
- P0 且待补且风险 9 的：**59 条**（页面上一键能筛出来的那批）
- 清单未对上 0，孤儿脚本 0 —— 和 QA 自己 `check-coverage.sh` 的结论一致
- 风险 ≥6 却排在 P2/P3 的：1 条（AUT-16）

## 5. 页面按「测试员下一步干什么」排的

第一版把 total/covered/gap/deprecated/scripts 六个数平铺成六张卡片，问题不是不好看，是**看不懂**：
`P` `R` `层` `状` 四个单字列名是 QA 仓内部的缩写，平台这边没有任何地方解释 `R` 是什么；
一个数字看完之后没有下一步动作。改版后的规矩是两条：

1. **每个数字都是一个筛选入口** —— 点覆盖率里的 P0 行就筛 P0，点「P0 待补 · 风险 9 —— 59 条」
   就筛出那 59 条并按风险倒序，点域名就筛那个域。
2. **口径全部照抄 QA 自己的定义**，不自造词。`R = 概率(1–3) × 影响(1–3)`、
   「P 和 R 是两条独立的轴，不许互相推导」都出自那个仓库的 `docs/test-scenario-catalog.md` §1.1。

三块看板：

| 看板 | 回答的问题 | 关键点 |
|---|---|---|
| 覆盖到哪了 | 覆盖率 + 分优先级进度 | 明说分母不含已废弃；红字点破「其中 N 条挂着已知缺陷」 |
| 还欠多少 | 缺口总数 + 分优先级 | 一个红按钮直达「P0 待补 · 风险 9」 |
| 清单可信吗 | 清单和脚本对得上吗 | 前两项是 `check-coverage.sh` 会 BLOCK 的；第三项（风险 ≥6 却排 P2/P3）只是提醒 |

**「已覆盖」只代表有脚本声明了这个场景 ID，不代表这条跑过、更不代表跑绿了。** 平台只读仓库，
拿不到运行结果。这句话写在页面的「怎么读这一页」图例里 —— 不写的话 47% 会被当成"47% 是绿的"。

对应的服务端字段（都在 `_assemble` 里算，前端不再自己 filter 一遍）：

| 字段 | 含义 |
|---|---|
| `summary.coveredWithBugs` | 已覆盖但脚本头挂着 `@known-bug` 的场景数（**覆盖率虚高多少**） |
| `summary.knownBugScenarios` | 所有带已知缺陷的场景数（含待补的） |
| `summary.riskMismatch` | 风险 ≥6（`HIGH_RISK`）却排在 P2/P3 的场景数 |
| `summary.byPriority` | `{P0: {total, covered, gap}, ...}`（不含已废弃） |
| `domains[].gap` / `domains[].p0Gap` | 按域找「黑洞域」用；页面按 `gap` 倒序排，`p0Gap` 决定先啃哪个 |

## 6. 顺带清掉的三个入口

编辑项目弹窗现在只剩「项目名称 + 描述」。去掉的是「Git 仓库地址」「脚本基础路径」，
外加 QA 仓那一组字段（挪到 QA 页，见 §3）。前两个的理由：

- `git_url` 的唯一消费者是 `POST /projects/:pid/branches/:bid/sync`，而前端触发它的
  「同步用例」按钮早就没了；
- `script_base_path` 只有 `script_ref_file` 那种老用例执行时要（沙箱 checkout），
  这类用例只存在于「测试平台」项目（323/337），之后新建的项目一条都没有。

**数据库列、schema、执行引擎里的代码都留着** —— 老用例还得跑。去掉的只是"新项目还能在页面上
填这两个字段"这条路。真要给老项目改这两个值，改库或走接口。
