# CC ↔ 平台闭环：需求与落地方案

> 2026-08-08 定稿。来源：三轮 party-mode 讨论（Winston 架构 / Murat 测试架构 / Amelia 开发 / Sally UX / John 产品）+ 代码库实测核查。
> 这份文档的作用是**防走偏**——后面每做一件事，回来对一遍"边界规则"和"红线"。

## 0. 一句话边界规则（所有争议以此仲裁）

> **平台是被测系统的「事实库 + 可重复执行器」；外部 Claude Code 是「一次性的智能」。**
> **需要开浏览器 / 试错 / 看现场才能得出的结论，在平台外产生；需要跨时间、跨人、跨环境重放的东西，在平台内存着。**

判定方法：对每个功能问一句——它的产出是「一次性推理结果」还是「可重放的事实」？

| | CC 端（开发者本机） | 平台 |
|---|---|---|
| 写 / 改脚本 | **唯一写入方** | 只读 + 版本存档 + 回滚 |
| 首次跑通验证 | **必须在这里** | 不做 |
| 回归重放 | 不做 | **唯一执行者** |
| debug / 试错 | **唯一** | 不做 |
| 失败**分类**（是什么） | 不做 | **平台确定性规则** |
| 失败**归因**（为什么） | **CC** | 只存，不判 |
| 状态写入（通过率、维度状态） | 不能 | **唯一写入口** |
| 用例/脚本**评审**（值不值得进回归） | 自审（`lum_review_case`，回推完自己先过一遍） | **同一套判据、同一份代码**：证据由平台收集、判定写在代码里（有 blocker 一律不过、加权 <80 不过），模型只出判断题的答案 |

### 三条红线

1. **平台侧 AI 生成能力封存，页面入口下线。** 不保留"平台也能生成，只是弱一点"的分支——否则两年后是两套生成路径、两套 prompt、两套失败模式。

   ⚠️ **这条的理由必须写准，别用错的**（2026-08-08 修正）：常被引用的"实测几十次跑不通"是 **2026-07-20 引擎重构之前**的状态（LangChain + ChatOpenAI 伪装 UA + haiku）。重构后 `app/services/ai/ui_script_gen_service.py` 走 `cli_agent.py`（真 `claude --print` + Playwright MCP + 原生 tool_use），**和 themisai 的 `claude_code_executor.py` 是同一架构，而且实测通过**：
   - 简单用例 TC-SVC-00009：生成 + 保存 + 运行全通，55s
   - 复杂用例 TC-SVC-00002：生成 ~12min（34 步、含自愈）→ verify PASSED → 运行 passed 6.4s

   **真实的下线理由是这三条**：① 复杂用例 12 分钟，批量不可接受 ② **探索阶段真的在被测系统里建了数据且不清理**（脚本 cleanup 只在脚本运行时跑，探索期残留），批量 = 批量污染 ③ 只实测 2 条，广度可靠性从未验证。

   **代码没删，`ui_agent_engine=cli` 还在。重新启用的判据**：
   1. 探索期数据隔离做掉（隔离租户 / 数据前缀 + 兜底清理）
   2. 跑满 20 条测广度，拿到通过率和平均耗时
   3. 两条都过了，才评估是否作为「批量首稿」通道回来——届时它和本机 CC 是**分工不是二选一**：服务端出首稿（快、脏、量大），本机 CC 精修与自愈（准、慢、量少）。这样不违反本条红线，因为两者做的不是同一件事。
2. **回推的是脚本，不是结论。** CC 说"我本地跑通了"只作为参考；`ui_status` / `api_status` 升到 `executable`，必须以**平台执行器至少成功跑过一次**为准。
3. **CC 的归因不改任何状态。** 它进"待确认"通道。人在平台上的确认动作，是状态的**唯一**写入口。

   ⚠ **这条 2026-08-24 收窄过口径，别照字面读。** 现在归因**按证据齐不齐分流**
   （`analysis_service.route`）：脚本自己错 / 用例过期 / 环境 / 数据 / 不稳定这五类，
   加上三样自证齐全的产品缺陷，CC **自己处置，不进待确认通道**。
   **红线本身没破** —— `confirmed_cause`、用例维度状态、通过率、报告结论仍然只由人写，
   `self_serve` 动的只是失败跟进单的流转状态。变的是「谁来推进这张单」，
   不是「谁能改状态」。代价见 §13.2 变化 4：人工确认变少，`agreement_stats`
   会失去分母，所以补了抽检。

## 1. 目标流程

```
人：「服务管理模块 ui_status=未开始 的，三件套都做了；订阅管理只做步骤+接口」
                            ↓
CC：建立批次意图 → 逐条推进 → 每完成一个维度立刻回推
                            ↓
平台：执行（记账）→ 出报告 → 失败自动分类 + 打包证据
                            ↓
CC：领失败 → 读证据（截图/HAR/步骤轨迹/脚本）→ 结构化归因回填
                            ↓
人：在平台上看 CC 的归因 → 确认 or 推翻 → 分流处置
                            ↓
      script_bug → CC 改脚本回推 → 平台复跑（回到执行）
      system_bug → CC 起草 issue，人按发送（gh issue create，平台只存 issue_url）
      case_expired → 人改用例
      dependency → 补共享资源
```

**不做全自动无人闭环。** 没有调度、没有 CI，也不该现在建。形态是"**一次人工触发，一整轮自动跑完，停在人工闸口前**"。

## 2. 关键设计决策（含被否决的方案）

### 2.1 "一次性生成三件套" → 意图一次下达，产物逐个回推

**否决**：把 N 条用例 × 3 种产物做成一个原子批处理。
**理由**：60 个可独立失败的动作捆成一根绳子，断在哪平台上看不出来，只能整批重来。

**采纳**：
- 人的意图落成用例上的一个字段 `target_level`（`spec` / `spec+api` / `full`），**不新建批次表**——意图最终就是"每条要做到什么程度"，存在用例上它才是持久事实而不是一句聊天记录
- CC 每完成一个维度立刻回推一次，对应的维度状态（`manual_status` / `api_status` / `ui_status`）随之推进
- **断点续跑的判据就是这三个现成字段**：CC 续跑 = "把 `ui_status != executable` 的挑出来接着干"

### 2.2 三件套同源生成的质量代价（Murat 的反对意见，已采纳为约束）

传统流程里，步骤用例和自动化脚本是**两次独立的理解**。写脚本时发现和用例对不上而"卡住"，这个卡住本身就是缺陷检出。同源生成会让三份产物**必然互相一致**，而一致会被误读成"验证过了"——**一致性冒充正确性**。

典型失效：CC 把"创建成功"理解成"返回 200"，于是步骤写"预期：创建成功"、接口断言 `status==200`、UI 断言 toast 含"成功"。三层全绿。但真实业务是异步创建，200 只代表受理。**三件套同源，没有任何一层能发现。**

**采纳的分档策略**：

| 优先级 | 产物 | 方式 |
|---|---|---|
| **P0** | 三件套 | **强制两阶段**：先只生成步骤用例 → 人**只看「预期结果」这一列**并确认 → CC 再据此生成接口 + UI |
| P1 / P2 | 步骤 + 接口 | 一次性，允许 |
| P3 | 步骤 | 一次性，允许 |

P0 的人工介入点**刻意选得极窄**——不让人审全文（会疲劳、会盖章），只看预期结果一列，一屏二三十条五分钟过完。这是用最低人力把丢掉的交叉验证买回来。

平台侧强制：**`priority=P0` 的用例不允许一次性三件套直出，人显式选了也不行。** 质量门禁要能覆盖人的手滑。

### 2.3 失败分析：分层，不分栏

**否决**：平台判一个原因、CC 判一个原因，页面并排两栏让人选。
**理由**：把矛盾转嫁给用户；两栏一旦不一致，用户对两边都失去信任。

**采纳**：
- **平台判「是什么」**（分类）：超时 / 元素找不到 / 断言不匹配 / HTTP 5xx / 脚本异常。grep 错误栈 + HAR 就能出，确定性规则，不用 AI
- **CC 判「为什么」**（归因）：需要翻流量、看截图、读代码才能得出的因果链
- 页面上是**一条记录**：类型标签（平台给）+ 分析正文（CC 给，带署名和 run_id）。没归因过就只有标签——**这天然构成待办队列**

### 2.4 运动员兼裁判问题（CC 分析自己写的脚本）

偏差**确定存在**且方向可预测：系统性低估"脚本自己有问题"（把测试缺陷伪装成产品缺陷）、系统性低估 flaky（CC 看不到历史）。

**不禁止，用三条锁住**：
1. 归因**必须结构化 + 必须自证**：`evidence` 字段必须引用**平台侧证据**的具体位置（哪一步 / 哪条断言 / error_summary 哪句 / 第几张截图）。**没有指向平台侧记录的 evidence，直接拒收。**
2. 归因**不改状态**（红线 3 —— 2026-08-24 起五类可自证放行，但仍不碰 `confirmed_cause`，见那条的注）
3. 上线反向指标：`CC归因 vs 人确认` 一致率，按 `failure_type` 分桶。`product_defect` 桶推翻率 > 30% → 触发人工复核 CC 的归因能力。**这是目前平台完全没有的东西：对 AI 判断本身的质量度量。**

### 2.5 防退化锁（Murat + Winston 独立提出的同一件事）

**这套架构最大也最隐蔽的失败模式：CC 会"改得太好"。**

给它"让测试变绿"的目标，它一定能做到——加 `waitForTimeout(5000)`、放宽断言、`try/catch` 吞异常、条件 `skip`。每一条都能变绿，每一条都在销毁这条测试存在的理由。**这个失败不会以"报错"出现，它会以"一切正常"出现。**

**锁**：
- 每次回推记录**断言指纹**（条数 + matcher 类型分布 + 强度评分）
- 修复版本的指纹**不允许弱于上一版**；变弱 → 拒收，除非 CC 显式声明"上一版断言错误"并给理由，转人工队列
- 同一脚本**连续修复 3 次仍未通过 → 强制转人工**

⚠️ **Amelia 的技术否决（已采纳）**：断言"强度"**做不到可靠硬拦截**。Playwright 断言形态太多（`expect().to_be_visible()` / `assert` / `wait_for_selector` 都算；一条 `to_contain_text` 拆成两条数量还涨了但强度降了）。误拦会逼 CC 想办法绕（拆断言凑数），比不拦更糟。

**落地版**：
- **硬拦截只保留一条：新版本断言总数为 0**（100% 可判，且是最常见的作弊路径）
- 其余降级为**软警告 + 记账**：存 `assertion_profile`，回推响应返回 `warnings: ["强断言 to_have_text 3→1，弱断言 to_be_visible 1→3，疑似削弱"]`

### 2.6 批量入库的四道闸（全部在回推入口）

批量生成会淹库，两种淹法，第二种更难受：
- 明面的：300 条重复语义、断言宽松的垃圾——好发现
- **暗面的：每条单看都合理，合起来覆盖度极度倾斜**。20 条都在测"创建服务"的参数组合，零条测删除的级联影响。**总量涨了，风险覆盖没涨**，而通过率、用例数全面美化

已经踩过一次（"P0 占比超标 / 模糊词 / module 为空"），那次是入库后发现；批量化之后入库后发现 = 人肉从 300 条里捞。

| # | 闸 | 动作 |
|---|---|---|
| 1 | **语义去重** | 与同 module 已有用例比相似度，超阈值**拒**，返回"疑似重复于 XXX" |
| 2 | **断言强度** | 只断言 status code / 只断言"不为空" / 只断言 toast 文案 → 标 `weak_assertion`，**可入库但永不能升到 executable** |
| 3 | **P0 配额** | 单次批量中 P0 占比硬上限 **15%**，超了整批打回让 CC 重新分级 |
| 4 | **覆盖倾斜** | 算这批打在哪几个 module / 哪几类操作（增删改查 / 异常 / 权限 / 并发），某格过高或「删除」「权限」为零 → **告警 + 人确认** |

1~3 平台自动拒，4 告警。**全部作用在 MCP 回推入口——那是唯一入口，这是架构上最大的便宜，一定要占。**

### 2.7 调试执行 vs 记账执行

`script_runs` 加 `run_mode`（`regression` / `debug`）。通过率、报告口径只算 `regression`。
- `lum_run_ui_script`（单条，语义就是"聚焦调试用"）→ 默认 `debug`
- `lum_run_ui_scripts_batch`（批量回归）→ 默认 `regression`

跟工具现有语义正好对齐，不用改调用方。

### 2.8 四层变量：谁维护，分两块的理由

| 层 | **谁维护** | 存的是 | 能不能填死 |
|---|---|---|---|
| 环境变量 | **人** | **值**（`BASE_URL`、账号密码） | 能。人知道，每个环境填一次 |
| 项目级共享资源（自动化数据） | **CC** | **怎么找到值**（`{match:{name:"默认上游"}, extract:{upstreamId:"id"}}`） | **不能**。`upstreamId=35804052` 换环境是别的数字，资源重建了还是别的数字 |
| 场景变量 | CC | 本条用例每次跑要换的值 | 用 random / template |
| 步骤提取物 | 引擎 | 本次执行的临时值 | — |

**为什么必须分两块**：合并的后果是逼人把探测出来的 id 填成环境变量字面量——**那正是"变量不许写死"禁的事，只是换个地方写死**。分块的理由是「存值 vs 存找法」，**跟谁来维护无关**。

**自动化数据的定位（2026-08-08 修正）**：它的主要写入方**从来就是 CC**（`lum_upsert_automation_resource`），页面只是查看和兜底。曾把它描述成"人来配 exists_check"，那是错的——那个描述等于把它讲成环境变量的翻版。

**为什么全平台 0 行**：闭环缺一环——CC 登记完拿不到回音。`lum_list_global_data` 只列静态定义，**不跑探测、不返回 `create_def`**，CC 无从知道"这个环境里现在缺不缺、缺了当初是怎么造的"。没有反馈，这功能进不了它的工作流。

**`create_def` 的执行归属，2026-08-21 复核后改口径。** 早前这里写的是"平台不执行 `create_def`，造数据归 CC"（同时撤回了更早的"人工补建按钮"方案）。**现在平台在执行期会真补建**，理由是原来那条口径漏了一种情形：`${资源名}` 是写在 JSON 步骤里的，链子**自己没有 if/else**——底座缺失时它只会红在"变量未解析"上，而"缺了就去造"这件事 CC 只能在**下一轮**做。于是二十条链一起红，等 CC 回来。既然 `create_def` 里已经登记了"当初是怎么造的"，那就该由跑的人现场补上。

分工现在是这样，**两条路行为不同，别混**：

| 入口 | 行为 | 在哪 |
|---|---|---|
| 页面 / 预检 / `lum_list_global_data(probe=true)` | **只探不建**，报 `state` + `canCreate` | `precheck_service._check_one` |
| 接口场景执行前 / UI 脚本执行前 | 探到 `missing` **且**有 `create_def` → 照它补建 → 复探一次 | `api_test_runner._resolve_automation_resources` → `_auto_create_resource` |

只认 `missing`（探测请求成功且明确没匹配上）。`unknown`（401 / 5xx / 超时 / 没配 url）一律不动——一次 token 过期就照着建，会在被测环境里造一堆重复底座，而且 `keep=true` 没人清理。

⚠️ **页面文案从"过度承诺"翻成了"反向说谎"（2026-08-21 修）。** 原来的问题是列名叫「缺失可自动创建」而代码只存不执行；改文案那次改成了「平台不会替你建 · CC 按定义自建」——而此时执行期已经会建了。**同一类 bug 换了个方向**：页面说的和代码做的不一致，只是这次是往低了说。判据别再取"平台建不建"这种全局说法，取"**在哪个入口**"——预检不建、执行前建。

### 2.9 国际化词典：是"不许写死"的另一半

**这一节的"缺三样"已经补齐（2026-08-21 复核）。** 写这节时的现状是：词典有 33 条、采集能用，但**没有任何消费方**，脚本里仍是硬编码中文，`pw_conftest.py` 靠注入 `locale=zh-CN` 把语种锁死。现在：

| | 数据 | 文案 |
|---|---|---|
| 不许写死 | ✅ 硬拦截 | ✅ 未解析的占位**拒绝执行**（`executor.py` / `ui_text_render.unresolved`） |
| 从哪取 | 场景变量 / 全局引用 / 提取物 | i18n 词典，脚本里写 `${键\|中文原文}` |
| 换环境 / 语种 | 平台注入真值 | 平台按 `PLAYWRIGHT_LOCALE` / `TEST_LANGUAGE` 渲染译文 |

**形态跟当初设想的不一样，是故意的**：不是 `t("登录")` 函数调用，而是 `${键|中文}` 占位。理由——脚本里别的取值都是变量形态（`os.getenv("SV_x")`、断言里的 `${svcName}`），只有文案是函数调用的话，读的人看不出 `t()` 也是"平台注入的数据"。替换发生在**执行前的源码文本**上，和替换 `os.getenv` 默认值同一处。

落地在四条执行路径（MCP 跑 / 页面跑 / 计划·回归·批量共用的那条 / 导出包），
外加 `pw_conftest` 收词典给残留的 `t()` 兜底。**为什么必须四条都渲染**：漏一条的后果不对称——正例红在「找不到元素」上（看得见），而「不应出现」这类负例**假绿**（未替换的占位匹配不到任何元素，"不该存在"当然成立）。这个库为此栽过两次，第二次是计划/回归/批量共用的 `_run_new_style_script`（见 §9.6 ①）。现在 `backend/tests/test_silent_key_mismatch.py` 里有一条结构性断言钉住"凡是把脚本写进沙箱的地方都得渲染"。

### 2.10 多人并发回推：能跑，但有三个坑

| # | 问题 | 后果 | 修法 |
|---|---|---|---|
| **严重** | `sync.py:116` `_active_user_id()` 注释原话"MCP 无登录上下文：取一个真实 active 用户（优先 admin）"。而 `mcp_api_keys` **有 `user_id`**，`middleware._resolve_scope` **已经按 key_hash 把那行查出来了**，只取了 `allowed_tools` 就丢了 | 所有人的回推 `created_by` 全是 admin；操作日志失去意义；**§2.4 的「CC归因 vs 人确认」按人分桶算不出来** | 中间件把 `user_id` 一起带出；`_active_user_id` 改成优先用调用方身份 |

**归属那条必须排在第二刀之前**——一旦多人开始用，之前攒的归因数据就全废了（分不清谁的）。

### 2.11 明确不做

| 不做 | 理由 |
|---|---|
| 平台侧 AI 自愈 / 自动改脚本 | 自愈 = 带失败上下文的生成，难度只高不低；且和红线 1 的三条下线理由（慢、污染被测环境、广度未验）完全同构 |
| **平台执行 `create_def` 自动补建** | 造数据归 CC（见 §2.8）。平台只报"缺了什么 + 当初怎么造的" |
| i18n `t()` 运行时 | 不进第一刀。词典现在 33 条且无消费方，先把回推链跑顺 |
| `repair_queue` 表 + `lum_claim_repairs` + 自愈次数计数器 | 为"多 CC 实例并发领任务、无人值守失控"这个不存在的场景做工程。**现在是一个人，人就是护栏。** 待修清单 = 执行历史上一个筛选条件 |
| 定时调度（cron / celery / APScheduler） | 会引入一个需要长驻、需要监控、会静默死掉的组件；已有两个长驻进程的维护成本。触发用 CC 的 `/loop` 或本地 crontab |
| 缺陷系统对接（Jira / 禅道） | CC 端有 `gh` 和文件系统，issue 在那边提，平台只存 `issue_url` 回链。**平台一行代码不用写** |
| 「病历」概念 + `case_file_events` 独立页签 | 三条时间线（病历 / 执行历史 / 生成档案）说的是同一件事，只需要一条 |
| `case_expired` 自动分诊 | 需要知道"预期该是什么"，HAR 里没有这个信息。并入 `unknown`，交给 CC 用视觉判 |
| healing_context「≥6 条压缩成摘要」 | 那是外部 agent 上下文有限的实现细节。**平台永远不该存外部智能的中间态。** |

> 覆盖率约 8%……本轮核心风险——异步一致性、汇总数据准确性、证据包可用性、
> 归因提交边界——均未触碰……**不能据此给出"整链复验通过"的判断**

**③ 捞到一个更严重的：章程解析失败被静默吞掉。**
`json.loads` 失败 → 截到最后一个 `}` 再试 → 还失败就返回 `{}`，然后**照样存库、
照样 yield done**，前端弹「章程已生成」。而 `{}` 是 truthy，前端判据 `!charter`
过不了，于是渲染出一个空壳：「检查点 (0/0)」、「完成当前检查点」永远禁用、
连"生成章程"的入口都找不回来 —— 一次 AI 输出抖动就静默废掉整条链，人只看到
一条成功提示。改成：解析不出检查点就是失败，报错并让人重试；前端判据改成
「有检查点」而不是「有 charter」。

**自己刚修完又犯一次**：新写的 summary 解析里，内层 `json.loads(text[:last+1])`
同样没兜住，直接 500。两层都要 try，兜底退化成纯文本结论。
记这一笔是因为它说明**"截断再解析"这个模式本身就该配 try**，不是个别疏忽。

### ✅ 补：flaky 自动隔离（2026-08-09，11/11 活体验证通过）

这条原本在下面的「延后」表里，理由是"脚本数是个位数，隔离服务的是想象中的规模"。
**这个理由站不住**——去看了一眼现状才发现，`is_flaky` 已经在用了，而且用法是有害的：

- 它是个**人工布尔**，`execution_service` / `execution.py` 两处直接 `if case.is_flaky: 跳过`；
- **一旦标上就永远跳过，没有回来的路**。脚本修好了也不会自动恢复，页面上也没有解除入口；
- 跳过时 `error_summary` 一个字不说，报告里只看到"skipped"，不知道为什么。

所以做的不是"上一套隔离机制"，是**给已经存在的跳过加上判据、期限和回来的路**。

| 做了什么 | 关键点 |
|---|---|
| `flaky_service.evaluate()` 挂在 `record_run` 这个唯一写入点 | 四条执行路径（单条调试/计划回归/批量/adhoc）自动都过一遍，不用各自记得调 |
| **判定按 `script_id` 分组** | 最容易错的一条。实测库里 `TC-XMGL-00001` 有两个脚本版本各自有失败——不分组的话，**一次成功的修复会被判成 flaky** |
| 只判"翻转"，不判"失败" | 一直坏（`failed×3`，翻转 0）和刚坏（`passed,passed,failed`，翻转 1）都**不隔离**——真 bug 必须继续报警，不能被隔离藏起来 |
| 14 天到期**自动失效** | 判据写在 `is_quarantined()` 里按时间比，不需要谁去清理；到期那一刻自己回来 |
| `flaky_evidence` 存每次执行的 runId/结果/错误 | 隔离是"平台替你做的决定"，必须能复核。详情页 popover 直接列出来 |
| `POST /cases/{id}/release-quarantine` + 页面「解除隔离（脚本已修好）」 | 人随时能推翻平台的判断，且**保留 evidence 备查** |
| 不覆盖人工 `is_flaky` | 人标的优先，自动判定不去动它 |

跳过时的 `error_summary` 现在说人话：人工标的说「人工标记为 Flaky，本次跳过」，
自动隔离的说「自动隔离中（同一脚本版本最近 3 次执行里结果翻转了 2 次），YYYY-MM-DD 到期后自动恢复执行」。

活体验证（`/tmp/verify_flaky.py`，真往 `script_runs` 写执行记录、走真实 `record_run`）
覆盖六个场景 11 项断言全过：稳定通过→不隔离；`passed→failed→passed`→隔离且证据齐；
**一直失败→不隔离**；**换脚本版本修复→不误判**；到期→自己回来；人工解除→立即恢复。
页面侧另验了列表「隔离」徽标、详情 popover 依据、解除后徽标消失，无 JS 报错。
封样 13 条单测（`tests/test_flaky_quarantine.py`），阈值常量被钉住。

**阈值仍然没有数据支撑，这次也没装作有。** 本想拿真实数据校准，结果库里只有 43 条
`script_runs` / 3 条用例，失败还多半是我自己造的——**样本量不够，校准是自欺**。
所以三个常量走环境变量（`FLAKY_WINDOW` / `FLAKY_FLIPS` / `FLAKY_QUARANTINE_DAYS`），
`flaky_service` 的 docstring 里写清了它是经验值、以及日后怎么校准（取稳定脚本翻转率的
95 分位当阈值）。这一条继续留在下面的延后表里。

### ✅ 补：把「文档优化」接上入口（2026-08-09，API 14/14 + 页面 17/17）

AI 能力清单里 `doc-optimize` 一直标着「暂无入口」。查下来实现是完整的：
`POST /documents/{id}/optimize` 保留截图、只按修改意见重写文字。**没人调它**，
页面上只有一个「重新生成」，走的是 `generate-with-screenshots` —— 要重填账号、
重新登录被测系统、把每一页重截一遍。想改一句话得付这个代价。

所以这次不是"做个新功能"，是**把已经写好的那条便宜的路露出来，并把两条路的代价标清楚**：

| | 优化文字 | 重新生成 |
|---|---|---|
| 碰不碰被测系统 | 完全不碰，不用填账号 | 拿账号真登录、点导航、截图 |
| 截图 | 沿用现有的（弹窗直接报"沿用 N 张"） | 全部重截 |
| 适用 | 文字不好、要补说明、要调结构 | 页面改版了、要补新模块 |

**接入口之前先补了后路。** 这个接口是直接覆盖 `doc.content` 的，之前没有调用方所以
覆盖不到人；一旦露出来，覆盖就成了真实风险——一篇文档是"真登录 + 逐页截图 + AI 写"
跑出来的，AI 改砸了原文没了就得重跑一遍。所以：

- 迁移 `s3a4b5c6d7e8` 加 `documents.previous_content`，覆盖前存旧正文
- `POST /{id}/revert-optimize`：两版**对调**而不是丢弃，来回撤都行
- 列表只回 `canRevert` 布尔，不把整篇旧正文塞进列表响应
- AI 一个字没回来时**不覆盖**（否则等于把文档删了），空文档不许优化（否则 AI 会
  凭空编一篇没有截图的假手册）
- 优化完**报截图数**：`imagesBefore/imagesAfter`。少了就弹确认框，把「撤销这次优化」
  直接递到手上 —— "保留截图"是这条路唯一的承诺，兑没兑现不该让人自己去数

活体验证都是真调 AI 真覆盖：API 侧 14 项（修改意见真被采纳、旧正文一字不差退得回来、
来回切不丢版本、空文档 422、没优化过点撤销 422），页面侧 17 项（两个按钮并存且悬停
各说各的代价、弹窗报"沿用 4 张截图"、跑的时候字数在动、完成提示"4 张截图都在"、
列表和抽屉都能撤销、撤销后标记真的没了、无 JS 报错）。

顺手修了同一页一处哑的地方：`platContent` 一直在攒流式正文却从没显示过 ——
一篇文档要写好几分钟，进度只有几行 step，人看不出到底还在不在动。现在报字数。

### ✅ 补：工具范围从 Key 级挪到项目级（2026-08-10）

**用户提了两次，第一次我口头应了、没写进任何文档，于是没做。** 记在这里，别再丢。

**原来的形态**：范围存在 `mcp_api_keys.allowed_tools` 上。每建一把 Key 都要重选一遍范围，

### ✅ 补：Mock 那一组的完整联调（2026-08-09，32/32 + 6/6）

之前只验到「页面打得开 + 锁能锁」。一个 Mock 服务真正要成立的是一整条：
**建条规则 → 起服务 → 从外面真打一发 → 收到的正是我配的那个响应 → 停掉之后真的连不上**。
中间任何一环断了，它对使用者就是废的。这次七个全走了一遍：

| Mock | 端口 | 怎么验的 |
|---|---|---|
| HTTP | 28200 | 真发 GET，状态码/响应体都是配的那份，调用进了请求日志 |
| LLM | 28100 | 真发 `chat/completions`，OpenAI 兼容结构（choices+usage），model 跟随请求 |
| OAuth2 | 28800 | 真换 token → introspect 说 active → JWKS 拿得到公钥 → **密钥错了要拒** |
| MCP | 28300 | 真 MCP 客户端 initialize + tools/list + tools/call，回的是配的假数据 |
| WS | 28400 | 真连一条 WebSocket 收发 |
| TCP | 28500 | 真开 socket 发字节 |
| UDP | 28600 | 真发数据报 |

外加：停服务之后**端口是真的关了**（不是只把状态改成 false），再起回来还能用。

**捡到两个真 bug，都在 MCP Mock：**

1. **建一个不带参数的工具，MCP Mock 从此再也起不来。**
   `ToolCreate.params` 默认 `None`，`add_tool` 用 `get("params", {})` 存下去 ——
   键在、值是 `None`，默认值用不上。起服务时迭代 `None` 直接 TypeError，
   整个服务起不来，**页面上只显示"已停止"，不说为什么**，删掉那个工具之前永远起不来。
   代码里本来防过同一类问题（工具名非法产生 SyntaxError 会"把整个 MCP Mock 启动永久打死"），
   这次是同一个形状的另一个入口。修法：写入时归一成 `{}`，读取时再兜一次，
   并且**每个工具的注册单独 try** —— 一条配坏了，代价应该是这一个用不了，不是整个服务起不来。

2. **页面上加了工具，对面 CC 根本看不到。**
   FastMCP 的工具是建 app 时一次性注册的，改 `self._tools` 不影响已经跑着的实例，
   而页面上没有任何地方提示要重启。现象是"工具建了但用不了"，人只会以为没建成功。
   修法：工具增删改之后自动重载。重载 = 停 + 起，**停完立刻起会撞上端口还没释放**
   （旧监听还在收尾，新连接被路由过去然后被掐断），所以等端口真空出来再起、
   起不回来要如实报出去 —— 悄悄留下一个停掉的服务比不重载更糟。

5 条单测钉住第 1 个（含"存量 `params=null` 的脏数据也要能起"和"一个坏工具不影响其余"）。

顺带记一条给后面接手的人：**TCP/UDP 的匹配模式只有 exact / hex / regex，没有 contains**
（前端也只给这三个）。第一轮验证我按 `contains` 配，TCP 那条"过了"其实是没匹配上、
走了 echo 兜底把输入原样回显 —— 断言写成"响应里包含标记"就会假过。
断言收严成"必须等于我配的那份"之后才暴露出来。

### ✅ 补：测试工具那一组的完整联调（2026-08-09，31/31 + 13/13）

跟 Mock 那组同一个标准：不是"页面打得开"，而是真用一次、结果得是对的。
靶子用平台自己的 HTTP Mock 造一条确定性路由，不依赖外网。

| 工具 | 怎么验的 |
|---|---|
| 工具箱 | AI 生成正则（生成的正则真能匹配手机号）/ JWT 签名（**用本地算法验签**，不是看它有三段就算过）/ HMAC（和本地 hexdigest 逐字比）/ HTTP 代理请求 |
| HTTP 请求 | 存一条 → 真发 → 200 且正文是靶子那份 → 回显实际发出的请求 → 进历史 |
| 压力测试 | 建场景+步骤 → k6 脚本含靶子地址和并发配置 → 真跑一轮 → 4 发全成功、有 p95 |
| 代理观测 | 起代理 → 真走一条 → 抓到并标记已转发 → 注入「全部拒绝」→ 请求真被拒 → 撤销后恢复 |

**捡到三个真问题：**

1. **工具箱「AI 生成正则」把一整个 JSON 文档填进了正则输入框。**（有截图）
   正则里几乎必然出现 `\d` `\w` `\s`，而它们在 JSON 字符串里是**非法转义** ——
   模型少写一个反斜杠 `json.loads` 就炸，而原来的兜底是**把整段原文塞进 regex 字段**。
   用户看到的是"正则语法错误"，完全不知道发生了什么。
   更麻烦的是它**间歇发作**：模型偶尔规规矩矩写 `\\d`，那次就正常 —— 比稳定坏难查得多
   （第一轮验证正好赶上正常的那次，差点放过去）。
   改成三层解析（直接 loads → 补非法转义再 loads → 正则抠 `"regex"` 字段），
   底线是**任何分支都不许把整段 JSON 当成正则返回**，解不出来就老实报"这次没解出来，再试一次"。
   9 条单测钉住，含"任何分支返回的 regex 都不以 `{` 开头"。

2. **压测的错误分布拿状态码顶包，把真实原因丢了。**
   断言没过时，错误分布的分类键是 HTTP 状态码 —— 页面上显示「错误分布: 200 × 4」，
   读起来像"服务器返回 200 也算错"。真实原因（`error_msg`）算出来了却被丢弃。
   改成有原因就用原因当键，现在显示的是
   「断言未过：期望状态码 500，实际 200」「断言配置有问题：status 没有给比较值」。

3. **断言字段名两边不一样，配错了会静默把每一发都判失败。**
   压测页面写 `value`，接口场景/回推那边写 `expected`（见 `lum_sync_orchestrated_scenario`）。
   用后者配压测断言，`str(200) == ""` 恒假 → **每一发都算失败**，而原因还显示成状态码。
   现在两种写法都认；断言压根没给值的，明说是"断言配置有问题"，
   别让人以为是被测系统坏了。

**顺带**：`toolbox-regex` 这个 AI 能力档位一直标着「已下线 / 后端无任何调用方」，
但功能**一直是通的** —— 端点直接 `complete()` 没带 capability，所以档位绑了模型也不生效，
于是干脆被标成下线。现在走 `resolve_ai_config`，标签改成真实入口
「工具箱 → 正则测试 → AI 生成」。这是本轮第三个"页面说自己已下线、其实还活着"的地方。

### ✅ 补：148 个 GET 端点全量扫一遍（2026-08-09，139/139）

上一条（`lum_get_merged_variables` 一直坏着没人发现）的教训是：**没人系统调过的接口，
坏了也不会有人知道**。所以把平台所有 GET 端点扫了一遍。

方法上有两条讲究，不然扫了等于没扫：

- **路径参数用真实 id 填**，不是造假 UUID。假 id 只能测出 404，测不出序列化崩溃 ——
  而 `lum_get_merged_variables` 那个 bug 正是只有拿真数据才暴露。
- **判据只认服务器自己的问题**（5xx / 422 / 静默错误结构）。404、403 不算 ——
  那可能只是这条数据不存在或没权限。

**捡到一个：`/api/llm-mock/logs/export` 一调就 422。**

`/api/llm-mock/logs/{log_id}` 注册在它前面，FastAPI 按顺序匹配，`export` 被当成
`log_id` 去解析 UUID。LLM Mock 页面上「导出日志」是 `window.open(...)`，
点下去只会开出一个满屏 422。而隔壁 `api_mock.py` 里两条路由的顺序**恰好是反的**，
所以那边一直好用 —— 两个几乎一样的页面表现不同，这个 bug 就这么活了很久。

这类错**看代码基本看不出来**（两个装饰器隔着几十行，各自都没毛病），
所以配了一条全仓封样：遍历真实路由表，任何"固定路径被前面注册的通配路径吃掉"
都会红。把修复 stash 掉验证过它确实会红，不是空跑。

**扫的覆盖度如实说**：148 个 GET 里真调了 139 个。
- 4 个刻意跳过：SSE 长连接和导出下载类（会挂住或产文件）

### ✅ 补：计划的「已暂停 / 已归档」是两个走不到的状态（2026-08-09，接口 14/14 + 页面 12/12）

**页面上一个都没接**。而计划列表有「已暂停」「已归档」两个筛选页签、有状态色、有标签 ——
有筛选、有颜色、有名字，就是没有任何路径能走到那个状态。

接的时候撞上两件事，都比"加几个按钮"要紧：

**一、归档是单向门。** `archive` 收 `draft`/`completed`，而 `reopen` 只认 `completed`，
`archived` 不在任何入口的允许列表里 —— 点下去就回不来了。

补了 `unarchive`：跑过的回「已完成」，没跑过的回「草稿」，
靠"有没有报告"这个可查的事实判，不额外存字段。

**二、`abort` 有个潜伏的 500。** 计划没有报告时，终止会崩在序列化上：
`updated_at` 是库侧 `onupdate`，`flush()` 之后处于 expired 状态，
pydantic 读它会触发一次惰性加载，而那已经不在 async 上下文里 → `MissingGreenlet`
→ 500 + 事务回滚。用户点「终止」看到"服务内部错误"，计划纹丝不动。
`pause`/`resume` 都在序列化前 `refresh` 过，`abort` 的 refresh 却挂在 `if report` 里面。
改成无条件 refresh。

**契约守卫被自己的改动照出来了一处不够精确**：新按钮的地址是
`plans/${id}/${action}`，最后一段是变量，精确匹配判成"后端没有这条路径"。
改成**两边的 `{}` 都当通配**去匹配 —— 段数对不上、前缀写错了照样红
（planted 了一条多两段的假地址验证过），但合法的动态调用不再误报。

顺带补上契约扫描的两个漏网 verb：`api.download`（3 处 Excel 导出）和
`api.sseStream`（场景生成的事件流）。这两类调用点**此前从来没被检查过**，
而且是安静地没被检查 —— 正面看那两条断言一直全绿。
所以加了第三条：**`request.js` 暴露的 verb 一个都不许漏**，
新增 verb 而检查不认识它就会红。`sseStream` 正是这条守卫第一次跑就抓出来的。

### ✅ 补：状态枚举补齐 + 全站按钮走查（2026-08-09）

**一、需求里没做完的：6 种状态只实现了 4 种**

`change-sync-log` 的「状态枚举扩展」要求
`passed / failed / error / skipped / xfail / flaky`，
通过率 `passed / (passed + failed + error + flaky)`，skipped 和 xfail 不进分母。
实现里只有 4 种，缺的两种各有后果：

- **flaky**：用例失败后重试通过，最终记成 `passed`，只在备注里写一句
  「重试 2 次，最终通过」——**通过率照样算 100%**。一次就过和试了三次才过，
  对使用者是完全不同的两件事，这正是这个状态要防的"假通过"。
- **xfail**：pytest 的预期失败在 junit 里是 `<skipped type="pytest.xfail">`，
  被并进"跳过"。分母没算错（两者都排除），但报告上写"跳过"读起来像没跑。

补齐：迁移 `u5c6d7e8f9a0` 加两个计数列；junit 解析按 `type` 区分 xfail；
执行器把"重试之后才通过"记成 `flaky`；分母加上 flaky。

**发现的连带问题：汇总卡片的两个百分比用了两个不同的分母。**
通过率按 `passed+failed+error` 算、失败率按 `totalScenarios` 算，
于是卡片上出现「通过 2 (50.0%) / 失败 2 (28.6%)」这种加不到一起的数（有截图），
而且都和后端算的 `pass_rate` 对不上。统一到规范口径后是 2/5 = 40.0% 和 40.0%。

活体验证：造一份含 6 种状态各一条的临时报告，页面上 6 种都渲染出名字
（以前多出来的会是空白格）、筛选条自动多出「重试后通过」「预期失败」、
两个百分比同分母。14 条单测封样，含「六种状态前端 statusMap 都得认得」。

| 图标白名单漏了顶栏三件套 | 语言切换 / 通知 / 侧栏折叠**每页都漏**，一共漏了 80 多次点击 |

38 个有副作用的（删除/清空/执行/启停服务/导入导出）刻意没点，逐条列了名 ——
不假装点过。

### ✅ 补：flaky 阈值真校准了 —— 样本不够就自己造（2026-08-09）

之前两次都写"库里只有 40 多条执行记录，样本量不够校准"。**那是懒。**
造三条脚本、每条真跑 24 轮（每轮真起浏览器），分布就有了：

```
stable   PPPPPPPPPPPPPPPPPPPPPPPP     实际失败率  0%
flaky40  FFFFPPPPFFFPPFFFFPPPPFPP     实际失败率 50%（脚本设定 40%）
flaky10  PPPPPPFPFFPFPFPPPPPPPPPP     实际失败率 21%（脚本设定 10%）
```

**结论一：噪音底线是 0。** 稳定脚本 24 轮零翻转 —— 环境抖动不会造成误隔离，
判据可以做得更灵敏而不用怕误伤。这条是之前完全不知道的。

**结论二：原来的 3 窗口是错的。连续失败不产生翻转。**
`FFFF` 的翻转数和 `PPPP` 一样是 0，于是"成片挂"的脚本躲过阈值：
50% 失败率的那条要跑到**第 23 轮**才被抓，21% 的第 8 轮就抓到 ——
**严重程度和检出速度反相关**。

**结论三：方向判据是对的，不能换成"窗口里既有 P 又有 F"。**
二值序列里连续两次翻转必然一来一回，所以 `>=2 翻转` 天然免疫"修好了"
（`FFFF→PPPP` 只有 1 次翻转）。而"混合"判据实测**在第 5 轮就把修好的用例关起来**。
错的只是窗口太短。

所以只改窗口：3 → **最近至多 7 次**（"至多"很重要，攒满才判的话强交替要白等 4 轮）。

| | 一直通过 | 一直失败 | 修好了 | 刚开始挂 | flaky40 | flaky10 | 强交替 |
|---|---|---|---|---|---|---|---|
| 原 固定 3 窗 | ✓ | ✓ | ✓ | ✓ | 第 23 轮 | 第 8 轮 | 第 3 轮 |
| **现 最近至多 7 次** | ✓ | ✓ | ✓ | ✓ | **第 9 轮** | 第 8 轮 | 第 3 轮 |

蒙特卡洛（10 轮内触发概率）：失败率 0% 和 100% 都是 **0%**（不误判、真坏的继续报警）；
50% 时 83% → **98%**；20% 时 71% → **81%**。

**改完再上平台真跑一遍**（不是离线算序列，是看平台自己做了什么）：
stable 12 轮一次都没被误隔离；flaky40 **第 9 轮被平台自己隔离**，
证据落库「同一脚本版本最近 7 次执行里结果翻转了 2 次」+ 7 条可复核记录。4/4。

还剩一个真的造不出来：**隔离 14 天**这个数取决于"人多久会回来看"，
那是团队习惯不是统计量，只能等真实使用。

### ✅ 补：P0 两阶段该不该留 —— 实测 80% 会退化（2026-08-09）

原话是「若实测 CC 的 P0 三件套一致性错误率 < 5%，我第一个撤回」。
之前答"分母是 0，测不出来"。同样是懒 —— **样本可以造**。

**怎么把这个说法变成可量的东西**：断言退化成弱代理，就是"一致性冒充正确性"的指纹。
所以造 6 条 P0 用例，每条的「预期结果」都**明确写死要读回来验证**，不留含糊空间：

> "创建之后必须再查一次列表，确认这个名字真的出现了；**只看 201 不算数**"

然后让平台从**同一份用例**生成接口场景（这就是"同源"），按写死的判据打分：
只有一步、或所有断言都只断 HTTP 状态码 → 弱代理；有"读回来"那步且断言了响应内容 → 真验证。
判据在代码里，不靠事后主观打分。

| 用例 | 结果 |
|---|---|
| 创建项目后列表可查 | ✅ 真验证 |
| 删除后列表不再出现 | ❌ 弱代理：2 步全是只断状态码 |
| 改名后详情里是新名字 | ❌ 弱代理 |
| 环境变量新增后能取到 | ❌ 弱代理 |
| 用例创建后编号自增且可查 | ❌ 弱代理 |
| 重复创建同名要被拒 | 生成直接失败（AI 返回的 JSON 解析不了，重试多次仍失败） |

**弱代理 4 / 5 = 80%。** 远高于"< 5% 就撤回"那条线，所以 **P0 两阶段门禁留着**，
而且这次是有数支撑的，不是谁的直觉。

最值得注意的是：**用例里已经白纸黑字写了"只看 201 不算数"，生成出来的照样只断状态码。**
把要求写进 prompt 挡不住这件事 —— 这正是"人得看一眼预期结果那一列"的理由。

顺带一个可靠性数据点：6 次生成里 1 次直接失败（1/6），失败原因是模型返回的 JSON 解析不了。

## 8. 用例模块整体走查（2026-08-10，全部实测）

起因是一句提问：「用例管理这个模块功能都检查了吗，都有正确的入口和收敛吗」。
逐页查下来七个问题，根子只有一个。

### 8.1 根因：两条执行通道，互相不知道对方存在

| | UI 脚本 | 接口场景 |
|---|---|---|
| 存哪 | `scripts` | `api_test_scenarios` |
| 跑完写哪 | `script_runs` | `test_reports` |
| 哪个页面看得到 | 用例 → 执行历史 | 测试报告 |

`api_test_runner._create_report` 直接建 `TestReport`，**从不调 `record_run`**。
于是同一条用例在两个页面各显示一半事实，看着像互相矛盾：
用例执行历史里 28 次全是 UI，而它的接口场景已经跑出 69 份报告。

**修法**：接口执行也落 `script_runs`（绑 `report_scenario_id` + `case_id`），
一次执行两处都记。这一条修完，「执行历史只有 UI」和「报告页全是接口」同时消失。

### 8.2 由此暴露的连带问题

| 问题 | 真实数据 | 修法 |
|---|---|---|
| 「可执行」永远靠手改 | `apply_case_status` 写死 `script_type != "ui"` 直接 return，接口维度整个是死的 | 两维一视同仁 |
| 批量执行说「N 个无脚本」 | 它有脚本，只是状态没到 `executable` | 拆成「有场景但状态没到」和「真没有」两句，各自说清下一步 |
| 场景列的 API 标签隐身 | 只看 `cases.api_scenario`；MCP 回推写的是 `api_test_scenarios`。7 条绑了用例的场景 100% 不显示 | `list_case_assets` 两个存储取并集 |
| 「手动」标签无信息量 | 硬编码，257/257 全亮 | 按真实步骤数显示；三样都没有显示「空壳」 |
| 执行轨迹 / 接口视图两个空页签常驻 | 全平台 **0/204** 条用例有 `lastResults`（生产者是已封存的平台侧 UI 生成）；`captured_requests` 库里有但 `/runs` 不返回 | 有数据才给页签；`/runs` 补 `capturedRequests` + `failurePhenomenon` |
| 来源页签八成是空占位 | 49/257 有溯源 | 有内容才出现 |
| 计划页状态列被操作列盖住 | 操作列声明 160px，4 个按钮实占 224px，`justify-center` 向两侧各溢 32px。实测 `overlap: 32` | 加宽 + 全列 `flexShrink: 0`。实测转为 `-16` |
| 计划页看不出跑 UI 还是接口 | `test_type` 一直在库里，列显示的是 `plan_type`(自动化/手动)。12 条计划全是 `api`，页面上无从得知 | 补「执行」列 |
| 报告页「类型」名不副实 | 它是**入口通道**不是执行方式 | 拆成「入口」+「执行」两列 |
| 报告名差 8 小时 | 名字用 UTC 拼，列表按本地渲染 `createdAt` | 两处都 `astimezone()` |
| 「待审」看得见改不了 | 审核动作只在 AI 生成向导第 5 步 | 列表上就地通过/打回 |

### 8.3 执行详情：给人看还是给 CC 看

原先不分类型一律甩一屏 pytest stdout。现在：

- **接口**执行落中文轨迹（步骤 + 每条断言写成「状态码 == 200」，失败带实际值），直接展开
- **UI** 执行只有 pytest 原文（执行器就这一种产物），先给失败现象 + 错误摘要 + 截图，
  原文收进「原始日志（排查用）」折叠

### 8.4 这一轮暴露的自测毛病（比 bug 更值得记）

1. **只验刚改的那个点，不验模块还成不成立**。`/runs` 不返回 `capturedRequests`
   这种，顺着页面点一遍就会发现，但没人点。
2. **断言停在数据库**。`failure_phenomenon` 后端算好落库了、测过落库，
   但接口不返回、页面看不见 —— 验证没有走完最后一段。
3. **拿空数据当"正常"**。走查脚本自动进了第一个项目，0 条计划，页面一片干净，
   差一点报「排版正常」。**空页面能通过任何检查。**
4. **断言里写 `or True`**。第一版走查脚本的时区那条恒为真。
   收紧之后立刻抓到一行真的没修好的历史数据。

对应纪律：断言要限定到目标那一层（列索引、行类型），
不能拿整页 `inner_text()` 做包含判断 —— 侧边栏里什么词都有。

### 8.5 第二轮走查（同日，问的是「这两个功能测过吗」）

三个问题，都不是显示层的毛病，是**行为**的：

**① 抓包 91% 是噪音。** 实测一次登录+建项目抓到 75 条，其中 68 条是前端源码模块
（`/src/App.jsx?t=…`、`/@vite/client`），真接口只有 7 条。人要在 75 行里挑出那 7 行，
等于没给。`har.py` 的静态资源名单漏了两处：`.jsx/.tsx/.ts/.vue` 不在扩展名表里；
dev server 发的是 `text/javascript`，而 mime 表只有 `application/javascript`。
补完 + 加 dev-tooling 路径 + HMR websocket（根路径的 101 升级），同一个脚本重跑：**75 → 8**。

> 埋雷时发现：只测 `text/javascript` 的话，把扩展名表改回旧版测试照样绿 ——
> 两条路径互相兜底，等于只验了一条。补了两条各自隔离的用例。

**② 用例已有接口场景时，点「编排为接口测试」会静默再建一条。**
前端 `LinkedApiScenarios` 认定"一个用例一条"（只显示步骤最多的那条），
后端却无条件新建。后果三层，全程无提示：

- 多出来的那条在用例页面上**看不见也删不掉**
- 却照样躺在分支的接口测试模块里，被批量执行捞走，稀释通过率
- 新的步骤更多时，**把原来那条已经跑通的顶掉**

而且**完全不看状态** —— 原场景是 published 还是 deprecated、用例的 api_status
是 debugging 还是 executable，一概照建。

修法：`on_existing` 三态。不传 + 已存在 → 拒绝（MCP 等非交互调用不该悄悄改数据）；
`append` 接到后面；`replace` **保留场景本身**（id/编号/报告关联都不动）只换步骤，
并把状态打回 draft。另外绑了用例时，AI 一次返回多个场景也**并进同一条** ——
这个洞在首次编排时就存在，只是运气好没撞上。

**③ 空目录 51/93。** 目录是建用例时按 module 顺带创建的，
`batch_hard_delete` / `empty_trash` 从不回收它。修法：删完把**因此变空的**目录一并收掉
（只收这次波及的，从没装过用例的不碰 —— 那可能是人先搭好的结构）；
另加「清理空目录」入口，只列名单、勾了才删、服务端再重判一次。

**列表按钮**逐个真点：AI 生成用例→跳转生成向导、从接口生成/AI 评审/导入/新建用例→各自弹窗、
导出→真下载 xlsx、就绪度筛选→在 105 条的分支上验，结果与库里 `ui_status` 计数对得上。
六个按钮全部有响应、无 5xx、无 JS 报错。

### 8.6 又一次假通过（这轮踩的）

`check("流量里没有前端源码模块", not any(...))` —— 选择器写的是 `.ant-table-tbody td`，
而「本次流量」是自绘 div，**一条都没命中**，`any([])` 恒为假，断言绿得理直气壮。

对策已写进纪律：**凡是遍历列表的断言，先加一条「真的读到了 N>0 行」**。

### 8.7 导入/导出的定位（四人评审后定稿，2026-08-11）

问题不是"导出不完整"，是**一个按钮同时想服务两个意图**：给人看 / 给机器用。
Excel 装得下什么决定了按钮做什么 —— 存储结构泄漏到了界面上。

**定死：**

| 意图 | 入口 | 形态 | 含什么 |
|---|---|---|---|
| 给人看（评审/交付/存档） | 导出清单 | Excel | 手动步骤。**并主动声明缺了什么** |
| 给机器用（逃生/存档） | 导出备份 | zip | 脚本正文 + MANIFEST + README |
| 团队内移植 | 从分支复制 | 平台内深拷贝 | 三件套一起走 |
| 批量改用例 | 导入 | Excel 回环 | **只增不删** |

**四条硬规则：**

1. **不往 Excel 里塞脚本和接口场景。** 接口场景是带状态传递的多步链，
   UI 脚本是代码，塞进单元格既看不懂也还原不了。
2. **缺什么必须说出来。** Excel 里加「说明」表 + 下载后 toast 报数
   （"6 条接口场景不在 Excel 里"）。沉默的缺失比报错更伤人。
3. **凭据一个字不出平台**，也不提供「包含凭据」这种选项。备份包跑不起来
   是**预期行为** —— 收到的人缺的是环境，不是资产。README 里写明。
4. **导入只增不删。** 第一版把全量同步改成"默认不勾的开关"被否掉了：
   一个勾选框能软删几百条用例，破坏性动作不该藏在便利入口里。
   要整体覆盖是另一件事（迁移），该独立入口 + 预览要删哪些 + 二次确认。

**顺带修掉的既有缺陷：** `/scripts/export` 把所有脚本扁平放在
`tests/{类型}/` 下，而 CC 回推的脚本几乎都叫 test_ui.py / test_api.py ——
**8 个脚本压出来只剩 2 个文件**。改成按用例编号分目录。
"平台没了资产还在"是这个功能唯一的价值，覆盖掉就等于没备份。

**待办（评审提出、本轮未做）：** 执行历史 / 报告 / 归因没有任何导出。
用例可以重写，执行历史重不出来 —— 它是唯一不可再生的资产。

### 8.8 第三次踩「源码文本断言」

这一轮埋雷抓到自己三处坏断言，全是同一个形状：

| 断言 | 被什么绕过 |
|---|---|
| `"project_scope or legacy_scope" not in src` | 注释里就有这句 |
| `'" → "' in export_src` | 我自己写的注释里有这个分隔符 |
| `"tests/{code}/" in src` | 兜底那行还有一处同样的字符串 |
| `"case.deleted_at" not in src` | 埋雷用 `c.deleted_at` 就绕过了 |

**纪律：断言行为，不断言源码文本。** 做不到就用 AST（如"函数体内任何对
`deleted_at` 的赋值"），别用子串。抽纯函数是为了能测行为 ——
`pick_scope` / `steps_to_text` / `backup_path` 都是为这个抽的。

## 9. CC 闭环体检（2026-08-11，真跑一遍整条链）

用 MCP 从零走一遍「①建用例+回推 → ②执行 → ③查报告 → ④分析」，抓到 4 个 bug，
**每一个都只有真跑才会暴露**，读代码看不出来。

### 9.1 提取路径不认 `$.` 前缀 —— 而且报错指错地方

`lum_sync_orchestrated_scenario` 的参数说明写的是 `variables_extract:{name:jsonpath}`。
外部 CC 照着写 `$.data.token` 完全合理 —— 而 `_extract_value` 是 JSONPath-lite，
只认 `data.token`。后果是**静默**取不到值：

1. 第 1 步断言过了（status 200），记成 pass
2. 第 2 步报「变量未解析：${TOKEN}」，提示指向"检查环境变量配置"
3. 根因在第 1 步，而错误在第 2 步 —— CC 会去查环境，查不出来

三处一起修：`_extract_value` 接受 `$.` 前缀（宽进）；提取失败在**当步**就判 fail
并列出响应实际有哪些顶层键；下游的「变量未解析」改成先让人往上看。

### 9.2 场景变量只在接口侧注册裸名，UI 侧没有

抽屉和工具说明都写「UI 和接口共用同一份」。接口侧注册 `SV_x` **和**裸名 `x`，
UI 侧只注 `SV_x`。CC 写 `os.getenv("PROJ_NAME")` 拿到空串，**不报错**，
表现成"填了个空项目名"。抽成 `add_bare_names()`，五条执行路径共用
（MCP UI 执行 / 页面运行验证 ×2 / 批量执行 / 计划执行 / 执行前预检）。

### 9.3 `lum_run_plan` 直接崩：`name 'flaky_service' is not defined`

`execution_service` 里这个 import 写在 `_will_run_automated` 函数内，
而 `start_execution` 也用它。**计划里只要有一条不是 executable 的用例**
就走到那个分支 → NameError 打死整个计划执行。提到模块级。
另写了一个 AST 扫描，全库 247 个文件确认同类问题只此一处。

### 9.4 计划会"假装要跑"

进回归的门槛是「该维度状态 = 可执行」，而这个状态**只有人能推**
（CC 不改状态是红线 3）。此前三步都在暗示"它会跑"：
`lum_create_plan` 说「1 条用例」、`lum_run_plan` 说「totalScenarios: 1」、
报告里一条 pending —— 实际一条都没跑。

改成两个工具都如实返回 `willRun` / `blockedCases` / `skippedAsManual`，
并说明卡在哪、该谁去做。判据与 `_will_run_automated` 共用同一套，
两边不一致等于换个地方说谎。

**这一条不是缺陷，是设计**：人确认才进回归。但工具得说出来。
体检里模拟人确认（走正式编辑接口改成 executable）之后，
`willRun: 1` → 计划真跑 → 报告 100%，链路是通的。

### 9.5 顺带发现、未修

`lum_create_case` 的自动拆步骤（`_split_coarse_steps`）会把
「填写名称，点击确定」拆成两步，**并给拆出来的新步骤填上
「操作完成，页面状态更新」** —— 这正是入库门禁 `_FUZZY_WORDS` 要拦的模糊词，
平台自己注进去的。拆步骤本身是对的，填充文案不对。

### 9.6 活体验证第二轮（2026-08-21）：外部 CC 照说明干活，平台每步都回「成功」

这一轮外部 CC 报回来的问题**全是同一类**：键名对不上就静默走另一条路，
入库那一刻不喊疼，执行时才炸，而错误指向的是**后果不是原因**。
挑出来的六条（都已修，回归在 `backend/tests/test_silent_key_mismatch.py`）：

**① 计划/回归/批量执行路径压根不做文案渲染。** `_run_new_style_script`
（`execution.py` 和 `adhoc_execution.py` 共用的那个）只烧了 `os.getenv` 默认值，
没调 `ui_text_render.render`。后果：同一份脚本 `lum_run_ui_script` 跑绿
（MCP 那条路渲染了），进计划直接 `status=error` / 0ms / 拒绝执行 ——
而报错叫人「占位里补上 `${键|中文原文}`」，脚本里写的本来就是那个。
`executor.py` 里那句「连'某条执行路径压根忘了渲染'也一起拦住」的注释预言中了：
拦住了，但话说错了。现在带 `|中文` 的残留占位会直说**是这条路漏了渲染**
（渲染过它一定会退回中文，不可能还留在正文里），并且四条路都渲染 ——
`test_silent_key_mismatch.py` 里有一条结构性断言钉住这件事。

**② `lum_upsert_scenario_variables` 收 `value` 当没看见。** 正确键名是
`value_template`，写成 `value` 时存进去是空串，而返回是「新增 1、更新 1」、
`errors: []`。六步接口链全挂在「变量未解析」上。现在：`value` 收成别名但**回显**
说改了什么；空值、不认识的 kind、拼错的字段一律报错不入库。
（`kind` 写错原来会静默变 `literal` —— 把 `random` 拼成 `rand` 的人以为存的是
「每次换新的」，拿到的是「整段固定」。）

**③ `lum_get_api_test` → `lum_sync_orchestrated_scenario` 不能读改写。**
读回来是驼峰（`variablesExtract` / `groupName` / `waitMs`…），写回只认下划线。
改一个 URL 再存回去，**所有提取被静默丢掉**，然后报「存在悬空变量引用」。
现在两边互认，并回 `keysAliasedFromCamel` / `keysIgnored` 说清做了什么手脚。
只读名单（`lastStatusCode` 这些）跟 `api_tests` 的输出对齐，有测试钉住漂移 ——
漏一个就会冒出假警报，真丢东西时反被噪声盖住。

**④ 反问 facts 里的「UI 脚本」恒为 false。** `reflect.build(case, {...}, neighbors)`
第四个参数（脚本）调用方从来没传。这四问值钱就值钱在"事实是平台数的、不是模型猜的"，
掺一条假的等于砸自己招牌。现在查库传进去。

**⑤ `lum_proxy_capture` 跑起来了但一条没抓到时没有任何提示。**
「把浏览器代理指过去」这句只在 `running: false` 那个分支里 —— 最常见的情况
（代理开着、浏览器没走它）反而没有。另外没有过滤：前端跑 Vite 时
实测 156 条里只有 9 条是 `/api/`，`limit=50` 全被 `.jsx?t=` 热更新占满。
现在加了 `url_contains` / `method`（在**全量**记录上筛再取 limit），
过滤后 0 条会列出实际抓到的目标，截断会明说砍了几条。

**⑥ `lum_run_plan` 说「拿 reportId 调 `lum_get_report_summary`」，那个工具要 `plan_id`。**
照提示做一定报参数错，而错误指向调用方。现在两个报告工具 `plan_id` / `report_id`
给一个就行（只有 reportId 时自己反查计划）。

顺带修的三处非本类问题：往已有一级模块加用例会被告知「这是新建的一级模块」
（而同一句里的「现有模块」列表含它自己）；`pw_conftest._do_login` 用 `page.url`
判「已登录」跟 SPA 路由守卫赛跑，输了就跳过登录、十几步后报 `element_not_found`、
失败截图是登录页（改成看「页面上还有没有密码框」，它跟渲染同步）；
被 AI 打回的用例在详情页点「保存」必 400「拒绝必须填写理由」——
详情页保存会把当前状态原样回传，而「AI 打回 → 人去改 → 保存」是这条链最常走的一步
（改成只在**真的把状态改成打回的那一次**要理由）。

**「UI 脚本里的 projectId 该放哪层」这一问，规范原来答不上来。** 变量分层写着
「多条用例只读引用的底座 → 项目级共享资源，跑前平台探一次并注入 `${资源名}`」，
但那句只对**接口场景**成立 —— UI 脚本这边只注环境变量 + 场景变量。
于是能跑的写法要么是 `kind=literal` + 真实 UUID（规范明令禁止），
要么自己在脚本里按名字反查一遍（可行，但规范里没写）。现在三条 UI 执行路径都注，
写 `os.getenv("SV_<键>")` 即可，**只在脚本真的引用了才去探**
（探测要打被测环境，不引用的脚本不该白付这个开销），
回出来的 `resourcesInjected` 列出这次真注了哪几个键。

审核那两条（批量弹窗没有进度、「先跑一遍再审」多数情况不会真跑、覆盖缺口没合并成）
见 [review-spec.md §13](review-spec.md)。

## 10. 铺开体检（2026-08-11，四个维度、复杂场景）

第一轮体检只走了一条 happy path。这轮按维度铺开，又抓到 6 个。

### 10.1 维度 A：失败现象分类（15 条，用真实错误原文）

七种现象各覆盖 + 历史上两次方向相反的误判 + 边界。**抓到一个**：

**5xx 的时间窗锚错了地方。** 窗口是 `max(抓包时间) - 5s`，锚在"最后一条抓包"上。
真实坑：页面早就静默了（最后一条抓包 t=3s），定位器又干等 10 秒才超时（失败在 t=20s）——
t=1s 那个无关 5xx 还在窗内，于是把"选择器过期"判成"系统挂了"。
改成锚在**失败时刻**（`record_run` 记账时就是失败时刻），拿不到才退回旧口径。

### 10.2 维度 B：复杂接口链（数组下标 / 非 2xx 当预期 / 造完清理）

`$.data[0].id`、`data[0].name` 都取得到；失败步骤之后**清理步骤照样执行**（对的，
不然造的数据永远留着）。**抓到两个**：

- **合成 UUID 被误判成写死资源 id。** 负向测试要一个肯定不存在的 id
  （全 0 / 全 f），门禁按"literal + UUID"报警。对正当写法报警，等于逼人改掉
  负向用例、或者学会忽略告警 —— 后者更糟，真的反模式也一起被忽略了。
- **Lumiere 自己少一条路由。** `/api/projects/{id}` 有 PUT 和 DELETE，
  唯独没有 GET → 返回 **405**。写接口测试的人会理所当然假设它存在（我第一次就撞上），
  而 405 比 404 更难懂。服务层 `get_project` 一直都有，缺的只是路由这一层。

### 10.3 维度 C：混合计划 —— 最大的一个洞

**MCP 回推的接口场景根本进不了计划回归。** 回归执行器只认 `scripts` 表的 api 脚本，
而 `lum_sync_orchestrated_scenario` 写的是 `api_test_scenarios`。
实测：全平台 **8 条有接口场景的用例，0 条有 api 脚本** —— CC 这条链的接口产物
一条都进不了回归，只能 `lum_run_api_test` 即席跑，不进通过率。

连带三个：
1. 建计划说「1 条会跑」、跑计划说「0 条会跑」—— 两个工具当场自相矛盾，
   因为判据各写了一套。改成 MCP 直接复用执行器的 `_has_new_style_script`。
2. 接口场景的 id 被当成 `scripts.id` 塞进 `script_runs.script_id`（外键）→
   执行成功了却在**记账**阶段撞外键，整次计划被打死。
3. 轨迹里印的是 `${BASE_URL}` 模板不是实际 URL。

修完：接口场景进得了计划、报告 100%、`script_runs` 里 `regression` 一条、
轨迹是真实地址。

**顺带**：执行崩溃会把计划永远卡在 `executing`，之后再也触发不了
（`start_execution` 要求状态在 draft/completed/paused）。本轮靠手工复位绕过，
**未修** —— 需要一个超时/异常兜底把状态放回去。

> **2026-08-21 复核：已修**，在 `app/services/stuck_recovery.py`。三条出口：
> 执行函数抛异常/超时走 `release_execution`，正常返回后 `ensure_finalized` 再兜一道
> （"报告出来了、计划还在 executing"就一定是漏了），另有 `start_watchdog`
> 在 `main.py` 启动时挂上、定期 `sweep_orphaned`。
> **判据不是"停在 executing 多久"** —— `reopen_plan` / `resume_plan` 也会把状态
> 置成 executing 且不跑任何后台任务，按时长扫会把它们误杀。

### 10.4 维度 D：flaky + 归因确认闭环 —— 这两段是好的

连跑 5 次让结果翻转：平台识别出 2 次翻转、`is_flaky` 保持 false、
`quarantined_until` 为空（**没擅自隔离**，符合"检测到不稳定 ≠ 隔离"的设计）、
3 次失败的时间戳不同但归一化后 `distinctErrors: 1`。

归因确认：CC 提交 → 进待确认队列且明确"不改任何状态" → 人在平台上
**必须选原因 + 写理由**才能确认（"确认是唯一算数的结论，不是走形式"）→
`confirmed_cause` 落库。红线守住了。

证据校验器还拦了我一次：我写的 request 证据是聚合描述（"total=1、只有 2xx"），
它要求指向具体请求。拦得对 —— 这正是"读着顺但对不上证据"。

### 10.5 我这轮的老毛病

`确 认` / `取 消` 的空格坑，**一轮里栽了四次**。已在走查脚本里统一成
"先去空格再比、点击用宽松正则"，不再逐处补。

## 11. 「接口测试」模块下线（2026-08-15）

左侧菜单的**接口测试**（`/projects/:id/api-test`）整个下掉了。它的本职是「给一个/少数
接口定义，AI 造一组正向/参数/边界/安全场景」，产物不绑用例（`source_api_ids`，
无 `source_case_id`）。

这是红线 1 在**接口维度**上的同一个动作：平台侧生成能力下线，生成归 CC，
平台做呈现和回推通道。

### 11.1 判死刑的不是使用率，是那条 NOT NULL

`scenario_variables.case_id` 是 **NOT NULL** —— 场景变量只能挂在用例上；
`api_test_runner.py` 里也只有 `if scenario.source_case_id:` 才去解析。
**所以不绑用例的场景在设计上就拿不到场景变量**，凭据只能靠环境变量兜。

实跑本模块的本职产物 `AT-0013 获取项目列表-正向测试`（published，3 步）：

| 环境 | 结果 |
|---|---|
| `api-test-local` | 3 步全挂：连接失败（该环境 `BASE_URL=localhost:8000`，错端口） |
| `测试平台self` | 3 步全挂：`变量未解析 ${ADMIN_USER}、${ADMIN_PASS}` |

AI 造的是 `${ADMIN_USER}/${ADMIN_PASS}`，各环境里实际叫 `ADMIN_USERNAME/ADMIN_PASSWORD`，
唯一对得上的那个环境又指着错端口 —— **两头都不通，而且不是配错，是结构性的**。

对照组：绑用例的编排链同一套引擎跑过 124/125 步。**引擎没病，病的是「无用例」这条路。**

### 11.2 库里的实情（下线时实查）

全库 55 条场景：

| 类别 | 条数 | 步数 | 跑过的步数 |
|---|---|---|---|
| `mcp` + 绑用例（真正在用的） | 7 | 124 | **124（99%）** |
| `ai` + 无用例（**本模块本职产物**） | 40 | 161 | **29（18%）** |
| `mcp` + 无用例（孤儿，用例删后残留） | 7 | 98 | 66 |
| `manual` + 绑用例 | 1 | 0 | 0 |

那 40 条的成分：30 条是 07-07/07-09 对 testBench 自己接口的 dogfood，**同一批建了两遍、
一字未改**、全停 draft；10 条是 `probe-*` 探针垃圾。**全部在 dogfood 项目**——
真正在做事的「网关管理系统」项目里本职产物 **0 条**，而页面默认档位是「单接口」，
所以人打开这个模块看到的全是那 7 条孤儿。

**通过率污染是实测到的，不是担心**：模块里点一次「运行」就落一条
`report_type='api_test'` 正式报告。库里 85 条这种报告的条目分布——
绑用例 12 条（通过率 66.7%）、**无用例 73 条（通过率 47.9%）**：
86% 的条目来自没有用例的场景，把整体从 66.7% 拖到 55%。

### 11.3 删了什么，留了什么

**留**（用例侧在用，一行没动）：`api_test_scenarios`/`api_test_steps` 两张表、
`api_test_runner.py` 执行引擎、list/get/create/update/steps CRUD、`/run`、`/generate`、
`api_test_folders`、计划执行、报告、分支复制、`lum_sync_orchestrated_scenario`。

**删**：
- 前端 `pages/api-test/` 七个文件 2085 行 + 菜单项 + 路由 + i18n
  （`RunResultPanel.jsx` **先挪到** `components/` —— 用例详情页 import 着它）
- 后端专属端点：`/stats/quality`（全仓零消费方，纯死代码）、`PUT /batch`、
  文件夹增删改 ×4、`/copy`、`/new-version`、`/split`、`/ai-optimize` + apply、
  `/run-step/{step_id}`；列表的 `kind` 参数（它存在的唯一理由就是分这两类）
- `services/ai/api_test_optimizer.py`
- MCP `lum_generate_api_test`；`apidoc` 档位收敛回「维护接口库」
  （原名「只有接口文档，连不上系统」，配的就是这个工具）
- `api-test-optimize` 能力标 `deprecated`；**`api-test-generate` 保持在线** ——
  用例详情「探索测试流量 → 编排为接口测试」走的是同一个 `/generate`

### 11.4 同批做掉的：让「无主场景」从此不可能出现

下线只是关窗口。**关了窗口，那 47 条无主场景反而更隐蔽** —— 页面上看不见了，
却仍会被执行捞取、仍会落进 `api_test` 报告。所以同一批把根挖了（迁移 `zz9orph1`）：

1. **清存量 47 条 / 259 步**（30 条 dogfood 重复件 + 10 条 probe 垃圾 + 7 条孤儿），
   连带回收 **10 个因此变空的目录**（只收这次波及的，从没装过场景的不碰 ——
   纪律和用例目录那边一致，见 §8.5）。清之前整表导出留档。
2. **外键 `SET NULL` → `CASCADE`**。这才是孤儿工厂：删一条用例，它的场景不会消失，
   只是把 `source_case_id` 置空、降级成无主。`case_service` 里补过一句 `sa_delete`，
   但那只堵住一条删除路径。
3. **`source_case_id` 收敛成 `NOT NULL`**。这两个改动**必须一起做**：
   只加 NOT NULL 不改 SET NULL，删用例会直接撞非空约束报错。

连带改的调用方（不改就会从"约定"变成"运行时崩"）：
- `lum_sync_orchestrated_scenario` 的 `source_case_id` 从「强烈建议」变**必填**，
  入口挡一道并说清为什么，别让 CC 撞一个看不懂的 `IntegrityError`
- 同一函数里「取不到用例就回退 `AT-#### max+1`」那条兜底**删掉** ——
  它会在用例 id 不存在时照建，然后撞外键。现在直接报「用例不存在」
- `POST /api-tests` 的 `sourceCaseId` 声明成必填（422 而不是 500）
- 模型 `ApiTestScenario.source_case_id` 同步改成非空 + CASCADE，
  否则 SQLAlchemy 以为可空、插进去才炸

**实测挡住了**（不是靠自觉）：HTTP 不带 `sourceCaseId` → 422 带字段名；
直接往库里 INSERT → `violates not-null constraint`；
造一条临时用例带场景、删用例 → 场景跟着没、全库无主 0 条（事务已回滚）。

**仍留着的**：历史 `api_test` 报告里那 73 条无主场景的执行记录**没删**。
那些运行确实发生过，删掉是毁审计痕迹；而"未来还会被捞进来"这件事，
已经被上面三条堵死了。

### 11.5 为什么不拆表

评审时提过「顺手把两类拆成两张表」，**否决**。一条接口场景就是一条接口场景，
执行语义、步骤结构、断言模型、报告口径完全一样，区别只在"谁生的"——
这正是单表 + 归属外键该干的事。1146 行引擎两边共用就是这个设计的回报；
拆表要付两遍引擎、两遍报告聚合、两遍分支复制。

正解是反过来：**把 `source_case_id` 收敛成 NOT NULL，让"两类"这件事本身消失。**

### 11.6 二次清扫：把「留着以防万一」的也清了（同日）

第一轮下线之后我留了几样东西，理由是"以防万一"。逐个查实际消费方，
发现它们本身就是模块残骸 —— **一个消费方都没有**：

| 清掉的 | 为什么它是死的 |
|---|---|
| `DELETE /{scenario_id}` | 用例侧只删步骤不删场景；删用例已由外键 CASCADE 带走 |
| `PUT /{scenario_id}` + `VALID_STATUS_TRANSITIONS` | 草稿/已发布/已废弃那个下拉是模块页的控件，用例侧从不改场景本体 |
| `lum_list_api_tests` 的 `standalone` 分组 | NOT NULL 之后恒为空。留一个永远空的分组只会让人以为"另一类还在" |
| `source_api_ids` 列 | 唯一写入方是生成服务的 `api_ids`，而它只有模块的生成弹窗会传 → 落库恒 None |
| `edited_after_generate` 列 | 唯一读者是 `/stats/quality`，那个端点已随模块删掉 → 只写不读 |
| `pre_steps` 列 | **执行器从头到尾不读它**。配了不生效，比没有更糟 |
| `api-test-optimize` 能力档位 | optimizer 服务已删，没有任何 `resolve_ai_config` 传这个 key |
| 无主场景的历史报告 | 88 条 `api_test` 报告里 73 条整条无主，指向的用例和场景都已不存在 |

**同源问题一并修**（不是清扫捡到的，是清扫时才看清的）：

- `/generate` 和 `POST /api-tests` 的 **`caseId` 从可选变必填**。可选是为了服务模块
  那个入口；留着的话不传就一路走到插库才撞非空约束，报出来是 500 + IntegrityError。
- 这两条路**不再发 `AT-####` 编号**，改用用例编号 —— 和 CC 回推那条路一致。
  原来发 AT-#### 的后果很具体：用例详情看到 `AT-` 开头会打「未绑定用例」的橙色提示，
  于是从「编排为接口测试」按钮建出来的场景，明明绑着用例却被自己标成孤儿。

**保留没删的，各有真读者**（别下次又当成残骸）：
`folder_id`（多场景执行时给报告命名）、`env_variables`（执行器合并变量的第一优先级）、
`status`/`source`（列表回显）、`PUT /{scenario_id}/steps/reorder`（见下）。

### 11.7 清扫时撞见的两个既有 bug（已修）

都在「用例详情 → 接口测试」页签的**保存链**上：`ApiStepList`（编辑器）→
`apiStepAdapter.nodeToStepPatch`（转字段）→ `CaseDetail.saveNodes`（落库）。
共同的根因是**保存时只逐个 PUT 内容，不告诉后端两件事：顺序、这是不是新的一条**。

**① 拖拽排序不落库。** patch 里没有 `sortOrder`，`UpdateStepRequest` 也不收，
新建步骤一律 `max(sort_order)+1` 落末尾 —— 拖完保存、刷新回原样。

这不是显示问题：执行器 `order_by(sort_order)`，而接口链天生依赖顺序（第 1 步登录取
token，后面才有 `${token}`；清理步骤得在最后）。顺序错了的表现是后面一片
**「变量未解析」假红**，而报错指的是变量，人会去查变量定义 —— **指错方向**。

修法：`saveNodes` 边写边记最终顺序（新建的 id 从 POST 响应接住），最后调一次现成的
`PUT /{scenario_id}/steps/reorder`。**这个端点当初差点被当死路由删掉** ——
它确实没有调用方，但它不是死的，是没接上的线；删了等于把修复路径一起铲掉。

**② 复制步骤会把原件覆盖掉。** `copy` 是 `JSON.parse(JSON.stringify(step))`，
**连原件的 id 一起复制走**；而 `saveNodes` 靠 `n.id 有没有值` 判断新建还是更新，
于是副本走 PUT 打在原件身上。结果不是多一条，是**原来那条被改名成「xxx (副本)」**，
全程无提示。修法：`delete clone.id`，顺带 `delete clone.lastStatus`（副本一次没跑过，
挂着原件的绿勾是假的）。

**两条都是下线之前就有的**，但这次下线**放大了第一条**：被删的模块页里有一处
`api.put(.../steps/reorder)`，那边的排序是正确落库的。也就是说以前还有一个能正确
排序的入口，现在用例侧这条成了唯一入口。

### 11.8 这一轮的自测（脚本在 `backend/scripts/selftest/`）

删横切的东西，只验改动点不算数。两个脚本，都断言到内容不看状态码：

- `selftest_api_scenario.sh` —— 接口场景整模块 14 项：读（列表/详情/按用例过滤）、
  写的两道闸（不带 caseId → 422、用例不存在 → 404）、已删端点确实不可用、
  步骤增改删**并读回来确认真落库**、§11.7 那两个 bug 的回归（排序真落库 / 复制不覆盖原件）、
  整链执行出报告
- `selftest_neighbors.py` —— 共用层四个出口 14 项：用例详情的接口维度状态、
  MCP 的 owes 判定、报告列表/详情/下钻/看板、分支复制的字段

**自测抓到的两个真问题**（都是这次改动引入的，已修）：

1. **分支复制被改崩了**：`sc.source_api_ids` 属性已不存在（AttributeError），
   且新建场景没带 `source_case_id`（撞非空约束）。修法是让 `_copy_cases` 回一份
   旧→新用例 id 映射，场景据此改绑到目标分支自己的用例上；映射里找不到宿主的跳过并
   `skippedNoCase` 计数 + 打 warning（静默少复制几条比报错更难查）。
   真跑验证：复制出的场景绑的是**新分支的** TC-XMGL-00001，5 步齐全。
2. **一刀切多了**：删 `PUT/DELETE 场景` 时把中间的 `POST ""`（用例侧「新建场景」按钮
   在用）一起带走了。是核对"剩余路由 vs 前端调用点"时发现的 —— **只看语法通过、
   只跑测试都发现不了**，那条路径没有测试覆盖。

自测脚本自己也错过两次，一并记着：断言 `endswith("/cases")` 在重定向丢了项目前缀时恒绿；
断言 HTTP 用例列表带 `owes`（那是 MCP 才有的字段）。**断言写错的表现和功能坏了一模一样，
但方向相反 —— 一个假绿一个假红，都得回去看清楚才能下结论。**

## 附：AI 评审为什么能替掉人工「待审」（2026-08-19）

人工待审这道闸原本要人干三件事：看这条场景合不合理、看验证点到不到位、看有没有漏。
其中**只有第三件真的需要人**（他知道业务上还有什么没测），前两件是有判据的活。

所以评审拆成两段（实现见 `app/services/review/`）：

| 谁判 | 判什么 | 为什么 |
|---|---|---|
| **平台代码** | 恒真断言、not_exists 缺基准、写完没读回、只打控制面、对照组塞一条、只断状态码、UI 脚本硬伤、按承诺还欠哪几维 | 这些都能证明。判据前几轮已经从真实事故里长出来了，各自有测试封样 |
| **模型** | 场景合不合理、这一条自己的承诺验全了没有、预期是不是照实现抄的、UI 脚本验的是不是该验的 | 需要判断力，但**不需要业务背景**——判据都在用例自身里 |
| **人** | 模块级还缺什么场景 | 只有他知道业务上还有什么没测。所以模块缺口走 `coverageGaps`（情报），**不参与这一条过不过** |

判定规则写在 `score_and_verdict()` 里，不在 prompt 里：
```
有 blocker         → rejected（哪怕体检分 95）
major >= 2 处      → rejected
其余               → approved（分数只做排序和体检，不参与判定）
```
**分数不当闸门**：每一维的分是模型给的，同一条用例两次评审拿 86 和 78 是常事
（评测实测：一条写得规范的 UI 用例被 78 分打回过一次）。拿抖动的数当闸门有两个坏处：
①结论不稳定，人就不信了；②"78 分低于 80 分线"没法照着改，而"这两条必须改"可以。
`blocker` = 放进回归就是**假绿**或根本跑不了。让模型自己下 approved/rejected，
一句"整体不错"就能把 blocker 盖过去——分数可以商量，闸门不行。

**已知的边界**（评测台 `scratchpad/eval_review.py` 跑出来的）：
- 平台判出来的那几类缺陷（恒真断言、只打控制面、写完没读回、只断状态码、对照组塞一条）
  命中稳定，因为它们根本不依赖模型。
- 「模糊预期」「预期照抄实现」靠模型判，会有波动。
- **模块级遗漏当时判不了**，所以那一栏留给人看。
  → 2026-08-21 改了口径：给它加上**页面探测出的实际可操作项**做对账之后，
  「模块体检」可以出覆盖缺口了，但定位仍是**情报、不是闸门**，不参与任何一条用例过不过。
  见 [review-spec.md §8](review-spec.md)。

> 这一节只讲判据。**审核怎么发起、怎么排队、结果看哪里**在
> [review-spec.md](review-spec.md)——那份还包含三个已经撤销的设计（模块放行 /
> 批量默认静态 / 脏数据账本），改这块之前先读，别照着旧行为实现。

## 13. 全自动一轮：把人从「按按钮」里拿掉（2026-08-24）

> 起因：用户问「这条链现在是 CC 和平台来回交互串起来的，能不能全部让 CC 串完」。
> 先分清两种解读 —— 答案相反，这一节只做第一种。

### 13.0 两种「全自动」，只做一种

| | 做不做 | 判据 |
|---|---|---|
| **(a) 编排全自动**：人不再在中间按按钮，平台仍是执行器 + 事实库 | **做** | 已经走了八成，缺的就是下面四处 |
| (b) 平台退化成存储，CC 自己跑回归、自己写状态 | **不做** | 红线 2（CC 本机跑通不算数：本机有 dev server、残留数据、cookie）、§2.4（运动员兼裁判，偏差确定存在且方向可预测）、§2.5（给它"让测试变绿"的目标它一定做得到，而**这个失败不以报错出现，以「一切正常」出现**）。另加一条最实在的：`duty.py` 自己的注释就写着「清单必须落平台 —— CC 一关会话上下文就没了，续不上」 |

**一句话**：把人从**按按钮**里拿掉，只留在**做判断**上。

### 13.1 现状：七个非人不可的点位

| # | 触发在哪 | 人做什么 | 不做会怎样 | 有判断成分吗 |
|---|---|---|---|---|
| 1 | Claude Code 里 | 说一句话起活 | **CC 永远不动** —— 没有调度 | **没有** |
| 2 | CC 的对话里 | 确认要建的用例清单 | CC 停着等 | 有（但被滥用了，见变化 3） |
| 3 | 用例管理页「AI 审核」 | 点按钮发起批量审核 | CC 只能一条条自审，**绕过队列** | **没有** |
| 4 | 计划页 | 建计划、点执行 | 无 —— CC 已有 `lum_create_plan` / `lum_run_plan` | 没有 |
| 5 | 报告页失败那行 | 选原因 + 写理由 | 那条停在待确认，CC 不能往下走 | 有 |
| 6 | 用例列表/详情 | 废弃审批：确认或驳回 | 挂在「待废审」，不进也不出 | 有 |
| 7 | P0 用例 | 只看「预期结果」一列并确认 | 平台硬拦，P0 不许一次性直出三件套 | 有 |

**点位 1 和 3 是纯按按钮。** 这两个才是「人被卡在流程里」的真正原因 —— 其余五个都要人真做判断，去掉就出事。

### 13.2 四处改动

#### 变化 1 · 起活不再需要人每次说话（点位 1）

现状：人每轮说一句话 → CC 干一轮 → 停住 → 等人下次再说。

改成：人第一次说 `/loop /lum-round <模块>`，之后 CC 自己按间隔醒，每次醒来先调
`lum_next_duty`；七个队列都空就说「这一轮干净」接着睡；有事才叫人。

**新增 `/lum-round` skill**，把一轮的顺序固化（现在靠 CC 每次自己记，忘一步链就断）：
`lum_next_duty` → 按它给的「建议顺序」逐队列处置 → 每条完事 `lum_check_deliverable`
→ 一轮末 `lum_check_branch` 收口。

⚠ **走 `lum_push_skill` 存 DB，不放 `app/skills/preset/`**（CLAUDE.md 明令 —— 那个目录只放
平台侧当 prompt 执行的 `lum-*`，混进去会让「AI 能力→模型」页冒出绑不上模型的空档位）。

触发仍然靠 CC 自己的循环能力。**平台不建调度**，理由见 §2.11：会引入一个需要长驻、
需要监控、会静默死掉的组件。

#### 变化 2 · 批量审核 CC 自己能发起（点位 3）★ 最要紧

**这是现在就在发生的问题，不是将来的隐患。**

`lum_review_case` 直接调 `reviewer.review_case`，**完全不经过 `review/queue.py`**。于是
CC 自己推进一批时只能逐条送审，而 review-spec §5 建那条队列要防的两件事一件都吃不到：

- **同环境串行**：两条脚本共用租户/账号，A 跑到一半 B 把 A 要用的数据删了 → A 莫名报错
  → 审核判 A「脚本有问题」。**这是假打回**，出几次这套审核就没人信了。
- **熔断**：环境一挂，连续 3 条环境类失败本该暂停整个队列；逐条调的话 20 条会一条接一条
  全标「无法审核」，看起来像用例集体坏了。

改法：新增 `lum_review_batch(branch_id, case_ids|module, env_id, run_first)`，
**复用现成的 `queue.enqueue`**，只做入队并回 `batchId`；配 `lum_review_batch_status(batch_id)`
读进度（复用 `queue.queue_view`）。**不新写任何调度逻辑。**

一个细节要照顾到（review-spec §5）：**人工发起的插到 CC 自审前面** —— 人在等结果，CC 不在等。
所以 CC 入队时优先级排在人后面。

#### 变化 3 · 报清单收窄（点位 2）

现状自相矛盾：instructions ⑦ 要求**任何写库工具**调用前都先报清单等确认，而
`lum_update_case` 的描述写着「**你写错了自己改，别喊人**」。两处打架，CC 照哪条都不对。

判据改成**按动作的可逆性分**，不按"是不是写库"分：

| 动作 | 要不要报清单 |
|---|---|
| 新增用例、删用例、改动别人的用例 | **要** —— 这几样回滚代价高 |
| 补一个还欠着的维度、改自己写错的字、改和实测不符的步骤 | **不要**，直接做，做完在回复里说一句 |

#### 变化 4 · 抽检（点位 5）—— 这是新问题，不是补功能

**自动化本身会把观测手段一起吃掉。** 这一条值得单独记，因为它不是"少做了个功能"。

§2.4 上线的反向指标 `CC归因 vs 人确认` 一致率（`agreement_stats`），是平台**唯一**能量出
"CC 有没有系统性把测试缺陷说成产品缺陷"的东西。而它的数据来源是**人确认**：
`confirmed_cause` 有值才进分母。

现在归因走 `route()` 分流，五类 + 自证齐全的产品缺陷都是 `self_serve` —— **压根不经过人**。
于是：**人工确认越少，这个指标越测不出来。** 把人从确认里拿掉，等于把体温计一起收走。

改法：`self_serve` 命中时，**按 `case_id` 取哈希抽十分之一**同时进待确认队列
（不阻塞 CC 继续改，只是让人偶尔复核一次），标 `route="self_serve_sampled"`。

- **用哈希不用随机**：同一条用例反复提交，抽中结果必须可复现 —— 随机的话
  一会儿抽中一会儿不抽，CC 会以为是平台行为不稳定。
- `agreement_stats` 里**抽检样本和人主动确认的分开算**：后者有选择偏差
  （人主动去看的往往是它已经觉得可疑的那些），混在一起算出来的一致率偏低，
  会误报"CC 在甩锅"。

### 13.3 优化后剩五个人工点位

| 保留 | 触发在哪 | 为什么不能去 |
|---|---|---|
| P0 预期确认 | 用例列表，只看一列 | 一屏二三十条五分钟过完，买回的是「三份产物同源、一起错」这个盲区（§2.2） |
| 需求没写清 / 拿不准 | 报告页失败行 | 定义上就是人的活 |
| 产品缺陷证据不齐 | 报告页失败行 | 齐了自动放行，不齐才落人 |
| 废弃审批 | 用例列表/详情 | 误废一条，那块功能再没人测且**永远不报错** —— 比假绿更毒 |
| **抽检复核** | 报告页失败行 | 新增，为了保住上面那个指标 |

**从 7 减到 5，去掉的正好是那两个纯按按钮的。**

### 13.4 明确不做（补充 §2.11）

| 不做 | 理由 |
|---|---|
| 平台侧定时调度（cron / celery / APScheduler） | 同 §2.11。触发用 CC 的 `/loop` |

### 14.6 差点把那 5 条数据删掉：模型没人 import 了

`Document` 模型原本是靠 `api/documents.py` 那条 import 链进 `Base.metadata` 的。
路由文件一删，**模型还在，但没有任何地方 import 它** —— metadata 里就没有这张表了。
后果不是"少个功能"，是三件事：

1. **`alembic revision --autogenerate` 会提议 `op.drop_table('documents')`**。
   模型里没有、库里有 → autogenerate 认为这张表该删。合进去就是把那 5 条数据删掉，
   而 diff 上只有一行。`alembic/env.py` 里那句
   「**不 import 的话 autogenerate 会提议 DROP 掉它们**」写的就是这个坑，
   只是这次是从相反方向踩进去的：不是忘了加 import，是删掉了唯一那条 import。
2. `Base.metadata.create_all` 建的测试库里不再有这张表。
3. `tests/unit/core/test_schema_invariants.py` 的 CASCADE 封样直接红
   （`表名对不上，模型改过？缺：['documents']`）—— **是它先把这件事喊出来的**，
   不然这个洞会一直躺到某次 autogenerate。

修法：`app/models/__init__.py` 里显式 import 一次（那个文件此前是空的），
并在 docstring 里写明它只放"没有别的地方会 import 它"的模型。
放这儿而不是 `env.py`，是因为 `env.py` 和 `app.main` 两条路都会经过 `app.models`
包的 `__init__` —— 一处补上，autogenerate 和运行时都盖到。

**这条留给下一次下线用**：删一个模块的路由文件时，先问一句
「这个模块的模型还有别人 import 吗」。表留着 ≠ 数据安全。

后端单测 **1413 条全过**；根目录那套（打真接口）**498 条全过**
（`DATABASE_URL` 用的独占库 `lumiere_test_doctakedown`）。

## 15. 「探索测试」下线（2026-08-27）

用户的原话是「**具体还要看这个功能做的怎么样，如果不太好直接下掉，
如果还可以就抽出来一个 mcp**」。查完是前者，理由不是"没人用"（那是结果不是原因），
是**它的输出跟被测系统没有关系**。

### 15.1 它实际产出什么

链路是四步：建会话 →「AI 生成章程」→ 人逐项勾检查点 → 生成总结报告。
`POST /sessions/{id}/generate-charter` 喂给模型的上下文只有两样：

```python
api_tree = await api_endpoints.list_api_tree(session, str(project_id))
endpoints = [n for n in api_tree if n.get("type") == "endpoint"]
api_text = "\n".join(f"- {ep['method']} {ep['url']} ({ep['name']})" for ep in endpoints[:20])
# → f"目标模块: {target_module}\n时间限制: {n}分钟\n\n项目API接口:\n{api_text or '（无录入）'}"
```

**而接口库全库 7 个 `endpoint` 的 `url` 一个都没填**（见 §14.1 的更正表）。
有探索会话的那个项目里两个接口，拼出来的原文逐字是：

```
- GET  (新建接口)
- GET  (新建接口)
```

也就是说模型真正拿到的上下文**就是模块名那几个字**。出来的东西自然长这样
（库里那条真章程的原文，不是编的）：

| 检查点 | |
|---|---|
| 1 用户创建功能 | 必填字段验证、重复用户检测、特殊字符处理 |
| 2 用户信息查询 | 列表展示、搜索过滤、分页功能、权限隔离 |
| 6 边界值与异常处理 | 空值、超长输入、SQL注入、XSS攻击、并发操作 |

**换任何一个系统的"用户管理"模块，这份章程逐字都成立。** 它不是探索的结果，
是"用户管理该测什么"的通用清单 —— 那种清单模型不看系统也写得出来，
所以它没有把任何信息从被测系统里搬出来。

### 15.2 章程之后没有执行

章程只是文字。勾检查点（`complete-checkpoint`）、写发现（`findings`）
全是人手填的表单，平台不驱动浏览器、不发请求、不截图。
`ExploratoryFinding.screenshot_url` 有这个字段，唯一那条发现里是空的。

留下的痕迹：**3 个会话、0 个检查点被勾过、1 条发现**，
全在 2026-06-26 一天里（自测），之后两个月没人碰。
`0/8`、`0/10` 这两个数说的就是「章程生成完，人没有接着往下走」。

### 15.3 那"抽成 MCP"呢 —— 已经有了，而且是活的

探索这件事的价值在**真去点一遍**，不在"列一份该测什么"。
外部 Claude Code 本来就能点（Playwright / `lum_proxy_capture` 看页面真发了什么），
而对账那半边平台早就有了：

```
lum_module_checkup(branch_id, module, observed_actions=[...])
```

`observed_actions` 就是「你在页面上探到的可操作项」，
返回的 `coverageGaps` 是拿它跟现有用例对账出来的 ——
**「页面上有这个操作、用例里一条都没覆盖」是最硬的缺口**，
而这正是探索测试想要的产物。区别在于：

| | 探索测试（下线的） | `lum_module_checkup` |
|---|---|---|
| 输入 | 模块名（接口库是空的） | 真在页面上探到的可操作项 |
| 产出 | 通用检查清单 | 跟现有用例求差集的缺口 |
| 谁去点 | 人，手填表单 | CC 自己点 |
| 落到哪 | `exploratory_findings`（1 条） | 直接变成待补用例 |

所以**不新写 MCP 工具** —— 再抽一个只会跟 `lum_module_checkup` 抢同一件事，

## 16. 「接口库还在被谁写」——把它变成可查的（2026-08-27）

### 16.1 事故本身：我断言错了，而且当时**没人能证伪**

用户问「API 接口这块 MCP 在用吗」，我答了"在用"。用户一句
「**mcp 用的不是场景的嘛**」把它顶了回来 —— 对的，MCP 写的是
`api_test_scenarios`（绑用例的编排链），不是 `api_nodes`（接口库）。

问题不在我记错，在**那句话当时无法被查证**：

| 想查的 | 当时能查到的 |
|---|---|
| 接口库最近谁写过？ | 无。`api_collection_service` 的 6 个写函数**一行日志都不记** |
| 是页面点的还是 MCP 写的？ | 无 |

只能靠间接推断：库里 12 个节点全叫「新建接口」「新建文件夹」——
那是页面新建的默认名，而 `lum_create_api_node` 的 `name` 是必填参数，
不可能产出这种名字；7 个 endpoint 的 `url` 一个都没填；最后一次写入停在 2026-07-10。
推断碰巧对了，**但那是运气**。

> **一个查不出来的事实，等于一个可以随便断言的事实 —— 谁写在注释里就算谁的。**

所以这次的修法不是"把注释改对"（下一个人照样只能猜），是让这个问题
**从此有地方查**。

### 16.2 四层，缺一层这事就会再发生一次

| 层 | 做了什么 | 挡住的是哪种复发 |
|---|---|---|
| **能查** | `api_collection_service.py` 六个写路径全部 `_audit_node(...)` 记账 | 「问了也查不到」 |
| **能筛** | 操作日志页 `TARGET_TYPES` 加 `api_node`，中文名「接口库」 | 记了但页面上筛不出来 = 等于没记 |
| **能看见** | 接口库页顶常驻 `<Alert>`：这是文档、**不产生可执行测试**，可执行的在用例详情里 | 下一个人**根本不会想到要去查** |
| **防漂移** | 静态封样 4 条 + 真跑集成 3 条 | 以后新加写函数又忘了记账 |

### 16.3 记账的四个取舍（都不是"顺手记一下"）

- **`write_audit_log` 而不是 `@audit_log` 装饰器** —— 这几个服务函数返回 `dict`，
  装饰器要从返回值上 `getattr(result, "id")`，拿到的是 `None`：
  记出来一行没有对象、没有项目的空日志，**比不记更坏**（它看起来像记了）。
- **删除要记在删之前** —— `delete + flush` 之后 ORM 对象属性过期，
  那时候再读 `node.name` 只剩一条查不出对象名的空行。
- **改动只记字段名，不记新旧值** —— `body`/`headers` 动辄几十 KB，塞进 `changes`
  会把审计表撑爆；而「谁改了它」这个问题只需要字段名。
- **导入/拖排序整批记一条** —— 一个 Postman collection 上百个接口，
  逐条记会把操作日志冲成一片，反而看不出"谁导入过什么"。

来源那一列不用额外做：`app/mcp/middleware.py` 的 `on_call_tool` 对**所有** `lum_*`
统一注入 `actor_type="mcp"` + `actor_label=<Key 名>`，
所以只要服务层记了账，MCP 写的和页面点的自动分得开。

**从此这个问题的答案是**：操作日志 → 对象类型选「接口库」→ 看「操作人」列的来源标签。

### 16.4 封样守的是"行为"，不是函数名

```python
if "flush" not in called:      # 读函数（list_tree/get_node）不 flush，自动跳过
    continue
if "_audit_node" not in called:
    missing.append(fn.name)
```

判据用**「这个函数会不会 flush」**而不是函数名前缀：以后加 `rename_node`、
`move_node`、`archive_node`，名字再怎么起都照样落在这条规则里。
守卫**咬过一次**才留下的 —— 把 `create_node` 里的记账删掉，确认它真的红了，再还原。

静态守卫看不出的那半边交给 `tests/integration/services/test_api_collection_audit.py`
真跑：它断到库里那一行的 `project_id` / `target_name` / `actor_type` 上 ——
**记了账但筛不出来，跟没记一样**。其中 `test_来源分得出是MCP还是页面`
就是 16.1 那个问题的答案该从哪儿来。

> 踩过的坑：第一版按 `created_at` 排序断言 `["create","update","delete"]`，红成
> `['create','delete','update']`。不是产品 bug —— Postgres 的 `now()` 是
> **事务开始时间**，同一个事务里写的几行时间戳一模一样，排出来是随机的。
> 线上每个 HTTP 请求各自一个事务不会撞，测试里三个动作在一个事务内会撞。

### 16.5 顺带：措辞「API 接口」→「接口库」

`menu.apis` 的**文案**改了（key 和路由没动；菜单项本身 §14 已经下掉，
这一页现在只从老书签/直链进）。原来那个名字跟「接口场景 / 接口测试」
只差一个字，真有人（包括我）把它当成可执行的接口测试。
MCP 那边的分区描述早就叫「**接口库·只记怎么调**」，这边跟上 ——
别再让同一个东西有两个名字。恢复入口的时候文案已经是对的了。

同一批还改了新建分支弹窗的「复制模块」——那三个勾选框里，
「API 接口（接口树）」和「接口测试（文件夹+场景+步骤）」**是并排放的**，
这就是这场误会的缩影。改成：

```
接口库（接口文档树·不可执行）      ← api_nodes
接口场景（绑用例的编排链·可执行）  ← api_test_scenarios，source_case_id NOT NULL
```

括号里那半句是刻意加的：光换名字，两个名字还是只差一个字。

页面上那条 `<Alert>` **故意不做"读过就不再显示"**：
存 localStorage 关掉的话谁都只看得见一次，而会踩这个坑的**恰恰是第一次打开这页的人**。
占 40px，不值得为它省。
