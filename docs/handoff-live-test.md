# 活体验收：CC ↔ 平台整条链（给接手活体测试的人）

> 这份文档给**第一次接触这套东西的人**看。照着往下走就行，不需要先读代码。
> 目标不是"点一遍看看有没有报错"，而是**验证每一步的交接有没有真的发生**。
>
> 一句话背景：用例和脚本由外部 Claude Code（下面简称 CC）写，平台负责执行、记账、审核、
> 跟进。**平台不会主动通知任何人**——人靠打开页面看，CC 靠每轮主动问。这是设计，不是缺陷。

## 1. CC 回推一条用例（验"规范生不生效"）

让 CC 做一件小事，比如「验证用例导航里新建模块后列表能筛到它」。要求它**先读规范**
（`tb_get_sync_spec`），然后按规范回推。

**该看到什么**：
| 看点 | 期望 |
|---|---|
| 标题 | 两段式，`对象+动作-预期`，短横不留空格，前段 20 字内 |
| 每个步骤名 | 带前缀：`前置:` / `操作:` / `验证:` / `清理:` |
| 回推返回 | 提示分三档：`blockers`(没入库) / `mustLook`(能证明的问题) / `fyi`(参考) |
| 回推返回 | 有 `reflect` 四问，每问带平台数出来的事实（几步、几条断言、邻居有哪些） |
| 交付门禁 | 四问没答之前，`tb_check_deliverable` 里有一条"还没答反问" |

**算失败**：标题一整句没断开、步骤名没前缀、四问没出现、或者四问是空泛的问句（没有事实）。

## 2. AI 审核（先静态，再执行式）—— **重点段**

### 2.1 静态审核
用例详情页 → 「审核」tab → 「AI 审核这一条」。

**该看到什么**：六个维度分、findings 每条指到具体步骤/断言/脚本行、结论是"通过/打回"。
判定规则是**有致命就打回、两处重要也打回**，分数只是体检分——所以会出现"80 分打回"或
"70 分通过"，那不是 bug。

### 2.2 执行式审核（这块最需要人验）
点「先跑一遍再审」。它会**真的跑一遍**，然后拿这次页面真实发的请求跟接口场景对账。

**故意制造一个错来验它**（这是这一段的核心）：
1. 找一条有 UI 脚本的用例
2. 把它接口场景里某一步的 URL 改错一点点——比如 `/api/projects` 改成 `/api/project`
   （要改成**一个真实存在、也能返回 200 的端点**，才能验出真本事；改成不存在的太容易了）
3. 点「先跑一遍再审」

**该看到**：一条**致命**级 finding，`endpoint_not_used_by_page`，大意是
"接口场景里这些端点，这次页面执行一次都没发过；真实流量里出现的是 …"。

**为什么非要验这个**：外部 CC 真出过这个错——页面调 `/subscriptions/provider-unified`，
它 22 条接口场景全用 `/subscriptions/provider`。后者存在、返回 200，**用例一直是绿的**，
但页面根本不用它。静态审核永远看不出来。

**算失败**：改错了端点却没报，或者没改也报（误报）。

## 3. 建计划 → 执行 → 报告 → 失败跟进（验"红了之后有没有人跟"）

1. 让 CC 建一个计划（挑测试平台里几条接口用例）并执行，或页面上「测试计划」建
2. 打开报告详情

**该看到什么**：
| 看点 | 期望 |
|---|---|
| 报告里有失败 | 页面上出现「失败跟进」区块，每条一张单子，状态是「待归因」 |
| 让 CC 归因 | 脚本问题/环境/数据 → 单子直接变「处置中」，**不用等人** |
| 让 CC 报产品缺陷 | 三样证据齐全（活体怎么复现、代码依据、单号）才放行变「已知问题」；缺一样自动落回「等你确认」并告诉它缺哪个 |
| 你点确认 | 报告页那条失败展开 → 确认面板 → 单子往前走 |
| 改完复跑 | 跑绿 → 单子**自动关闭**，并记着"凭哪一次跑绿关的" |
| 人工关闭 | 「人工关闭」按钮 → **原因必填**（留空点不动） |

**复发要专门验一次**（这是最容易做错的地方）：
单子关掉之后，**再造一次同样的失败**（比如把脚本改回错的）。
**该看到**：**新开一张单**，上面标「第 1 次复发」——而不是把老单子的次数 +1。
理由：修好过又坏了是回归，并进老账里"中间绿过"这段会被埋掉。

## 4. CC 每轮的入口（验"交接靠不靠状态"）

让 CC 调 `tb_next_duty`。

**该看到**：四个队列 + 每条的"下一步该调哪个工具"：
```
待归因（红了还没分析，带现象/红了几次/第几次复发）
待复跑（已确认修好、或关联 bug 标了 fixed）
待补场景（审核时被反复提到的模块级缺口）
待自证（回推四问没答的）
```
**算失败**：明明有红的失败却不出现在「待归因」；或者已经确认过的还停在「待归因」。

## 5. 模块审核报告（验"欠账攒不攒得起来"）

左侧「执行与产出 → 审核报告」。

**该看到**：按模块列出 通过/打回/待复审/未审、均分、和**覆盖缺口去重合并**
（"越权 3×"这种，鼠标悬浮能看到是哪几条用例提的）。这一页存在的理由就是最后那一列——
每条用例审核时提的模块级缺口，散着没人看，合并了才是补测清单。

## 6. UI 脚本用接口造数（验多角色）

让 CC 写一条 UI 脚本，要求：**前置数据和清理走接口，页面上只做被测那一个动作**。

沙箱里有个 `api` fixture：
```python
def test_xxx(logged_in_page, api):
    svc = api.json("POST", "/api/v1/services", json={"name": n})["data"]
    api.role("tenant").json("POST", "/api/v1/subscriptions", json={...})   # 换角色造
    ...页面上点那一下，验页面看得见的结果...
    api.delete(f"/api/v1/services/{svc['id']}")
```
角色来自环境变量：成对的 `<X>_USERNAME`/`<X>_PASSWORD` 自动成为一个角色。

**该看到**：脚本步数明显变少（一个 20 步的脚本里往往 15 步是造数）；
角色名写错时报错会直接列出这个环境有哪些角色。

## 已知的边界（别把这些当 bug 报）

1. **平台不主动通知**。人靠打开页面看，CC 靠每轮问 `tb_next_duty`。没有值守。
2. **AI 相关功能依赖网关**。网关限流时会降级到本机 claude CLI，一次审核可能要 1~3 分钟。
3. **审核分数会波动**（同一条用例两次可能 86 / 78），但**判定只看 findings**，不看分数。
4. **审核列只显示状态**（通过/打回/待审），不区分是 AI 审的还是人审的——谁审的、审了几轮
   在详情页「审核」tab 里。
5. **回推时四问不拦入库**：不答也能入库，代价是交付门禁不放行、审核扣分。
6. **产品缺陷挂了单号之后回归会跳过它**（不再刷红），但交付门禁照旧算"卡在产品缺陷"——
   不是通过。

## 这三块我已经活体验过一遍（你重点复核，不是从零试）

1. **执行式审核**（§2.2）：端点正确时零误报（8 条真实流量）；把一步换成"存在、返回 200、
   但页面不调"的端点后，立刻报致命 `endpoint_not_used_by_page` 并列出两边端点。
2. **失败跟进闭环**（§3）：红→开单→归因（脚本类自证进「处置中」/ 产品缺陷缺证据落回「等你确认」
   并列出缺哪几样）→改对复跑绿→**自动关单**（记「复跑跑绿 / platform」）→
   再制造同样失败→**新开一张、标复发、挂着上一张**。
3. **多角色 `api` fixture**（§6）：真跑通一条"接口造数 → 页面验证 → 接口清理"的 UI 脚本，12 步全绿。

验的过程里修掉 9 个真 bug（都带了测试），其中值得你知道的三个：
- `tb_run_ui_script` 不回 `runId`，而归因要它 —— 归因链第一步就断了
- `evidence` 有两套不兼容形状（老校验要数组、自证要对象），导致"自己处置不用等人"压根走不通
- 审核在没给环境时会瞎跑（BASE_URL 空、脚本导航到 `/login` 直接挂），
  然后把这个假失败报成"这条用例跑挂了"

## 怎么把问题报回来

每条按这个格式，缺哪一样都会让定位变成猜：
```
在哪一段：§2.2 执行式审核
我做了什么：把 TC-PTZS-00004 接口场景第 3 步 URL 改成 /api/project，点「先跑一遍再审」
期望：出现致命 finding endpoint_not_used_by_page
实际：只给了 3 条 minor，没提端点的事
证据：用例编号 / 报告 id / 截图 / 后端日志里那一段
```
