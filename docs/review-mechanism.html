testBench · 用例审核 / 模块审核

用例审核这道闸，怎么才能让人一直信它

这套机制要替掉的是人工「待审」那道闸。核心不是「让 AI 打个分」——恰恰相反： 模型只出意见，判定权全部收在代码里； 没在真环境上跑成功的结论，一律不算通过。

下面是这套东西的全部判据、流程、以及每一条判据「什么时候会冤枉人」。 反例和出口写得比规则本身还长，是故意的——一条没有出口的硬规则， 会让人在第三次被冤枉之后整体不看这个结论，那时候闸门就等于不存在了。

判定：代码 · 意见：模型 · 情报：给人
实现：backend/app/services/review/ · 流程：docs/review-spec.md

分工

人工待审要干三件事，只有一件真的需要人

看场景合不合理、看验证点到不到位、看漏了什么——前两件是有判据的活，第三件才需要业务背景。

平台代码 · 判事实

恒真断言、写完没读回、只打控制面、只断状态码、UI 脚本硬伤、步骤↔脚本缺口、真实流量对不上、跑完留残留、按承诺还欠哪几维。

这些都能证明，所以它们是「事实」——模型不许推翻，只能引用和归类。

模型 · 判判断题

场景本身合不合理、这一条自己的承诺验全了没有、预期是不是照着实现抄的、UI 脚本验的是不是该验的东西。

需要判断力，但不需要业务背景——判据都在用例自身里。

人 · 收情报

模块级还缺哪些场景。只有他知道业务上还有什么没测。

所以模块缺口走 coverageGaps，是情报，不是闸门，不参与任何一条用例过不过。

模型能标 blocker，但必须点名是哪一类

不设这道闸的话，「能更强」的意见迟早也会被标成致命——而闸门一旦变成「什么都打回」， 人就开始整体无视它。说了等于没说，和上一版评审输出「缺少安全测试场景」是同一种失效。

所以模型标 blocker 必须同时给 kind，且只能从这四类里选，点不出类别的最重只能标 major：

kind含义
expectation_copied_from_impl预期照着实现抄——把 bug 固化成「预期」
assertion_cannot_fail这条断言无论系统怎么坏都不会红
no_real_verification通篇没有验证该功能的动作，只走了一遍流程
script_cannot_run脚本必挂：语法错、API 用错、依赖不存在的东西

另外三条给模型的硬性约束，每条都是被真实失效逼出来的：

① 不许输出任何统计数字。平台会算，模型会数错——上一版评审说「50 条没有预期结果」，库里真实是 5 条。

② 每条意见必须指到具体位置（步骤名、断言、脚本里的那一行）。指不到位置的意见对每条用例都成立，等于没说。

③ 别把「还没做」当质量问题。按 target_level 还欠哪几维是进度，不是质量；只有「承诺要做却没做」才提。

判定

判定写在代码里，不写在 prompt 里

让模型自己下 approved／rejected，一句「整体不错」就能把 blocker 盖过去。分数可以商量，闸门不行。

# app/services/review/reviewer.py :: score_and_verdict()
有 blocker                  → rejected   哪怕体检分 95
major ≥ 2 处                → rejected   一处不打回，两处叠加就该打回
没真跑成功（三种情形）      → inconclusive 既不算通过也不算打回
其余                        → approved

# 分数（六维加权）只做排序和体检，不参与判定。

为什么分数不当闸门

每一维的分是模型给的，同一条用例两次评审拿 86 和 78 是常事——评测里实测过， 一条写得很规范的 UI 用例被 78 分打回过一次。拿抖动的数当闸门有两个坏处：

  • 结论不稳定，人就不信它了；
  • 「78 分低于 80 分线」这句话没法照着改，而「这两条必须改」可以。

但分数也不能白给：模型没给某个适用维度的分时，按该维度上最重的 finding 兜一个 （blocker 40 / major 65 / minor 85 / 无 80），而不是当满分——缺分数默认满分等于漏评就白送。 另外每一维按最重的 finding 压顶（blocker 封顶 45、major 封顶 70）： 不压的话会出现「平台明明判出一条 major，模型却给这一维 85 分，加权照样过线」——机器事实等于白判。

approved通过

没有致命问题。最多允许一处「还能更强」的 major 列在报告里。

rejected打回

放进回归就是假绿或者根本跑不了。附 mustFix 清单，能照着改。

inconclusive无法审核

没环境 / 既没 UI 脚本也没接口场景 / 环境本身挂了。既不算通过也不算打回。

第三种结论是这套设计里最容易被省掉、也最不能省的一个

早期「没跑成功」只是一条 minor finding，不阻断结论。于是「全批 16 条通过」里混着 4 条根本没跑过的， 而报告上它们和真跑过的长得一模一样。

为什么也不能判成 rejected

用例可能完全没问题，是环境没配或者挂了。打回它等于让人去改一条没毛病的用例，改完还是跑不了。

含金量看不出来的通过，比不审更坏——它发了一张假凭据。

判据规范

什么样的判据配得上硬拦

起因是一条真规则写坏了：no_readback 原来照「有没有 GET 回读」判， 而「发布服务 → 打一下服务，通了」是比回读更强的验证。那条规则在逼人写冗余接口。

①

硬拦只给「必然出错」

放进去 100% 会挂，或 100% 是假绿，且不存在任何合法写法能长成这样。 写得出「合法写法」这三个字的，就不配硬拦。

②

判据要对着「想防的后果」，不是对着「我讨厌的写法」

想防「写完没验效果」，判据就该是「有没有任何一步验了效果」——而不是「有没有 GET」。 前者换个更强的验法照样过，后者逼人加冗余请求。

③

「通常不对但存在合法写法」的，只能是警告，而且必须给忽略出口

提示里要写清「如果 X，忽略这条」。没有出口的提示等于逼人照做， 而人照做完发现更糟，下次就整体不看提示了。

④

严重度由后果定，不由把握度定

判据靠猜意图（自然语言、命名习惯）的，最重只能到 minor—— 它的错误率不来自「这件事严不严重」，而来自「我可能理解错了」。

附则：能证明的才硬拦。同一条判据，有证据时可以硬拦，没证据时只能警告。

例：「断言期望值写成字符串 "true"」——如果历史执行记录里那个字段确实是布尔， 那是必然假红，可以硬拦；没跑过的时候平台并不知道那个接口返回的是不是字符串 （有些老接口真的返回 "enabled": "true"），这时只能提醒。

工程纪律：每条规则的注释里必须写出反例——什么情况下它会冤枉人。 写不出反例的规则不许上线。对应地，判据的反例测试里 每条判据都有一条「应该沉默」的用例，那些比「应该报」的更重要。

判据清单

平台代码判出来的事实

这些检查器都是从真实事故里长出来的，各自有测试封样。模型看到它们时被告知「一律为真」， 任务是归类和说清后果，不是复核对不对。

kind判什么严重度反例 / 出口
tautology_assertion断言恒真：系统怎么坏它都不会红 blocker恒真的定义就是假绿本身，不存在合法写法
vague_expectation预期写着「功能正常 / 无报错 / 显示正常」 blocker这类词跑起来永远是绿的
ui_script_hard_errorUI 脚本必挂：sync_playwright、写死地址、清 storage 换角色 blocker确定信号，不需要理解业务
step_action_not_in_script「操作:」步骤在脚本里找不到对应动作 blocker脚本里一个中文字符都没有时整条判据不生效（纯 i18n key 写法）
expectation_not_asserted「验证:」步骤在脚本里找不到对应断言 blocker预期里没有引号锚点也没有数字时不参与判定（隐式验证）
endpoint_not_used_by_page接口场景验的端点，页面执行一次都没发过 blocker整条 URL 全是变量、归一后对不上任何真实流量的，跳过不比
no_readback写完没读回来确认真改了 major判的是「有没有任何一步验了效果」，不是「有没有 GET」
control_plane_only只断控制面状态就当生效了 major纯控制面系统没有数据面可打；触发靠步骤名里的「生效」，是在猜意图
residue_not_cleaned造了数据、一次删都没试过 major这条用例就是在验「建完要能留下」；清理走后台 API；共享夹具
i18n_key_not_in_dict文案占位符的键在项目词典里查不到 major只在项目真有多语种词条时才报，只测中文的项目报了纯属噪音
status_only_assertion读操作只断了状态码，没断响应内容 minor验的就是「能不能调通」（放行、可达、健康检查）时 200 就是结论；断错误码不算弱
control_group_in_one对照组塞在同一条用例里 minor权限矩阵类用例「两种角色各看到应有范围」是正常写法
cleanup_failed删了但没删掉（DELETE 非 2xx） minor删不掉是被测系统的 bug，不打回用例，开单

严重度是会往下调的。control_plane_only 从 blocker 降成 major， 理由就是元规则 ①④：反例是纯控制面系统（这个测试平台自己就是——「建用例 → 列表能查到」， 那个「生效」本来就发生在同一个域里）。

也会往上调：tautology_assertion 从 major 升成 blocker， 因为「恒真」的定义就是假绿本身，标成 major 意味着要凑够两处才打回。

去重要三道判据，缺一个都会漏

机器判出来一批、模型用自己的话又说了一遍同一处，报告上就会把一处问题写成两处， verdictReason 还会写「有 2 处重要问题」——直接影响判定。

  • 同维度 + 两边声明的步骤号撞上（stepRef，最准的一道，双方都填结构化字段）；
  • 措辞前缀重合——模型抄机器原话时命中；
  • 同维度 + 散文里提到同一个位置数字——模型换了说法但带着步骤号时命中。
新判据够不着的地方

接口侧那批机器判据（tautology_assertion、no_readback…）是按步骤名定位的， 压根没拿到序号，填不出 stepRef。所以旧的两道一条都没删—— 拿一个模型可能不写的字段去换掉两道已经在跑的判据，是净亏。

执行式审核

没真跑过的结论不算通过

原本打算「批量默认静态审核」，作废了。静态查得出一批问题，查不出的恰好是最贵的那一类。

只有真跑才查得出静态会怎么误判
接口场景验的端点，页面根本不调「写得挺完整」，照样给 80 多分通过
步骤里写的动作，脚本里压根没做靠读文本比对，模型会被脚本里相近的代码骗过去
选择器早就失效、脚本跑不起来从没跑过的脚本，静态看不出它跑不跑得动
跑完留了一堆垃圾数据完全看不见

实测的量级差：同一条用例，静态审 84 分通过， 真跑审 56 分打回。

页面打开时调的是 /api/v1/subscriptions/provider-unified， 而那 22 条接口场景全用 /api/v1/subscriptions/provider。 后者确实存在、返回 200，所以用例一直是绿的； 但 provider-unified 坏掉、少给字段、跨租户条目漏掉，那批用例一条都不会红。

这种错静态审核永远看不出来——两个 URL 都合法、都能通。判据是 URL 集合比对，不问模型。

四方对账：步骤 ↔ 脚本 ↔ 真实流量 ↔ 接口场景

锚点比对，不是数数。原来那条是数数（手工 N 步、脚本 M 个动作，M < N/2 就报）， 两头都犯错：一步「进入详情页并展开更多下拉」在脚本里是两个动作（少报）， 两步「点确认」「点提交」可能被一句链式调用覆盖（误报）。

改成对锚点：中文用例的步骤里几乎必然带引号标签——点击「弃用服务」、 状态徽标变为「已弃用」。这些标签在脚本里要么以文本选择器出现， 要么以断言期望值出现。一个都找不到 = 这一步脚本里没有，这是确定判断，不需要理解业务。

跑挂了 ≠ 用例不合格

被测系统真有 bug 时脚本必然跑红。直接打回用例的后果是 用例被判死刑、bug 没人管，而且被测系统一出问题整批全红。所以先归因，三分：

归因怎么认结论后续
脚本 / 断言写错SyntaxError、NameError、选择器语法错 打回用例整改后再审
被测系统 bug断言没过、接口返业务错误码 用例照样可以通过开失败单 + 挂 bug_refs，永不清除
环境 / 数据问题ECONNREFUSED、502/503/504、DNS、证书 无法审核环境就绪后重审
归因用后果分档，不用把握度分档

环境类和脚本类都只认确定信号；剩下的（断言没过、返业务错误码）一律不算脚本的错—— 把「没判出来」默认成「用例的错」，正好制造那个最坏后果。真正写错的断言由别的判据 （恒真、只断状态码、写完没读回）去抓，那些不需要真跑就成立，不会因为归因保守而漏掉。

已知会冤枉人的情况：被测系统返回 500 且恰好是脚本传了非法参数导致的， 会被归成 system_bug——代价是多开一张单，不是错误打回。可以接受。

流程

发起、排队、结果看哪里

入口即类型：不额外问「你这次要审模块还是审单条」

你的动作平台理解成类型
点中某模块，一条都没勾，点「AI 审核」审这个模块模块全量 / 模块增量
列表里勾了 N 条只审这 N 条抽审
进用例详情点「AI 审核」只审这一条单条
报告页选「只做体检」不跑用例，只看模块覆盖体检

类型必须进报告。一眼看不出是审了整个模块还是抽了三条， 这份报告过两周就没人信。只有「模块全量」能代表这个模块的情况—— 否则挑三条好的一审，就能宣布模块没问题。抽审的报告顶上明写「不能代表整个模块」。

确认框：能选的只有三样

范围（全部 / 只审没审过的和被打回的 / 只做体检）、环境、要不要顺带体检。 九项检查故意不做成可勾选——能勾就能放水：今天嫌某项烦关掉， 以后这批「通过」就没法解释含金量。检查项只展示，不给开关。

一个环境一条队列，串行

并行换来的不是快，是假打回。两条踩过的：

  • 两条脚本用同一个租户、同一个账号，A 跑到一半 B 把数据删了 → A 莫名报错 → 审核判 A「脚本有问题」，其实是被踩的。
  • 被测系统那边「关闭本租户审批开关」是个全局开关，一条脚本把它关了，另一条正好在测开关开着的行为——两边结果都不可信。

假打回出过几次，这套审核就没人信了。所以同环境串行，不同环境可以同时跑。

01

发起 · 没配环境的项目直接拦下

弹窗说「先去项目设置加一个」，而不是跑起来然后 16 条全标「无法审核」。 环境要记进报告——「在哪套环境上审过」是结论的一部分，测试环境过了不等于预发也过。

02

排队 · 人工发起的插到自动自审前面

人在等结果，自动化不在等。同一条用例被重复发起 → 合并，不跑两遍。 体检不占队列（它只读用例库，不碰被测系统）。

03

熔断 · 连续 3 条环境类失败就暂停整个队列

环境一挂，队列会一条接一条全失败，16 条全标「无法审核」，看起来像用例集体坏了。 页面上说「环境好像挂了，剩下 13 条先停着」，等人确认后继续。

熔断状态是 paused 不是 failed——判成失败，那些用例会被当成「审过了没过」。 阈值 3 不是拍的：1 会被单条用例的偶发网络抖动误触发，5 的话 16 条里已经白跑三分之一。

04

取证 · 事实先出，模型后判

步骤原文 + 接口场景每步的 URL/断言 + UI 脚本正文 + 最近几次执行记录 + 真实流量 + 同模块邻居标题。

喂给模型的证据可以截断，代码判据一律用全文。混用过一次，代价见「踩过的坑 ②」。

05

判定 · 合并事实与意见，代码下结论

机器那份原样进结果（模型可能漏掉它，也可能把 blocker 说成 minor）； 模型复述的那条被去重丢掉，保留机器那条——它的严重度才是权威。

06

落库 · 一次审核一行，进度不丢

批次实体记类型/范围/环境/发起人/状态/进度，刷新、关页面、重启都不丢。 进程被 kill 时有收尾逻辑，否则正在跑的那批永远停在 running，页面上转到天荒地老。

报告页：一行一次审核，默认只看「我」发起的

自动化每次回推都会自审，一天几十条，全混在一起就找不到自己点的那次了。 行上的动作是「看报告」，不是「再审一次」——审核在用例管理页发起，这页只看结果。

结论会过期，列表上要看得见

用例的场景步骤和 UI 脚本版本摊平成一个签名存进审核轮次。内容改了签名就变， 列表和详情带一个只读派生字段 reviewStale，在原标签旁叠一个 ⚠。

两个刻意的取舍

没有新增状态枚举值。过期的用例仍然是 approved，按 approved 照样筛得到—— 它说的是「这个结论可能对不上现在的内容」，不是「这条没通过」。动那个字段会牵连门禁、筛选、批量操作一大片。

存量轮次没有签名的不给这个字段，而不是给 false——判不出来就不猜。 给 false 等于断言「没过期」。

签名只摊场景的定义（url/method/断言/body）和脚本版本号，不摊执行结果。 否则每次重跑都会把上一轮的 approved 标成「过期」，而内容其实一个字都没改。 而且单条和批量必须走同一段哈希——两处各写一遍，任何一处漂移都会让整库的 approved 全被标成过期， 一个假警报比不报警更贵。

模块审核

逐条只知道「这条不行」，看模块才知道「这一整片都犯同一个错」

模块体检一两分钟，不占队列、不用环境。三块输出，来源完全不同——这是它最值得抄的地方。

共性问题

把逐条 findings 按 kind 归类。纯汇总，不问模型——它就是个 group by。

塞模型调用既慢又不稳，而「同一份报告两次打开长得不一样」比不聚合更糟。

覆盖缺口

额外一次模型调用。「这个模块没测到什么」只有读过全部标题才答得上，代码判不了。

最多 8 条，按「不补会漏掉真 bug」排序。

覆盖分布

纯代码数个数：P0 占比、六类操作各几条、缺哪一类。

模型读 60 条标题时不会去算比例，而比例恰恰是最刺眼的信号。

覆盖缺口是情报，不是闸门——不参与任何一条用例过不过。

早期的结论是「模块级遗漏判不了，该由人看」。现在敢让它出缺口， 是因为多了在页面上探测到的实际可操作项做对账，不再是纯凭用例标题猜。 但定位没变：它只负责告诉你「还该补什么」。

缺口按话题归并，不按字面

原来的去重键是「去掉前缀后的头 12 个字」，而模型每轮措辞都不一样—— 实测某模块 8 条缺口全是 1×，其中三条讲的是同一件事（越权）。 这一页存在的理由就是那个 count 列，1× 一片等于这页没有信息。

改成关键词 → 话题标签（权限与越权 / 并发与竞态 / 幂等 / 边界 / 分页 / 清理残留 / 多语言 / 性能…）， 命中不了的退回实词签名。判据在代码里不问模型：这页每次打开都要算。 每桶保留各条原话——合并了得能核对是不是一件事。

模块审核的另一半：命名与归位

「模块」这个容器本身也要被审。事故现场：顶层有「本租户订阅(0)」「跨租户订阅(1)」， 同时「订阅管理」下面又有「本租户订阅(8)」「跨租户订阅(7)」—— 同一个东西摆在两处，用例被劈成两半，顶层那两个还是空的。

根因不在规则，在给的信息

建模块时平台只告诉调用方「现在有哪些一级模块」，没给完整模块树。 它看不见「订阅管理」下已经有这个子模块，就在顶层又建了一个。 原来那句「一级模块按功能域分」只是警告，被无视了—— 而无视一条无害的警告是完全理性的行为。

#规则处置
1建之前先全项目搜这个名字，不分层级判据的前提，不给全树后面三条都判不出来
2同一位置已有同名硬拒，让它用现成的
3不同父模块下的同名子模块允许，但平台回一句「注意：X 下也有同名的」
4一个在顶层、一个要挂到模块下硬拒——这就是事故现场那种，必须先合并
5范围词 / 自指词：平台自身、系统、通用、其他、公共…硬拒，可枚举、判断确定、无合法反例

三个连带的实现细节，缺一条这五条闸就白装：

① 闸要装在两侧。规则原来只挂在程序化回推口，页面上的「+ 新建模块」压根不过闸—— 而事故现场那两个空模块就是人在页面上建的。

② 规则 4 只拦得住「再建一个」，拦不住已经裂了的那两处。 得补一个「挪位置 / 合并」动作：目标已有同名时先回一句「会搬 N 条，确认？」，点第二次才真搬。 踩过的真错：第一版合并把父模块传成了同名那个模块自己的 id， 于是挪出「订阅管理/跨租户订阅/跨租户订阅」——套了一层空壳，比裂着更难懂。

③ 合并之后不能被回推复活。调用方手上还是老模块名，没有回落规则它下次又在顶层建一个， 合并等于白做。

为什么命名值这么多力气

用例编号前缀由模块名生成，而且改名刻意不变（历史名单就是为这个做的）。 所以一个建错的模块名会一直挂在那批用例上，洗不掉。

活体验证

跑起来才暴露的六个真问题

全部判据实现完、单测全绿之后，在真环境上跑一轮链路（建模块 → 审核真跑 → 组计划执行 → 归因待办）查出来的。 六条里有一条是「这套审核里最值钱的判据，此前从来没生效过」。

① 流量对账空转，而空转和「端点都对」在报告上长得一模一样 ★

现象：真跑模式、脚本 55 步全执行，trafficSeen 却恒为 0。

根因：多角色脚本必须自己开浏览器 context，而参数里带着同一个 record_har_path—— 每个 context 关闭时把 HAR 整份重写，后关的直接覆盖先关的。 实测：测试内打印 28MB，进程退出后只剩 324 字节、0 条记录。

修法是给每个 context 分独立 HAR、读取时合并。修完同一条用例 trafficSeen 0 → 51，当场抓出一条真的端点不符。

这条的普遍教训

一个「什么都没查到」的判据，和一个「查过了都没问题」的判据，在报告上必须长得不一样。 否则它空转多久都没人知道。

② 脚本截断制造假 blocker，而且专挑写得用心的打

评审证据只喂脚本前 6000 字，而 UI 脚本开头是大段 docstring——某条用例的 def test_ 在第 10361 字符、第一个 expect() 在第 6534 字符， 全在截断点之后。于是判出「没有测试函数」「一个断言都没有」两个假 blocker （实际各有 1 个和 11 个）。

错的方向是固定的：注释写得越足越容易被打回。 修法是代码侧判据一律用全文，喂模型的截断改成头 + 尾。修完那条用例 46 → 68 分，两个假 blocker 消失。

③ 幽灵端点误报

接口场景里整条 URL 全是变量的步骤，归一后是 /api/{id}{id}，跟任何真实流量都对不上， 每次都被报成「页面一次都没发过的端点」。这条判据一旦开始喊狼来了，真的那条也没人信了——所以跳过不比。

④ 模块体检把父模块算成 0 条

16 条用例全在子模块下，直属是 0 条。体检、批量范围、确认框条数三处都只查了直属—— 体检报告一片空白，看起来像「这个模块很干净」，实际一条都没看。改成连子树一起。

⑤ 裂口提示变噪音

命名裂口检查原来无条件追加，于是每建一条用例都收到同样两句提示—— 跟「我现在要往另一个模块加一条」毫无关系。每次都出现的提示等于没有提示。 改成只提跟本次模块相关的那一处。

⑥ 共性问题最大的一桶写着「other」

模型产出的 finding 只有维度没有 kind，全落进兜底桶。这一块存在的理由是 「改一处能修一片」，而「5× other」说不清是哪一处。改成没 kind 就按维度分桶，并给每个 kind 配人话标签。

还没在活体里跑到的，也照实记着： 熔断（环境一直是好的，没造出连挂三条的现场，判据有单测但没在真环境触发过）； 被测系统 bug 开单那条路（那轮执行 3 条全绿，没有失败可归因）。

拿走用

不依赖这个平台的十条

如果你要给自己的用例库做一道 AI 审核闸，这十条是从上面所有踩坑里剩下的通则。

  1. 判定权收在代码里，模型只出意见。让模型自己下结论，一句「整体不错」就能把致命问题盖过去。
  2. 分数不当闸门。模型给的分会抖，抖的数当闸门有两个坏处：结论不稳定、没法照着改。「这两条必须改」可以照着改。
  3. 写得出「合法写法」的判据，就不配硬拦。硬拦只给 100% 假绿或 100% 跑不了、且不存在合法写法的那些。
  4. 每条规则必须写出反例，写不出的不许上线。反例测试里「应该沉默」的用例比「应该报」的更重要。
  5. 猜意图的判据最重只能到 minor。严重度由后果定，不由把握度定——它的错误率来自「我可能理解错了」。
  6. 没有出口的提示等于逼人照做。人照做完发现更糟，下次就整体不看提示了。出口要写在提示正文里。
  7. 「没查成」必须是第三种结论。不是通过也不是打回。含金量看不出来的通过，比不审更坏——它发了一张假凭据。
  8. 跑挂了先归因再定责。被测系统有 bug 时脚本必然红。直接打回等于「用例判死刑、bug 没人管」。
  9. 并行换来的不是快，是假打回。共享数据、全局开关，一次串台就够毁掉这套审核的信誉。
  10. 报告要能区分「审了什么范围」。否则挑三条好的一审，就能宣布整个模块没问题。
