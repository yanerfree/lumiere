# 审核：怎么发起、怎么排队、结果看哪里

**状态：设计定稿（2026-08-21 讨论确定），§12 十二项已全部实现并活体验证过
（2026-08-21，分支 `feat/ai-review-batch`）。**
下面写的是目标行为，现在也是实际行为。改这块之前先读 §10 那三条撤销决定，
别照着更早的旧行为改；**活体验证跑出来的六个真问题记在 §14**，
其中一个是「执行式审核最值钱的判据此前从来没生效过」。

判据本身（哪几维、谁判、为什么能替人工待审）在
[cc-platform-loop-spec.md 附节](cc-platform-loop-spec.md) 和
`backend/app/services/review/RULES.md`，这份只管**流程和交互**。

---

## 0. 一句话

审核 = 拿真环境跑一遍，把**步骤、脚本、实际流量**三边对上。
**没真跑过的结论不算通过。**

---

## 1. 为什么必须真跑（原本打算批量默认静态，作废了）

静态审核（只读用例和脚本，不执行）查得出这些：恒真断言、写完没读回、
只断状态码、模糊预期、UI 脚本硬伤。查不出的恰好是最贵的那一类：

| 只有真跑才查得出 | 静态会怎么误判 |
|---|---|
| 接口场景验的端点，页面根本不调 | "写得挺完整"，照样给 80 多分通过 |
| 步骤里写的动作，脚本里压根没做 | 靠读文本比对，模型会被脚本里相近的代码骗过去 |
| 选择器早就失效、脚本跑不起来 | 从没跑过的脚本，静态看不出它跑不跑得动 |
| 跑完留了一堆垃圾数据 | 完全看不见 |

实测有一条 83 分通过的用例，静态审核逐条夸它"读回验证比较扎实"，
而它的接口场景指着一个页面从来不调的接口。**这种通过比不审更坏**——
它给了一个"审过了"的假凭据。

所以：**批量也必须真跑**，没跑成功的一律不能是 approved。

---

## 2. 三个入口，判据是"你从哪儿发起的"

不需要额外选"我这次是要审模块还是审单条"：

| 你的动作 | 平台理解成 | 类型 |
|---|---|---|
| 左侧点中某模块，**一条都没勾**，点「AI 审核」 | 审这个模块 | 模块全量 / 模块增量 |
| 列表里勾了 N 条，点「AI 审核」 | 只审这 N 条 | 抽审 |
| 进用例详情，点里面的「AI 审核」 | 只审这一条 | 单条 |
| 报告页「审核...」里选"只做体检" | 不跑用例，只看模块覆盖 | 体检 |

点下去**一定先弹确认框**（§3），把要干什么写清楚，不让人猜。

## 3. 确认框：你选什么 + 它会查什么

```
审核「订阅管理」

【你选】
  范围   ● 全部 16 条   ○ 只审没审过的和被打回的（7 条）   ○ 不审用例，只做体检
  环境   [ 测试环境 ▾ ]
         ☑ 审完顺便做一次模块体检

【这次会逐条查这些】—— 不可勾选
  1  真跑一遍，跑不起来就不算通过
  2  步骤里写的每个「操作」，脚本里有没有真做这个动作
  3  步骤里写的每个「预期」，脚本里有没有对应的检查
  4  接口场景里调的接口，页面上是不是真的会调它
  5  断言是不是恒真的（写了等于没写，坏了也照样绿）
  6  改完数据有没有读回来确认真改了
  7  预期里有没有「显示正常」这种模糊话
  8  跑完有没有把造的数据清干净
  9  跑挂了先分清是脚本问题、还是被测系统的 bug

预计 25 分钟 · 可以关掉页面              [ 开始审核 ]
```

**检查项故意不做成可勾选。** 能勾就能放水：今天嫌某项烦关掉，
以后这批"通过"就没法解释含金量。能选的只有三样——审哪些、哪个环境、要不要顺带体检。

第 2、3 条是这轮新提的硬性要求（原来是模型判、算 major）：
**每个「操作:」步骤脚本里必须有对应动作，每个「验证:」步骤必须有对应断言**，
缺一个就是 blocker。加上第 4 条的流量对账，这三条合起来才叫"页面上完全可复现"。

## 4. 类型：报告里必须区分

一眼看不出是审了整个模块还是抽了三条，这份报告过两周就没人信。

| 类型 | 含义 | 报告里有什么 |
|---|---|---|
| **模块全量** | 模块全部用例 + 体检 | 逐条结果 + 共性问题 + 覆盖缺口 |
| **模块增量** | 只审没审过的和被打回的 + 体检 | 同上，注明"另 N 条沿用上次结论" |
| **抽审** | 勾选的 N 条 | 只有逐条结果 |
| **单条** | 详情页发起 | 一条 |
| **体检** | 不跑用例，只看模块覆盖 | 只有共性问题 + 覆盖缺口 |

**只有「模块全量」能代表这个模块的情况。** 抽审、增量只能说"这几条过了"——
否则挑三条好的一审，就能宣布模块没问题。

## 5. 环境与排队

### 发起时必选环境

- **没配环境的项目不能发起**——弹窗直接说"先去配环境"，
  而不是跑起来然后 16 条全标"无法审核"。
- **环境要记进报告**："在哪套环境上审过"是结论的一部分。
  测试环境过了，不等于预发环境也过。
- 单条审核别每次都问：默认用项目默认环境，按钮旁小字写"在 测试环境 跑"，想换点一下改。
- **体检不用选环境**，它只读用例库、不碰被测系统。

### 一个环境一条队列，串行

并行换来的不是快，是**假打回**：

- 两条脚本用同一个租户、同一个账号，A 跑到一半 B 把数据删了 →
  A 莫名报错 → 审核判 A"脚本有问题"，其实是被踩的。
- 网关那边「平台关闭本租户审批开关」是个**全局开关**，一条脚本把它关了，
  另一条正好在测开关开着的行为 → 两边结果都不可信。

假打回出过几次，这套审核就没人信了。所以：

- 同一环境 → 排队，一条接一条。一个项目通常就一个测试环境，所以实际上就是排队。
- 不同环境 → 可以同时跑。
- **人工发起的插到 CC 自审前面**——人在等结果，CC 不在等。
- 同一条用例被重复发起 → **合并**，不跑两遍。
- 体检不占队列。

### 环境挂了要熔断

环境一挂，队列会一条接一条全失败，16 条全标"无法审核"，看起来像用例有问题。

**连续 3 条都是环境类失败 → 暂停整个队列**，页面上说"环境好像挂了，剩下 13 条先停着"，
等人确认后继续。不白跑，也不污染一整批结论。

## 6. 审核报告页：一张表，一行一次审核

现在这页是"一行一个模块"，塞不进类型，而且点一行只是跳到筛好的用例列表——
那是筛选器，不叫报告。改成：

```
审核报告      待审：订阅管理 16 · 服务管理 6 · 跨租户订阅 1     [审核...] [刷新]

类型      范围            环境      发起人  状态 / 结果                      时间
模块全量  订阅管理 16 条   测试环境   我      ⏳ 进行中 5/16 · 约 18 分钟      08-21 20:14
模块全量  服务管理 6 条    测试环境   我      ⏸ 排队中 · 前面 11 条           08-21 20:15
抽审      订阅管理 3 条    测试环境   我      ✓ 通过3                        08-21 15:02
单条      TC-DYGL-00008   测试环境   CC     ✗ 打回                         08-21 14:40
体检      订阅管理         —         我      ✓ 覆盖缺口 5 项                 08-20 09:30
```

- 状态五种：排队中 / 进行中 x/y / 已完成 / 部分失败 / 已取消。排队中的可取消、可插队。
- 「还有多少没审」放标题右边那行字——它只有三个数，不值一张表。
- **默认只看「我」发起的。** CC 每次回推都会自审，一天几十条，全混在一起就找不到
  自己点的那次了。开关可切到"包含 CC 自审"。
- 点某行 → 打开那次的报告（§7）。行上的动作是「看报告」，
  **不是"再审一次"**——审核在用例管理页发起，这页只看结果。
- 标题右边「审核...」是顺手的入口（在这页想起来要审某个模块，不用跳回去），
  「重做模块体检」也在这儿。不是流程里必须的一步。

未审过任何东西时表是空的，显示"还没审过，点右上角开始"，待审数照样看得见。

## 7. 模块报告长什么样

```
订阅管理 · 模块全量 · 测试环境 · 08-21 20:14 · 共 16 条

结论：打回 3 条，无法审核 4 条（缺环境）

【共性问题】—— 改一处能修一片
  · 9 条只看了接口返回的状态码，没读回数据确认真改了
  · 5 条承诺要做 UI，但根本没有 UI 脚本
  · 4 条的预期写着"正常显示"这类模糊话

【覆盖缺口】—— 这个模块还缺什么
  · 16 条全是走通的正向流程，没有一条测"审批被驳回后重新提交"
  · 跨租户订阅只测了两级都通过，没测中途撤销
  · 一条权限用例都没有：非本租户的人能不能看到别人的订阅

【逐条结果】（默认折叠）
  TC-DYGL-00017  通过
  TC-DYGL-00016  打回 · 步骤3说要搜索，脚本里没做这个动作
  ...
```

**价值在前两块。** 一条一条看只知道"这条不行"；看模块才知道
"这一整片都犯同一个错"和"这个模块压根没测到的地方"。

- 点某条用例 → 跳那条详情看细节
- 顶上「去改这些」→ 跳到已筛好的用例列表（只剩被打回的 3 条）。
  跳列表这个动作留着，但它是"我要动手改了"的入口，不是"我要看结果"的入口。

## 8. 模块体检

**输入**：这个模块全部用例的标题和步骤 + CC 在页面上探到的这个模块实际有哪些可操作项。
**输出**：共性问题（把逐条 findings 归类聚合，纯汇总）+ 覆盖缺口（额外一次模型调用）。

- 一两分钟，不占队列，不用环境。
- 三个发起口：模块审核时默认附带 / 报告页单独做 / **CC 自己通过 MCP 问**
  （它写完一批用例后问"这个模块还缺什么"，拿到清单接着补，不用人催）。
- **覆盖缺口是建议清单，不是门禁**，不参与任何一条用例过不过。

> 与旧结论的差异：`cc-platform-loop-spec.md` 附节写着"模块级遗漏判不了，
> 该由人看"。现在敢让它出缺口，是因为多了**页面探测出的实际可操作项**做对账，
> 不再是纯凭用例标题猜。但定位没变——**情报，不是闸门**。

## 9. 跑挂 ≠ 用例不合格（这条不做会很伤）

被测系统真有 bug 时，脚本必然跑红。直接打回用例的后果是：
**用例被判死刑、bug 没人管**，而且被测系统一出问题整批全红。所以真跑失败先归因，三分：

| 归因 | 结论 | 后续 |
|---|---|---|
| 脚本/断言写错 | 打回用例 | CC 整改后再审 |
| 被测系统 bug | **用例照样可以通过** | 开失败单 + 挂 `bug_refs`（留痕迹，永不清除） |
| 环境 / 数据问题 | **无法审核** | 既不算通过也不算打回 |

### 新增一个结论：「无法审核」

缺环境、没脚本、环境本身挂了 → 不是通过也不是打回。
现在 `review_run_skipped` 只是一条 finding、不阻断结论，要改成**硬阻断**：
没真跑成功，就不可能是 approved。否则"全批通过"里混着没跑的，含金量看不出来。

## 10. 这轮撤销的三个设计（别照着旧的实现）

**① 「模块放行」——撤。** 模块没有状态；用例是陆续写的，永远不存在"写完了"这一刻；
硬造一个放行，CC 再补一条用例它就过期了。而且**不放行没有任何影响**，
平台里没有任何东西会去读它——那就是个装饰。
真正需要"放行/卡住"的地方是**发版和测试计划**，按计划范围算，跟模块无关。
"怕抽审三条看起来像审了整个模块"这个担心是真的，但§4 的类型列已经解决了。

**② 「批量默认静态审核」——撤。** 见 §1。

**③ 「脏数据账本」——撤。** 正常脚本跑完就该自己收拾干净；留垃圾只有两种可能：
脚本没写清理，或者删不掉（那是 bug）。所以不做账本这种功能，
改成审核的第 8 项检查：跑完还留着 → 脚本没清理就打回脚本，清理跑了但删不掉就开单。

**④ 「一页两张表」——撤。** 一张表加类型列就够了（§6）。

## 11. 模块命名（这轮一起定的）

### 事故现场

网关管理系统里，顶层有「本租户订阅(0)」「跨租户订阅(1)」，
同时「订阅管理」下面又有「本租户订阅(8)」「跨租户订阅(7)」——
**同一个东西摆在两处，用例被劈成两半**，顶层那个还是空的。

**根因**：CC 建模块时，平台只告诉它"现在有哪些一级模块"，
没给完整模块树。它看不见「订阅管理」下已经有这个子模块，就在顶层又建了一个。
`check_module_name()` 那句"一级模块是按被测系统的功能域分的"只是**警告**，被无视了。

测试平台自己项目里是另一种写法：4 条用例全挂在「平台自身」下——
那是个**范围词，不是模块名**。真实模块该是「用例管理」「国际化词典」这些，
左侧菜单指得到的东西。连带后果：`case_code` 前缀由模块名生成且**改名刻意不变**
（`former_names` 就是为这个做的），所以 `TC-PTZS-*` 洗不掉。

### 规则

1. **建之前先全项目搜这个名字**，不分层级——不能只给一级列表。
2. **同一位置已有 → 硬拒**，让它用现成的。
3. **不同父模块下的同名子模块 → 允许**（「订阅管理/审批配置」和「服务管理/审批配置」
   确实是两回事），但必须明确说出挂在谁下面，平台回一句
   "注意：订阅管理下也有同名的，你这次建的是服务管理下的"。
4. **一个在顶层、一个要挂到模块下 → 硬拒**，这就是事故现场那种，必须先合并。
5. **范围词/自指词硬拒**：平台自身、系统、通用、其他、公共、本平台……
   可枚举、判断确定、无合法反例，按 `RULES.md` 的判据就该硬拦。

另加一个**合并动作**：平台自己发现"顶层和某模块下有同名"，
提示"疑似同一处被拆两处，要不要把顶层那 1 条搬进去、把空的删掉"。

## 13. 已落地（2026-08-21，接活体验证那一轮的反馈）

这一节记的是**已经在跑的行为**，不是计划。前面 §12 的清单据此更新过状态。

**① 批量审核的进度看得见了。** 批量仍是一次长 POST（30 条实测跑满 5 分钟），
但客户端可以自带 `batchId`，边跑边轮询 `GET .../ai-review/batch/{batchId}`
拿 `done/total/approved/rejected/current/finished`，弹窗显示 n/N。
在此之前弹窗只有一句「逐条评审中…」——而每条都是**审完就落库**的，
详情页的轮次早就出来了，弹窗还在转：看起来像卡死，实际早就在干活。
进度台账在内存里（只留最近 20 批），重启丢了无所谓 —— 结论在库里。
这不等于 §12 ①的批次实体：**刷新页面照样丢**，跨进程也查不到。

**② 「静态审核」和「执行式审核」在页面上分得开了。** `case_review_rounds`
加了 `review_mode` / `traffic_seen` 两列（migration `zzn0rvmode`），
轮次时间线上一个标签直说是哪种、对了多少条真实流量。
非做不可的理由：两者结论强度差一个量级 —— 同一条用例实测**静态 84 分通过、
真跑 56 分打回**（接口场景里的两个端点，页面执行一次都没发过；
这个判据是 URL 集合比对，不靠模型）。此前两种审核在时间线上长得一模一样，
「这条凭什么过的」看不出来。存量轮次是 NULL，不编造、不显示。

**③ 「先跑一遍再审」这个按钮以前多数情况下不会真跑。** 页面发的请求不带
`envId`，而挑环境只认「计划/报告里跑过」的历史 —— MCP 调试跑不算。
于是**新用例点这个按钮就是静态审**，两个按钮点出来一样的结果，
而降级理由只是一条 minor finding，页面上看不见。现在挑不到历史环境时退回
「有 BASE_URL 且 sort_order 最小」的那个环境（没 BASE_URL 的环境跑出来是
空地址的垃圾运行，会被报成"这条挂了"，所以不选它），并且无论跑没跑成
都把 `reviewMode` 报出来。

**④ 覆盖缺口按话题归并，不按字面。** 原来的去重键是「去掉前缀后的头 12 个字」，
而 LLM 每轮措辞都不一样 —— 实测某模块 8 条缺口全是 1×，其中三条讲的是同一件事
（越权）。这一页存在的理由就是那个 count 列，1× 一片等于这页没有信息。
现在走关键词→话题标签（权限与越权 / 并发与竞态 / 幂等 / 边界 / 分页 / 清理残留 /
多语言 / 性能…），命中不了的退回实词签名。**判据在代码里不问 LLM**
（`app/services/review/gap_merge.py`）：这页每次打开都要算，塞模型调用既慢又不稳，
而「合并结果每次不一样」比不合并更糟。每桶留各条原话，合并了得能核对是不是一件事；
被截断时页面上明说还有几类没显示。

## 14. 活体验证跑出来的六个真问题（2026-08-21，§12 实现之后）

链路：CC 建模块/用例 → AI 审核（真跑）→ 组计划执行 → CC 归因待办。
在「网关管理系统」真环境（stoa）上跑通，下面每条都是**跑起来才暴露**的。

### ① 流量对账此前从来没生效过 ★

**现象**：`reviewMode=run_first`、脚本 55 步全执行，`trafficSeen` 却恒为 0。

**根因**：多角色脚本必须自己开 context（`browser.new_context(**browser_context_args)`），
而 args 里带着同一个 `record_har_path`。Playwright 在**每个 context close 时把 HAR 整份重写** ——
后关的直接覆盖先关的。实测：测试内打印 28MB，pytest 退出后只剩 324 字节、0 条 entry。

**为什么最贵**：`traffic_diff` 是这套审核里最硬的一条判据（URL 集合比对，不问模型），
它抓的正是 §1 那个「接口场景验 `/provider`、页面实际调 `/provider-unified`，
两个都返回 200 所以用例一直绿」。它空转了多久没人知道，因为**空流量和"端点都对"
在报告上长得一模一样**。

**修法**：conftest 给每个 context 分 `network-N.har`，读取时合并（`har.parse_har_dir`）。
修完同一条用例 `trafficSeen` 0 → 51，当场抓出一条真的端点不符。

### ② 脚本截断制造假 blocker，而且专挑写得用心的打

评审证据只喂脚本前 6000 字，而 UI 脚本开头是大段 docstring ——
TC-DYGL-00016 的 `def test_` 在第 10361 字符、第一个 `expect()` 在第 6534 字符，
**全在截断点之后**。于是判出「没有测试函数」「一个断言都没有」两个假 blocker（实际各有 1 个和 11 个）。
错的方向是固定的：**注释写得越足越容易被打回**。

修法：代码侧判据一律用全文（`evidence._judged`），喂模型的截断改成头+尾。
修完那条用例 46 分 → 68 分，两个假 blocker 消失。

### ③ 幽灵端点误报

接口场景里整条 URL 全是变量（`${BASE_URL}${path}`）的步骤，归一后是 `/api/{id}{id}`，
跟任何真实流量都对不上，每次都被报成「页面一次都没发过的端点」。
**这条判据一旦开始喊狼来了，真的那条也没人信了** —— 跳过不比。

### ④ 模块体检把父模块算成 0 条

「订阅管理」的 16 条用例全在子模块下（审批配置 1 / 本租户订阅 8 / 跨租户订阅 7），
直属是 0 条。体检、批量审核范围、确认框条数三处都只查了直属 ——
体检报告一片空白，看起来像"这个模块很干净"，实际一条都没看。
改成连子树一起（`_folder_scope`）。

### ⑤ 裂口提示变噪音

`find_split_modules` 原来无条件追加，于是**每建一条用例**都收到同样两句
「顶层和订阅管理下都有跨租户订阅」—— 跟"我现在要往服务管理加一条"毫无关系。
每次都出现的提示等于没有提示。改成只提跟本次模块相关的那一处。

### ⑥ 共性问题最大的一桶写着「other」

模型产出的 finding 只有 `dimension` 没有 `kind`，全落进兜底桶。
这一块存在的理由是"改一处能修一片"，而「5× other」说不清是哪一处。
没 kind 就按维度分桶，并给每个 kind 配人话标签。

### 顺带确认能用的

- 事故现场（顶层「本租户订阅(0)」「跨租户订阅(1)」+ 订阅管理下同名的 8/7 条）
  被 `find_split_modules` 在真实数据里找出来了；八条命名判定全部符合预期。
- 没配环境的项目发起审核 → 400 + 「先去项目设置加一个」，不再是跑起来全标无法审核。
- 队列串行、进度落库、关页面不丢、报告页一行一次审核、模块报告 —— 都按设计工作。
- 体检传 `observed_actions` 之后出的缺口是具体的（「查看怎么消费」入口零覆盖），
  不传只能凭标题猜。
- 计划执行 3 条 100% 通过；CC 待办队列被审核产出的覆盖缺口喂上了（待补场景 5 条）。

### 还没在活体里跑到的

- **熔断**（连续 3 条环境类失败）：环境一直是好的，没造出连挂三条的现场。
  判据和计数逻辑有单测，但没在真环境上触发过。
- **被测系统 bug 开单那条路**：这轮执行 3 条全绿，没有失败可归因。

## 15. 接手清单四项（2026-08-24，§14 那轮之后）

§14 的六条修完之后还剩四条**只做了缓解、没解决**的。这一节记的是已经在跑的行为。

**① 单条审核超时，现在查得到。** `tb_review_case` 还是一次同步 await（静态审多数
十几秒，为它背一个轮询循环不划算），但它现在**在批次台账上留一行**
`kind="cc_inline"` 的账：既是"正在审"的标记，也是防重复的锁。超时后 CC 再调一次
会被挡下并拿到 `{"status": "in_progress", "startedMinutesAgo": …}`，而不是又触发
一次分钟级真跑。另开只读工具 `tb_review_check(case_id)` 查状态和上一次的结论 ——
它**不触发**评审。

`cc_inline` 是**专门开的 kind，不是复用 `single`**：`single` 是人在详情页点
「审这一条」发起的，那种**走队列**（`api/case_review.py` 里 `len(case_ids)==1`
就推断成 single）。当成内联标记的话，服务一重启的收尾逻辑就会把人正在等的那次
审核判死 —— 库里现成就有 4 条 `actor=admin` 的 single 批次。
超过 15 分钟没动静的 `cc_inline` 视为进程崩过，标 failed 后放行；`single` 一律不碰。

**② 结论过期，列表上看得见了。** `content_hash` 之前只影响详情页时间线，
列表的「通过/打回」不会退化 —— 于是"通过之后又被改过"的用例在列表上仍是一枚绿标。
现在列表和详情都带一个**只读派生字段** `reviewStale`，前端在原标签旁叠一个 ⚠。

**没有新增 `review_status` 枚举值**，照抄 `rounds.display_status()` 里
`resubmitted` 的旧取舍：动那个字段会牵连门禁、筛选、批量操作一大片。
所以 `reviewStale=true` 的用例**仍然是 approved**，按 `reviewStatus=approved`
照样筛得到 —— 这是有意的，它说的是"这个结论可能对不上现在的内容"，
不是"这条没通过"。存量轮次没有 `content_hash` 的**不给这个字段**
（不是给 false）：判不出来就不猜，给 false 等于断言"没过期"。

**③ 步骤角色不再让模型猜前缀。** 「前置/清理」这类角色此前只写在 `_SYSTEM`
提示词里让模型自己从中文前缀认。现在 `evidence._steps_text()` 直接把
`role`（setup/action/verify）和 `refsScenarioStep` 标成结构化字段，
和机器判据共用 `step_coverage.role_of` 同一份正则 —— 两处漂移就会互相冤枉。
**判分逻辑一个字没动**，这条纯粹是喂给 LLM 的证据质量。

**④ finding 去重补了一道结构化判据，但它只是第三道、不是替代。** 两边现在都可以
声明 `stepRef`：LLM 按提示词填，机器那边由 `step_coverage` / `_vague_findings`
把手上现成的 `seq` 直接带出来。

**这道判据够得着的范围要说清楚**，别照着"从此不用猜数字"去理解：
接口侧那批机器判据（`tautology_assertion`、`no_readback`、`control_plane_only`…）
是**按步骤名**定位的，压根没有序号，那些仍然只能靠散文里的数字碰运气。
活体验证时就撞见过这种够不着的情况（机器判据措辞里一个数字都没有，模型老实填了
`stepRef` 也无处可撞），所以旧的两道判据——措辞前缀重合、同维度同数字——一条都没删。
