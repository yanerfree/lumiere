## 三、Track A —— 生成质量

### A1. 生成即验证，未验证不得发布 🔴 最高优先

**问题**：MCP instructions 里写了"先活体验证"，但那是软约束，模型可以不听；
34/35 场景停在 draft，没人知道哪条真能跑。

**做什么**
1. `api_test_scenarios` 加验证态（复用 Phase 0 的记录）：`未验证 / 已验证(env, 时间) / 已失效(改动后未重跑)`。
2. **状态门禁**：`draft → published` 必须有一条"当前内容 + 某环境全绿"的验证记录。
   内容变了（步骤 hash 变化）自动退回"已失效"。
3. 列表和用例 Tab 上直接显示验证徽标，一眼看出哪些是"写出来了但没跑过"。

**为什么值得**：这是把"AI 写得像模像样"和"真能跑"分开的唯一硬手段。目前两者混在一起。

**验收**：手工改一条已验证场景的 URL → 徽标自动变"已失效"；未验证的点发布 → 被拒并提示。

### A2. 前置数据机制落地到真实项目 🟡

**问题**：机制建好了但 0 采用（现状 #2），26 处写死 UUID 还在。

**做什么**
1. 给网关管理系统登记 4 个 `automation_resource`（`upstreamId`/`isolationId`/
   `consumerAppA`/`consumerAppB`），各配 `exists_check`。
2. 把 8 条用例里的 literal UUID 场景变量改成引用。
3. 跑一遍确认 5 条场景仍全绿 —— **这一步才算真验证了那套机制**，之前只在我自己造的
   场景里验过。
4. 顺手把 `tb_upsert_automation_resource` 的用法写进 CC 的 onboarding 提示。

**验收**：删掉某个资源 → 预检当场报"缺 upstreamId"，而不是等到第 7 步报"变量未解析"。

### A3. 已验证契约回灌 🟡

**问题**：CC 每次生成都得重新猜接口契约。我这次实测就撞出 2 处不一致
（`POST /environments/{id}/variables` 其实是 `PUT`；`{"variables":[...]}` 其实收裸数组）。
猜错的代价是整条场景白写。

**做什么**：某条场景验证全绿后，把每一步的**实测契约**（真实 method / 状态码 /
请求体形状）回写到「API 接口」模块，标记来源=实测。下次生成时 `tb_list_api_tree`
优先给实测契约，而不是文档里的。

**验收**：故意把接口文档里的 method 写错 → 生成出来的步骤用的是实测的那个。

### A4. 清掉两处已知的质量污染 🟢 小改动

- ~~步骤拆分塞模板套话~~ **已修**（`test_cases.py:602`）：拆出来的中间步骤现在
  **留空预期不编**。原先填的是"操作完成，页面状态更新"—— 那正是入库门禁
  `_FUZZY_WORDS` 要拦的模糊词，平台自己注进去的。
- `_looks_hardcoded` 扫 body 全部字符串，请求体里合法的中文 `description` 会被
  误报成"疑似写死的业务数据"。加字段名白名单（description/remark/comment/note/title）。
  **仍未做（半做了）。** 2026-08-21 复核：函数已经收了 `field_path` 参数、
  加了枚举字段白名单（`_ENUM_FIELD_RE`：type/protocol/status/mode/…），
  所以 `config.protocol="http"` 这类不再误报。但**文本字段没进白名单**，实测：

  ```
  description  "用于回归的测试服务，勿删"  -> 报警 True
  remark       "本次自动化创建"          -> 报警 True
  note / title 同样 True
  ```

  这是 **bug 不是需求变更**：误报的代价不只是噪音 —— 警告多了人就不看了，
  真正写死的 id 反而被淹掉，而这个函数存在的理由就是抓那个 id。

## 四、Track B —— 生成效率

### B1. 增量修复代替整体重生成 🔴

**问题**：11 步的场景错 1 步，现在只能整条重生成 —— 又慢，又可能把原本对的 10 步改坏
（我这次就亲手制造过一次：编辑器往返把 `in [200,204]` 改成 `== "200,204"`）。

**做什么**
- MCP 增 `tb_patch_scenario_steps(scenario_id, steps=[{sort_order, ...只传要改的字段}])`，
  按 `sort_order` 定点改，不动其它步骤。
- 配套 `tb_rerun_failed_steps(scenario_id, env_id)`：只跑失败步骤及其**依赖前置**
  （靠 `variables_extract` 反查依赖链），不整条重跑。

**收益**：改一步的成本从"重生成 11 步 + 重跑 11 步"降到"改 1 步 + 跑 2~3 步"。

**验收**：故意改坏第 7 步 → `tb_rerun_failed_steps` 只跑第 1(登录)、7 步。

> **2026-08-21 复核：上半做了、下半没做。**
> 定点改步骤已经有了，但形态跟这里写的不一样：不是新增
> `tb_patch_scenario_steps`，而是 `tb_sync_orchestrated_scenario(mode='patch')`
> **按 step name 匹配**（不是 `sort_order`）。按 name 更稳 —— 插一步之后
> sort_order 全变，而 name 不变。
> `tb_rerun_failed_steps`（只跑失败步骤及其依赖前置）**仍然没有**，跑就是整条重跑。

### B2. 已验证片段库 🟡

**问题**：每条场景都在重写「登录取 token」「清理」这类样板，既费 token 又是错误来源。

**做什么**：把验证过的步骤块存成可引用片段（`login/ADMIN`、`cleanup/env`…），
生成时用 `${block:login}` 引用而不是复制。片段升级一次，引用它的全部场景跟着变。

**验收**：新建场景只写业务步骤，生成的 token 量明显下降；改片段后引用方全部生效。

### B3. 生成前置成本的削减 🟢

- 429 已在 `d8ac5cb` 修完（有 CLI 通道时立刻降级，不再干等 ~98s）。
- 新模型 `temperature` 400 也已修。
- 剩下：给 `tb_list_api_tree` / `tb_get_case` 这类高频只读工具加短 TTL 缓存，
  CC 一轮生成里往往要重复拉好几次。

> （`script_bug` / `system_bug` / `env_issue`）后续动作要可点 —— 那条并进 C2。

**问题**：现状 #1 —— 三样都齐了，就差一个按钮。

**做什么**
1. 运行结果面板（刚做的吸底面板）加「诊断失败原因」按钮，调已有的
   `POST .../skills/tb-diagnose`。
2. 诊断结果按 skill 里已定义的三分类展示：`script_bug` / `system_bug` / `env_issue`，
   每类给对应的下一步动作：

**验收**：拿一条真失败的场景点诊断，三分类判对且给出的修复建议可执行。

### C2. 失败态可执行化 🟡

现在失败信息已经能看见了（上一批做的：变量未解析当场说、每步请求/响应/断言可展开），
下一步是**从"看得见"到"点得动"**：

- 变量未解析 → 面板上直接给"补到环境变量 / 补成场景变量 / 登记为前置资源"三个按钮。
- 断言不通过 → 给"实际值 vs 期望值"的 diff，以及"就用实际值更新断言"（人确认后执行）。
- 连不上 → 直接显示该环境 BASE_URL 和服务状态（复用刚做的「服务与端口」）。

### C3. 抖动识别 🟢

同一条场景连续跑 N 次，结果不一致的标 flaky，不计入"一次通过率"，单独列出。
没有这个，Phase 0 的指标会被抖动污染，越优化数字越难看。
