# CC 反馈通道 + 「CC 反馈」页：需求与落地方案

> 关系：这是 [cc-platform-loop-spec.md](cc-platform-loop-spec.md) §13（把人从按按钮里拿掉）
> 的**配套欠账**。那一节把人从流程里拿掉之后，CC 的观察就没有出口了 —— 和 §13.4
> 「自动化本身会把观测手段一起吃掉」是同一个坑，只是这次被吃掉的不是指标，是**回声**。

---

## 0. 一句话边界规则（所有争议以此仲裁）

**这条观察有没有一个「能自己报错」的家？有 → 去那儿；只有人肉看才发现得了 → 才进这个通道。**

推论：被测系统的缺陷**永远不该**报到这里 —— 它有个严格更好的家叫「一条会红的用例」。
把缺陷写成一句自由文本，等于放弃了回归保护，而且**永远不会再报错**（假废弃同一种毒）。

---

## 1. 缺的是什么（不是推测，是现在就在丢的东西）

MCP instructions 已经写着两条要求（`app/mcp/__init__.py`）：

- 「**发现了这条用例之外的问题**：别的模块的缺陷、**平台工具本身不对劲**、
  文档和代码互相矛盾 —— 顺手说一声，别因为『不在这次范围内』就咽下去。」
- 「**卡住了**：环境连不上、账号没权限、依赖的数据造不出来 —— 说出来，别硬试。」

**「说一声」说给谁？** 说给坐在那个 CC 会话里的人 —— 那可能是外部项目的开发，不是平台维护者。
而 §13.2 变化 1 之后，`/loop /lum-round` 那条链上**根本没人坐在那儿**：CC 醒来、干一轮、
说一句、睡下去，会话上下文一关就没了。`duty.py` 自己的注释早写过这件事：
「清单必须落平台 —— CC 一关会话上下文就没了，续不上」。

**这不是假想的损失，历史上这一类发现全靠人碰巧在场：**

| 发现 | 类别 | 怎么被发现的 |
|---|---|---|
| §9.1 提取路径不认 `$.` 前缀，**而且报错指错地方** | 工具缺陷 | 人手工 dogfood 时撞到 |
| §13.2 变化 3 instructions ⑦ 和 `lum_update_case` 描述**互相打架** | 规范冲突 | 人读代码时读出来 |
| 共享资源功能**全平台 0 行**（CC 登记完拿不到回音） | 通道断了 | 人查表查出来 |

这三条要是发生在自动轮里，今天不会有任何记录。

## 2. 现有写回通道对一遍，剩下的才是缺口

| CC 撞到的东西 | 现在的家 |
|---|---|
| 本条用例红了、判得出原因 | 跟进单 + `lum_submit_analysis` |
| 被测系统反直觉行为，下轮别再踩 | `lum_add_project_note` |
| 这个模块缺场景 | 建用例（`lum_module_checkup` 也会算） |
| 前端没给 testid，UI 脚本没抓手 | `lum_upsert_selectors(status='gap')` + `blocked_cases` |
| 这条用例卡在外部条件 | `lum_update_case(blocked_external)` |
| 这条用例在验什么 | `reflections` |
| **平台工具描述与行为不符 / 返回缺字段 / 报错指错地方** | ❌ 无 |
| **平台规范自相矛盾**（两处描述打架、文档和工具行为不一致） | ❌ 无 |
| **卡住了，且不属于任何单条用例**（环境连不上、账号没权限、依赖数据造不出来） | ❌ 无（`blocked_external` 只挂单条） |
| **「要是平台有 X，我这轮就不用绕这一大圈」** | ❌ 无 |
| 被测系统缺陷，但这一轮**建不了用例**（不在本分支范围 / 缺账号） | ❌ 无 |

**通道只收这 5 类。** 前 6 行有更好的家，报进来是退步。

## 3. 五个 kind，各自的准入证据（硬拒，不软警告）

| kind | 必交 | 拒收时告诉它 |
|---|---|---|
| `tool_defect` | `toolName` + `calledWith` + `gotBack` + `expected`（**引工具描述原话**） | 缺哪一样 |
| `spec_conflict` | `whereA` / `whereB`（文件:行 或 工具名）+ 各自原话 | 只有一处出处 = 那是你的理解，不是冲突 |
| `blocked` | `tried`（≥2 次尝试的记录）+ `needs`（谁做什么才能解） | 试一次就报 = 还没到"卡住" |
| `gap_request` | `detour`（这轮为它绕了什么路、多花了什么） | 没有绕路成本 = 那是建议不是需求 |
| `out_of_scope` | `whyNoCase`（**为什么建不了用例**）+ 复现要点 | 建得了就去建，见 §0 |

**理由**：这五样都是"真撞到了就写得出来，写不出来大概只是顺口一提"。
和 `lum_submit_analysis` 的 `product_defect` 三件套（liveVerified/codeRefs/issue）同一条思路 ——
**门槛不是为了拦，是为了让报上来的那条自带复现步骤**，否则受理人要回头猜。

## 4. 防倒灌三道闸（没有这三道，这个页面三周后没人看）

1. **指纹去重，口径直接照抄 `failure_tickets`**（`models/failure_ticket.py` 的归并口径，
   连理由一起抄）：`kind` + 归一化锚点（工具名 / `文件:小节` / 端点模板）。
   - 单子**开着**时同指纹再报 → `occurrences+1` + 更新 `last_seen_at`，**不新开**。
   - 单子**关掉之后**又撞到 → **新开一张 + `reopened_from`**。
     「修好了又坏」是回归，是新信息，并进老账里会把它埋掉。
2. **每分支每轮最多 3 条新指纹**，超了拒收。CC 一轮能撞到十个"不对劲"，
   全收进来就没有优先级了 —— 迫使它自己排序，别把判断成本整个推给人
   （同 instructions ①-A「别甩清单」）。
3. **CC 填不了 severity。** 排序 = `复发次数 × kind 权重`。
   让它自己填，填出来一路是 high —— 那一列就等于不存在。

## 5. 回音：这一节是全文重点

**已经有一个现成的反例**：共享资源（`lum_upsert_automation_resource`）全平台 0 行，
loop-spec 记的原因是「CC 登记完拿不到回音，没有反馈，这功能进不了它的工作流」。
反馈通道要是没有回流，三周后就是第二个 0 行功能。

四处回流，缺一处都断：

1. **`lum_next_duty` 加一个队列「反馈有回音了」** —— 按 **project** 取（不限分支：
   同一个洞换个分支照样存在），每条带状态 + 结论原文。
2. **复报当场给回音**：「已收到，这是第 3 次，状态=已受理」。
   否则它会以为没送达，然后换个说法再报一条（指纹绕过去了，去重就白做）。
3. **`wont_fix` 必须写理由**；之后同指纹再报 → 直接回原理由、**不入队、不计数**。
   不给理由，它下一轮一定原样再报一次。
4. **`fixed` 必须写「现在该怎么做」** —— 因为工具缺陷最常见的修法是**改工具描述**
   （MCP 描述就是本平台唯一的规范载体）。而这里有个本仓库特有的坑：
   **改完描述不重启后端就不生效**（CLAUDE.md 硬规则），CC 下一轮看到的还是旧描述，
   会判定"说改了没改"然后再报一次。所以页面在 `resolution=改了工具描述` 时
   **明着提示** `bash deploy/restart-backend.sh`。

## 6. 状态机（别发明新的，照跟进单的经验）

```
new ──受理──> triaged ──┬──> fixed      （必填：现在该怎么做）
 │                      └──> wont_fix   （必填：为什么不修）
 └──> duplicate（合并到另一条，回音指向那条）
```

- **CC 不能关单**，和 §13.4 同一条红线。CC 只能「报」和「复报」。
- `fixed` 之后同指纹再撞 → 新开 + `reopened_from`（说明没修对，或者是回归）。

## 7. 页面需求：`/settings/cc-feedback`「CC 反馈」

**放在设置菜单，和「服务监控」并列**（同属"平台自身"那一组），**不进项目菜单** ——
同一个工具缺陷在 N 个项目里各挂一条，而它们是同一个洞。每条带项目/分支来源列即可。

**权限**：新增一个权限点 `system.ccfeedback`（读写同档，admin）。
**不拆读/写两档**：没有"只看它但不受理"的人，拆出来的只读档是空档位。
（权限点唯一出处仍是 `core/permissions.py`。）

### 默认视图 = 待办，不是全量

顶部四个数字：**待受理 / 已受理未修 / 复发中（fixed 后又撞） / 本周新增**。
**不做百分比** —— 分母是"CC 撞到的洞"，没人知道它多大，通过率式的数字在这儿是假精确。

### 列表

| 列 | 说明 |
|---|---|
| 类型 | 5 个 kind 徽标，颜色区分 |
| 标题 | CC 写的一行；不截断到看不懂，超长省略 + 悬浮全文 |
| 锚点 | 工具名 / `文件:小节` / 端点模板 —— **可点，同锚点聚合筛选** |
| 撞了几次 | `occurrences` + 最近一次时间；复发过的（`reopened_from` 非空）单独标 |
| 来源 | 项目 · 分支 · Key 名（`mcp_api_keys.name`，答"哪个 CC 报的"） |
| 状态 | new / triaged / fixed / wont_fix / duplicate |

默认排序：`状态(new 前)` → `撞的次数 desc` → `最近一次 desc`。
筛选：类型、状态、项目、锚点关键字。

### 详情抽屉

- **CC 交的证据原文**：`calledWith` / `gotBack` / `expected` 分块、等宽、可整块复制
  （受理人第一个动作就是照着复现一遍，复制不动就等于没交）。
- **复发时间线**：每次撞到的时间 + 那次的分支/用例编号。
- **受理区**：状态下拉 + 结论文本（`fixed`/`wont_fix` 必填）+
  `resolution=改了工具描述` 时那条重启提示 + 保存。

### 空状态：不写「暂无数据」

写：「CC 这一阵没报东西。要么真没洞，要么它没在用这个通道 ——
后者这么查：<操作日志 → 按 `lum_report_feedback` 筛>」。
理由是 CLAUDE.md 那条规矩：**别断言"谁在用/还活不活着"，要让它可查并把怎么查一起写上。**
一个 0 条的列表默认长得像"很干净"，而它同样可能是"通道死了"。

### 页面明确不做

| 不做 | 理由 |
|---|---|
| 评论区 / 多人讨论 | 受理人就一个，讨论发生在 CC 会话里 |
| 指派给人 | 同上 |
| 优先级手填 | §4.3，会被填成一路 high |
| 通知推送（渠道已有） | 低频异步，推送会训练人忽略它。先看量 |
| 反馈进「项目须知」 | 须知是 CC 每轮都读的**事实库**，混进它自己的抱怨会污染判断 |

## 8. MCP 侧（两个工具，不多加）

- `lum_report_feedback(kind, title, anchor, evidence{...}, project_id, branch_id?, case_code?)`
  → 回 `{feedbackId, 第几次, 状态, 已有结论}`。
- `lum_list_my_feedback(project_id, status?)` → 报过的 + 回音（`next_duty` 之外的直查口）。
- **不加 `lum_close_feedback`**（CC 不关单）。
- **instructions 里「顺手说一声」那句改成指向这个工具** —— 它现在没有落点，是条死路。

## 9. 记账与封样（CLAUDE.md 硬规则，别漏）

- 写操作**必须记操作日志**，对象类型加「CC 反馈」；`actor_type` 由现成的
  `mcp/middleware.py:on_call_tool` 注入，页面上就能分清人受理和 CC 报送。
- 新增的 HTTP 写路由会自动进 `tests/test_authz_seal.py` 的反向差集
  —— 游客非 GET 闸门自动覆盖，**别加白名单**。
- 改完 MCP 注册/描述 → `bash deploy/restart-backend.sh`（不重启对外不生效）。

## 10. 验收标准（可判定，不含"用户满意"）

1. `tool_defect` 缺 `gotBack` → **拒收**，返回里明说缺哪一样
2. `out_of_scope` 不写 `whyNoCase` → 拒收，并指向「去建用例」
3. 同一件事报 5 次 → 库里 **1 条**、`occurrences=5`、`last_seen_at` 更新
4. 一轮报第 4 条新指纹 → 拒收，提示自己挑最堵的
5. 受理后 `lum_next_duty` 出现「反馈有回音了」队列，含结论原文
6. `wont_fix` 那条同指纹再报 → 回原理由、**不入队、`occurrences` 不变**
7. `fixed` 后同指纹再撞 → **新开一张**，`reopened_from` 指向老那张
8. `resolution=改了工具描述` → 页面出现重启提示
9. 非 admin：菜单无入口 + 直连路由拿不到数据；游客打写路由 403（跑 `test_authz_seal.py`）
10. 页面 0 条时显示的是「怎么查通道死没死」，不是「暂无数据」

## 11. 排期

| 刀 | 内容 | 量级 |
|---|---|---|
| 1 | 表 + 迁移 + 指纹归并 + `lum_report_feedback` + 三道闸 | M |
| 2 | 回音四处（`next_duty` 队列 / 复报回音 / wont_fix 短路 / fixed 带做法） | S |
