# CC 反馈通道 —— 需求方案 + 开发计划

> **一句话**：外部 Claude Code 在梳理用例、回推平台的过程中撞到的**平台自己的问题**，
> 现在只能靠人转抄。开一条它自己能走的通道，落到一个页面上，
> 分成 bug / 优化 / 需求三类处置，**每一条都必须有回音**。

状态：**已实现**（2026-09-01）。实现清单见 §10 的 Story 表。

---

## 0. 仲裁规则：什么算「该走这条通道」

只有一句判据，先过它再往下看：

> **这条观察有没有一个「能自己报错」的家？**

有 → 走那个家，别往这儿塞。没有 → 才是这条通道的东西。

| 观察 | 它的家 | 为什么不走反馈通道 |
|---|---|---|
| 被测系统的缺陷 | `lum_submit_analysis(cause=product_defect)` | 有跟进单、有复跑、跑绿自动关 |
| 被测系统「本来就这样」的反直觉行为 | `lum_add_project_note` | 下一轮读得到 |
| 用例该废了 | `lum_request_deprecate` | 有证据校验和废弃审核 |
| 前端没给 testid | `lum_upsert_selectors(status='gap')` | 进 `lum_next_duty` 的待补队列 |
| 一份规范/写法约定 | `lum_push_skill` | 不限长度，下一轮 pull 得回来 |
| **平台工具本身不对劲 / 文档和实现打架 / 缺一个口子 / 卡死了** | **← 就是这条通道** | 今天没有任何家 |

这一栏必须写在工具描述里。不写的话，反馈通道会变成上面五种东西的垃圾场 ——
每一条塞错地方的反馈，都是一条**从此不会自己报错**的信息。

## 1. 今天到底丢了什么（不是推测，是实测）

`app/mcp/__init__.py` 的 `instructions` 里写着：

> · **发现了这条用例之外的问题**：别的模块的缺陷、平台工具本身不对劲、文档和代码
>   互相矛盾 —— 顺手说一声，别因为"不在这次范围内"就咽下去。

「顺手说一声」只到得了**当时坐在那个 CC 会话前面的人**。而 `/loop /lum-round` 跑的时候没有人。
`app/mcp/tools/duty.py` 自己的注释把这件事写得最清楚：

> 清单必须落平台 —— CC 一关会话上下文就没了，续不上。

于是这条指令是**一条死路**：它要求 CC 说出来，却没给它嘴。

三条已经实际丢掉的证据：

1. **2026-09-01 那份反馈文档**（648 行、31 条问题、`~/ai-admin/Lumiere-平台反馈-汇总版-2026-09-01.md`）——
   CC 只能写成一个本地 md 文件，靠人把它端过来。它自己在文末写着「需要具体的用例编号、
   场景 id……可以索取」——**索取的通道也是人**。
2. **共享自动化资源全平台 0 行**。工具早就有，CC 也被反复引导去用。
   为什么没人用？因为登记完拿不到任何回音 —— 写进去和不写进去，下一轮看到的东西一模一样。
   **没有回音的写入通道等于没有通道**，这条通道要引以为戒（见 §5）。
3. 反馈文档 §2.3 点名了平台给的「出路 B」文案**根本没实现**。这种「文档和实现打架」
   平台侧无从发现 —— 只有照着做的人撞得到。

## 2. 裁定一：放全局，**不**放项目内

用户点名要评估这一条，所以把理由写全。

**结论：全局一张表、一个页面（`/settings/cc-feedback`），`project_id` 只作为「来源线索」记着，可为空。**

### 为什么不是项目内

1. **反馈的对象是 Lumiere 自己，不是被测系统。** 项目是「被测系统 + 它的用例」的边界，
   而 `in` 算子两边不归一类型、`replace` 会静默删步骤、`lum_get_case` 少返 5 个字段
   —— 这些在哪个项目里撞到都是同一个缺陷。
2. **放项目内 = 同一件事有 N 个家。** 三个项目的 CC 各撞一次，就是三行一模一样的东西，
   谁都不知道另外两行存在。这正是 `failure_tickets` 的归并口径要防的形状
   （同一件事 `occurrences+1`，不是开三张单）。
3. **处理方只有一拨。** 修平台的是平台维护者，不按项目分。项目内页面意味着他要
   逐个项目翻一遍才知道有没有新反馈 —— 而「要主动翻」的东西，实测就是没人翻
   （共享资源 0 行是同一个病）。
4. **这里的项目级隔离是「假隔离」。** 同 `CLAUDE.md` 里 mock 表那一条：
   行上加个 `project_id` 不改变「它是同一个平台缺陷」这个事实，只是让人以为分开了。

### 那 `project_id` 为什么还要记

**当线索，不当边界。** 它回答的是「在哪儿撞到的、去哪儿复现」——
`lum_get_case` 少返字段那条，得知道是哪个项目的哪条用例才能重放。
同理还记 `reporter`（哪把 MCP Key 报的）和 `tool_name`（撞到的是哪个 `lum_*`）。

**反例自查**：有没有真的只属于某个项目的反馈？有 —— 比如「这个项目的须知里混进了 9 条
`ai_review` 产出」。但它仍然是**平台的分类设计问题**（`knowledge_entries` 没把
AI 产出和人写的知识分开），项目只是它露出来的地方。**没有找到必须按项目隔离的反馈类型。**

### 权限

一个新权限点 `system.feedback.manage`，**admin only**。

不拆 read / manage 两档：这一页除了处置没有别的用途，看反馈的人就是处理反馈的人。
拆开会造出一个**没有任何角色拿得到的孤儿权限点**，而 `tests/test_permissions_seal.py`
正好在盯这种东西。

CC 侧的写入**不走这个权限点** —— 它走 MCP Key，和别的 `lum_*` 一样。

## 3. 裁定二：三分类 + 处置规则

用户定的分类：**bug / 优化 / 需求**。落成 `category ∈ (bug, improvement, requirement)`。

| 类 | 判据 | 处置 |
|---|---|---|
| `bug` | 平台**说了会做 A，实际做了 B**（含静默失败：知道出了问题却返回一个语法上合法的结果） | 直接修 |
| `improvement` | 行为没错，但**代价不合理**或**让人容易走错路**（上下文税、拒绝信息不指路、命名不对称） | 直接改 |
| `requirement` | 平台**今天没有这个能力** | 合理且该做 → 直接做；否则 → `wont_fix` + 写清理由 |

### 「CC 说的类」和「平台判的类」分开记

两个字段：`reported_category`（CC 的主张）、`category`（平台分诊后的裁定）。

看着冗余，其实是**用户那句话里最要紧的信号**——「或者是他判断错了，没找对方法」。
只留一个字段的话，「CC 报成 bug、其实是它没找对方法」这件事分诊完就消失了；
留两个，它就变成一条可以统计的事实：**这把 Key 报的 bug 里有几成其实是用法问题**，
那是工具描述该改的地方，不是 CC 的错。

### 严重程度由平台判，**不收 CC 填的**

反馈文档里 CC 自己打了 ★/★★/★★★。参考可以，落库不行 ——
自评严重度会单调通胀（每个报的人都觉得自己那条最急），一轮之后这一列就没有区分度了。
`severity` 由分诊时填。

### `wont_fix` 必须写理由，而且**理由要回给 CC**

用户原话：「就回复他原因，并置为不需要处理」。落成硬校验：
`status=wont_fix` 时 `resolution` 非空，否则 400。

理由分两种，都要写在 `resolution` 里：

- **这件事不该做** —— 说清为什么（例：mock 表加 `project_id` 是假隔离）。
- **你判断错了 / 没找对方法** —— **必须给出正确方法**。只说「你错了」等于没回音，
  下一轮它还会照原样再撞一次。

## 4. 三道闸：防止这条通道变成倒灌口

开一条「随便说」的通道，最可能的结局是它被填满噪音，然后没人看。三道闸：

### 闸一：指纹归并（抄 `failure_tickets` 的口径）

`fingerprint = sha256(normalize(tool_name + title))[:32]`。

- 命中**还开着**的同指纹 → `occurrences+1`，**不新建行**。
- 命中**已 `wont_fix`** 的同指纹 → **不新建行**，当场把上次的 `resolution` 甩回给 CC。
  这是这条通道最重要的一个行为：**「不需要处理」必须能挡住第二次上报**，
  否则「回复原因」就只是一句客套，下一轮照样再来一遍。
- 命中**已 `done`** 的同指纹 → **新建一行** + `reopened_from`。修好了又复现是**回归**，
  是新信息，并进老账里会把它埋掉（同 `failure_tickets` 的裁定）。

### 闸二：证据门槛

- `title` 必填，`body` **≥ 40 字**。「这个工具不好用」这种直接拒。
- `category=bug` 时 `evidence.expected` 和 `evidence.actual` **都必填** ——
  「说好的是什么 / 实际是什么」。这不是额外负担：那份反馈文档里 31 条**每条都有这个形状**，
  它本来就是想清楚了才写得出来的东西。
- 拒绝时**说清怎么补**，不只报字段名（同项目须知超长那条的做法）。

### 闸三：每把 Key 每天 40 条新指纹

超了拒收，并提示「先把已报的合并同类项，或等回音」。
归并命中（`occurrences+1`）**不计入**配额 —— 撞同一个坑第五次不该被罚。

数字定在 40 而不是 3：那份反馈文档一次攒了 31 条，这是**真实的一轮的量级**，
而配额**必须高过它** —— 一度写成 20，等于拿自己举的正面例子当上限，
认真写满一轮的人会在第 21 条上被弹回来，这道闸就从「挡噪音」变成「挡人」。
闸门要挡的是「同一件事说五遍」（走归并，本来就不占配额）和「无证据刷条数」
（闸一闸二已经挡住了）—— 配额是第三道，不是第一道。

## 5. 回音：四条路，一条都不能砍

共享自动化资源 0 行是前车之鉴：**写进去和不写进去，下一轮看到的一模一样 → 没人写。**

1. **上报当场就有回音**：命中 `wont_fix` 指纹 → 直接返回上次的理由和正确做法。
2. **`lum_list_my_feedback`** —— 主动查我报过的和它们的下场。
3. **`lum_next_duty` 第 ⑧ 队列「平台反馈有回音」** —— 只在有未读回音时出现。
   这是最重要的一条：CC 每轮上来第一个调的就是 `next_duty`，回音在这里才**不需要它记得去查**。
4. **`status=done` 的回音必须写「现在该怎么做」**，不只是「修好了」。
   还要提醒：平台后端不带 `--reload`，改完要 `bash deploy/restart-backend.sh` 才生效
   —— 否则 CC 会拿旧后端验一遍，得出「你没修」的结论。

## 6. 状态机

```
  上报 ──→ new ──（AI 自动分诊，落地即判）──┬──→ triaged ──→ in_progress ──→ done
                                            │       （人改代码时推进）      ↑
                                            ├──→ wont_fix ─── 同指纹带**新说法**重报
                                            │      （回音：理由 + 正确做法）  ↓
                                            ├──→ duplicate            needs_human（等人拍板）
                                            └──→ needs_human ←── AI 判不了 / 护栏降级
                       done 之后同指纹再报 → 新行 + reopened_from（回归）
```

- `new`：刚报进来，AI 还没判完（正常只停留几秒；`CC_FEEDBACK_AUTO_TRIAGE=0` 时会一直停在这）。
- `triaged`：定了类（bug/优化/需求）和严重度，认下了。**AI 落得了这一档。**
- `in_progress`：在改。
- `done`：改完了，`resolution` 必填。**AI 落不了** —— 它没改过代码，给了 `done` 也按
  `triaged` 落（`coercedFromDone`）。
- `wont_fix`：不做，`resolution` 必填。**AI 落得了，但 AI 判的可翻案**（见下）。
- `duplicate`：`duplicate_of` 必填。
- **`needs_human`（不是状态，是一列 `needs_human` 文本）**：AI 说它判不了，附一句
  「缺什么才能判」。这一列非空 = 这条欠人一次拍板，页面上「等人拍板」筛的就是它。
  人一拍板（走 `POST /{id}/triage`）就清空。

**「谁判的」单独记一列 `decided_by`**（`ai` / `human` / `system`）。它不是装饰：
它决定这条 `wont_fix` 还能不能被翻案 —— 人判的终局、AI 判的可翻，存不下这个区别就无处安放。

**只有 `new` 和 `triaged` 算「待处理」**，页面默认筛这两个。

## 7. 页面

路由 `/settings/cc-feedback`，菜单挂在「系统管理」组，`system.feedback.manage`。

**列表**（列序就是这个，2026-09-01 定）：标题 / 优先级 / 类别（平台判的，旁边小字标
CC 报的是什么，不一致时高亮）/ 状态（下面小字标「谁判的」）/ 撞了几次 / 最近一次 /
来源（项目 + Key 名 + 工具名）/ 操作 =「AI 处理」。

标题上挂标签：**等人拍板**（`needsHuman` 非空）、**抽检**（`sampled`）、**复发**（`reopenedFrom`）。

**列表上方**：勾选 → **「批量处理（N）」**；一条都没勾 → 「批量处理全部待处理」。
跑起来后上面出一条进度条（`GET /cc-feedback/batch-status`，页面每 3 秒轮一次 ——
一批几十条要跑几分钟，不轮的话页面看着像卡死了）。

**没有「手工录入」入口。** 那个入口只在「处置只有人能落」的口径下才有意义；
现在人来是为了看，和为「等人拍板」那几条选方案。接口 `POST /api/cc-feedback` 还留着
（脚本导入历史反馈用，见 `backend/scripts/cc_feedback.py import`），只是页面上不给按钮。

**筛选**：状态（多一档「等人拍板」）、类别、来源项目、关键词。默认「待处理」。

**抽屉**（点标题打开）：正文 + 证据（expected/actual/repro/refs）+ 归并历史 +
AI 分析结论（如果跑过）+ 处置区。

**处置区就是「点击处理」**：
- 一行按钮：`认下并分类`（选 bug/优化/需求 + 严重度）、`开始处理`、`处理完了`、`不需要处理`、`标为重复`。
- `处理完了` / `不需要处理` 弹出**回音输入框**，必填，占位符直接写要求：
  「不需要处理」→「说清为什么不做；如果是他没找对方法，把正确方法写出来」。
- `AI 处理` 按钮：让 AI **直接把裁定落下来**（判不了的落成「等人拍板」），理由见 §9。
  **人拍板那一组按钮一个都没删** —— 它们现在是兜底路径，不是主路径。

**空状态**不写「暂无数据」，写「CC 还没报过问题。它撞到平台自己的毛病时会走
`lum_report_feedback` 报到这里」，并给一句怎么验证通道是通的。

## 8. MCP 工具（2 个）

### `lum_report_feedback`
参数：`title`、`body`、`category`（bug/improvement/requirement）、
`tool_name`（选填但强烈建议 —— 它是指纹的一半）、
`expected` / `actual` / `repro` / `refs`、`project_id`（选填，默认取本 Key 的项目）。

证据**摊平成四个参数，不收一个 `evidence` dict**（规划稿写的是 dict）：
`category=bug` 时 `expected`/`actual` 是必填的，而必填字段藏在一个 dict 里，
调用方少写一个键的表现是「dict 收下了、校验才炸」，报错离出错的地方隔了一层。
摊平之后工具签名自己就是那张清单。

返回三种形状之一：
- 新建：`{id, status:"new", note:"已收到，回音会出现在 lum_next_duty 的「平台反馈有回音」队列里"}`
- 归并：`{id, merged:true, occurrences:N, currentStatus}`
- **短路**：`{id, alreadyDecided:"wont_fix", resolution:"…上次的理由和正确做法…"}`

### `lum_list_my_feedback`
参数：`project_id`（选填）、`status`（选填）、`unread_only`（默认 true）。
返回我报过的 + 它们的下场 + 回音，并**把读过的标记掉**（`ack_at`），
这样 `next_duty` 的第 ⑧ 队列才会消下去。

### 档位：**每一档都加这两个**

`profiles.py` 里九个档位全加。理由：撞到平台毛病这件事**不挑活**——
写 UI 脚本会撞、归因会撞、维护接口库也会撞。哪一档没有，哪一档的 CC 就还是只能咽下去。
这是唯一一组「跨全部档位」的工具，`test_mcp_profiles.py` 里补一条封样钉住它。

### 顺带改掉那条死路

`app/mcp/__init__.py` 里「顺手说一声」那一句改成点名 `lum_report_feedback`
—— 指令要求做的事，必须有工具做得到。

## 9. AI 处置：它自己落裁定（2026-09-01 反转）

`POST /api/cc-feedback/{id}/analyze`（单条）、`POST /api/cc-feedback/ai-handle`（批量，
带 `ids` 就只判勾选的），capability key `cc-feedback-triage`（text 档）。
上报落库时也会自动丢一个后台任务去判（`_spawn_auto`）—— 所以正常情况下人打开页面看到的
已经是判过的。

**这一节此前叫「给建议，不改状态」，2026-09-01 反转。** 原来那个理由是真的（`wont_fix`
的回音永久短路同指纹上报，单方面落它等于把一类反馈关死），所以反转不是把守卫拆掉，
是**先把不可逆性拆掉**：

输出一段 JSON，页面按字段渲染（**这是实现里的形状，规划稿那版四段没落地**：
`verdict` 和状态机重复了，`where_to_look` 让模型去猜文件路径，猜出来的十有八九不存在 ——
猜错不报错，只会让人照着去翻一个空目录）：

| 字段 | 干什么 |
|---|---|
| `category` | bug / improvement / requirement |
| `severity` | high / medium / low。判据是**会不会导致假绿或让人做出错误决定** |
| `verdict` | `triaged` / `wont_fix` / `duplicate` / `needs_human`。**`done` 不在里面** —— 那得有人真去改代码 |
| `reasoning` | 判据，两三句 |
| `resolution` | 回音，**直接落库发回给 CC**。`wont_fix` 时**必须写出正确做法**（只说「你错了」等于没回音，缺了就降级成 `needs_human`） |
| `fixHint` | 怎么改（给维护者看的） |
| `risk` | 不处理会怎样 |
| `needsHuman` | `verdict=needs_human` 时必填：**缺什么才能判**。不许写「这个比较复杂」 |

**三件事同时成立，才允许 AI 落 `wont_fix`；少任何一件都得退回去让人落：**

1. **AI 判的能翻案。** 同指纹重报，且正文**确有新东西**（`_body_key` 归一化后不相等：
   去空白去标点，改标点/换行重排不算）→ 不短路，转「等人拍板」。照原样复读不算新证据 ——
   否则短路等于没做，这条通道立刻退回倒灌口。判据故意**不做语义比较**：那种判错了没人
   看得出来，而这里判错的后果是一条裁定被复读推翻。
2. **人判的才是终局。** `decided_by=human` 的 `wont_fix` 照旧永久短路，重报只拿回上次理由。
3. **抽检。** 每 `WONT_FIX_SAMPLE_EVERY`（=5）条 AI 判的 `wont_fix` 抽 1 标 `sampled`
   给人复核 —— **裁定已经生效，抽检只用来校准 AI 判得准不准**，不拦。
   **取模不掷骰子**：掷骰子会出现连续二十条一条没抽到的走运区间，而抽检的全部意义就是
   稳定的覆盖率。

**判不了就说判不了。** 护栏一律降级成 `needs_human`，不许硬凑一个裁定：JSON 解析不出来、
`verdict` 不在允许集合、`wont_fix` 没写回音、`needs_human` 没写缺什么 —— 每一种都落
`needs_human` 并把原文留着。

**解析不了不算失败**：模型裹一层 ```json 就剥掉；实在解析不出来就存原文给人看
（`parseFailed`），总比「AI 分析失败」四个字有用。
**但一个字都没回来时报错、不落库** —— 存了就是页面上一块**空的** AI 分析，看着像
模型读过觉得没啥可说，实际是这次调用整个没产出，而且它还会覆盖掉上一次真有内容的那份。
实测成因（2026-09-01，dev 库真跑）：主路 429 → 降级到 CLI 通道（claude-proxy :38210，
那头是 Claude Code），而反馈正文本身长得像**一件待办** —— 它会去做事而不是作答，
回给我们的 text 就是空的（把「只输出 JSON」换成「先用一句话回答」，它回的是
「我先去看执行器实际怎么做的，再判。」）。换一个没被限流的模型走主路，同一条提示词稳定出 JSON。

### 判据从哪来 —— 这一条决定「自己判」是判还是猜

`_platform_facts()` 喂三样，**都是可执行的事实**：

1. **撞到的那个工具的描述原文** —— 平台「说了会做什么」。bug 的定义就是它和实际不一致，
   没有它就没有判 bug 的尺子。
2. **它的实现源码**（`inspect.getsource` + `文件:行`）—— 实际做了什么。
3. **全量工具清单**（60+ 条，每条一句话）—— 判「他其实没找对方法」唯一的判据。
   这一类占实测反馈的相当一部分，而且**回音必须写出正确方法**，写不出就等于没回音。

工具名不在清单里时**明说「不在清单里」**，不装作没这回事 —— 否则模型会拿全表硬凑一个结论。

**故意不读 `docs/*.md`**：那些是给人看的取舍记录，篇幅大，和某一条反馈的相关性只能靠
关键词猜 —— 猜错不报错，只会让判据里混进一段不相干的取舍史。

### 批量：全局单例，顺序跑

`_BATCH` 一个全局字典 + 一组后台任务强引用（不持强引用会被 GC 掉，表现成「批量跑了一半
不动了」）。**不并发**，理由是实测的：并发只会一起撞 429 然后一起降级到 CLI 通道，
而那条通道对这种提示词回空（见上）—— 于是「跑得更快」变成「一批全废」。

`GET /api/cc-feedback/batch-status` 拿进度。**这条路由必须声明在 `/{feedback_id}` 前面**，
否则 `batch-status` 被当 uuid 解析成 500；封样在
`tests/api/cc_feedback/test_cc_feedback_flow.py::test_进度查得到而且不会被当成id`。

### 还有一条纪律没变

`done` 归人。`lum_review_case` 的结论不由分数定、`lum_submit_analysis` 的 `product_defect`
要人拍板 —— 同一条纪律在这里的落点是 `done`：它的含义是**代码改完了**，
而 AI 没改过代码。这不是「不给它权限」，是它在事实上判不了这件事。

## 11. 明确不做

- **不做讨论区/多轮对话。** 一条反馈一个回音。要来回聊的那种，本来就该是人和人聊。
- **不做通知推送。** 平台有通知渠道，但反馈不是紧急事件；每轮 `next_duty` 看得到就够了。
- **不给 CC 改状态的能力。** 它只能报和读。谁能把自己的反馈标成"已解决"，这条通道就废了。
  （2026-09-01 补：平台侧那个落裁定的 AI **不是 CC** —— 它读的是平台自己的源码和工具清单，
  裁定也落在平台这一侧。**报的人不判自己报的那条**，这条没变。）
- **不做投票/优先级排序。** 只有一个报告方，排序没有信息量。
- **不做附件上传。** 证据用文本 + 引用（用例编号、场景 id、运行 id），平台自己查得到。
