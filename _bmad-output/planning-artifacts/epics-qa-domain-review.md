## Epic 0 — 量一下现在够不够（不落代码）

**这一步不产代码，产两个数。** 没有这两个数，Epic 2 的 `MAX_OUTPUT_TOKENS`
和能力位 `timeout_seconds` 就只能拍脑袋 —— 而 `qa_catalog_review.py` 的既有规矩是
「先量再定，把量到的数写进注释」（那份文件里已经有一段"2026-08-27 真去量了一遍"）。

- **S0.1 ✅ 已完成（2026-08-28）· 两个数都出来了，而且当前 `max_tokens` 明确不够。**
  UAG/`MCP`（80 场景 / 49 脚本 / 6 批，单批 prompt 最大 73882 字），去掉提示词那行
  「每一项最多 6 条」，`max_tokens=16000`，跑了 **两轮共 12 次调用，12 次全成功**。

  | 量的东西 | 实测 | 定成 |
  |---|---|---|
  | 单批正文长度 | 6717 – **10217** 字符（12 次） | — |
  | 折算输出 token | 最大 ≈ **6386**（JSON+中文混排，保守 /1.6） | `MAX_OUTPUT_TOKENS = 10000`（×1.5 上取千） |
  | 单批墙钟 | 237 – **404** s（并发 6） | 能力位 `timeout_seconds = 1020`（×2.5 上取） |
  | 每批 `finish_reason` | 12/12 = `'stop'` | 见 S0.2 —— 这个值是假的 |
  | 每批 `usage` | 12/12 全 0 | 同上 |

  **结论一：现在的 `max_tokens=2400` 只够装 38%。** 模型自然想写 ≈6386 token，
  被 2400 砍掉的是后 60%。这不是"偶尔超一点"，是**常态性截断** ——
  正是 Epic 1 三态要抓的那件事，而它现在一声不响。
  （注：CLI 通道忽略 `max_tokens`，所以**只有网关那条路真的在砍**。见 S0.2。）

  **结论二：`timeout_seconds` 只管主路，降级那条是硬编码的 600。**
  `_get_timeout()` 取的是能力位的 `timeout_seconds`（现值 **120**），
  而 `llm_client._PROXY_TIMEOUT = 600` 写死在模块里。第一次量的时候我把 endpoint
  旁路到 proxy 却没换 timeout，**6 批整整齐齐全在 120.1s 超时** —— 生产里跑得通
  纯粹是因为降级路吃的是那个 600。把 `timeout_seconds` 提到 1020 只解决主路。

  **结论三（写进 Epic 2 的 AC）：提 `max_tokens` 会把主路撞穿，③ 和 ④ 必须同批落地。**
  实测单批 237–404s，但那是**走 claude-proxy 量的**（`_PROXY_TIMEOUT = 600` 写死在模块里）；
  网关主路吃的是能力位 `timeout_seconds`，现值 **120s**。
  提到 `max_tokens=10000` ⇒ 输出约 4 倍长 ⇒ **主路上会整整齐齐全在 120.1s 超时**
  （Epic 0 已经这么撞过一次，见结论二）。而各批耗时相近 ⇒ **不是丢一批，是 6 批一起挂**
  ⇒ `if not good: raise` ⇒ **整个域的评审直接没了**。
  所以「④ 是 DB 配置改动、写进上线步骤就行」这个定性偏轻了：
  **只做 ③ 不做 ④ 比现状更差**，跟只删 ①② 不做 ③ 是同一类错。

  ⚠ **勘误（2026-08-28 当天查回来的）：这跟 `arq` 的 `job_timeout = 600` 无关。**
  本条最初写成「arq 的 600 会先撞上」，是错的 —— 域评审走的是
  `qa_catalog_review.spawn()` 里的 `asyncio.create_task`，**跑在 API 进程内**；
  `engine/worker.py::functions` 只注册了 `run_git_sync` / `run_automated_execution`。
  那个 600 管的是 Epic 7 的爬虫（Q2-H 的分片方案仍然照旧），管不到域评审。
  记这一条不只是订正一个数：**它正是本模块要治的病的又一个样本** ——
  「worker 全局的 600」是个真事实，被搬到了一个它不适用的地方，
  而搬过去之后**读起来一样有据**。查法就一句 `grep functions app/engine/worker.py`。

  ⚠ 顺带一条不在 Epic 2 范围、但被它放大的：`asyncio.create_task` 起的活
  **不会因为超时被谁杀掉，但会因为后端重启被杀掉**，而 `finish()` 只在异常路径上跑 ——
  进程被杀不是异常 ⇒ 那条 review 永远停在 `running`（没有任何 reaper 扫它），
  正是 `execute()` docstring 自己警告的「页面上一条 running 永远转下去」。
  批次变长 ⇒ 窗口变宽。**本 Epic 不修**，单列在建议开发顺序表后面。
  ⚠ 临时脚本 **cwd 必须是 `backend/`**，否则静默丢 `.env`，429 降级通道消失（本次撞了一次，
  症状正如 CLAUDE.md 所写：静默，12 发全 429 且不降级）。
  ⚠ **Bash 工具的 cwd 在两次调用之间不保留** —— 每条命令都得自带 `cd .../backend &&`。
- **S0.2 ✅ 已完成（2026-08-28）· 两个凭据都不给，而且 `unknown` 是主路不是边角料。**
  强制打 claude-proxy(:38210)，`max_tokens=64`，要它「把 1 数到 500，每个数占一行」：

  - `finish_reason` = **恒 `'stop'`**（键在，值是常量）
  - `usage` = **恒 `{"prompt_tokens":0,"completion_tokens":0,"total_tokens":0}`**
  - `content` = **1891 字，1→500 全数完了** ⇒ **这条通道压根不理 `max_tokens`**

  三条推论，每条都改设计：

  1. **「`completion_tokens` 撞上限」这条判据在 CLI 通道上是死的**，因为它恒为 0。
     三态判定不能建在它上面。
  2. **CLI 通道上"按上限截断"这件事根本不会发生**（它忽略上限）。所以截断只发生在
     网关那条路 —— 而网关路才会给真的 `finish_reason='length'`。
     两条通道的失效模式完全不同，三态必须**按通道分**，不能一套判据打两条路。
  3. **`unknown` 是常态。** 实测期间网关持续 429（`GW-2006`，后转
     `no upstream tokens available · resets 09:59` —— 是**额度耗尽**不是并发限流），
     12/12 次调用全走 CLI 通道。**S1.3 的渲染必须当主路设计**，
     不能做成"极少数情况下的灰色小字"。

  **纯代码的检测法（S1.1 照这个实现）**：`prompt_tokens == 0` 而 prompt 非空，
  是个**可证伪的假值** —— 12/12 命中。比"看键在不在"强：键是在的，值才是假的。
  ⚠ 所以 S1.1 原本打算改 `LLMResponse` 默认值（`"stop"` / `0`）的做法**不够** ——
  改了默认值也区分不出「通道没报」和「通道报了个常量假值」。
  必须新增一个字段（例：`usage_trustworthy` / `reported: set[str]`）由 `complete()`
  按原始 JSON 填。爆破半径已核：`complete().finish_reason` **零消费方**，
  `completion_tokens` 两处记账（`usage.py:53` 用 `or 0`、`llm_structured.py:146` 是 `+=`）。
- **S0.3 ✅ 已完成（2026-08-28）· 结论推翻了洞四的「线上」定性，见下方 Epic 1。**
  跑了两个配了 `qa_repo` 的项目全部 38 个域（网关管理系统 14 + UAG 24），
  逐域比 `len(scripts)` vs `sum(len(b) for b in batches)`：
  **撞 `MAX_BATCHES` 的域 = 0 个，每个域都是「进批 == 读到」。**
  最大的域是 UAG/`MCP`：**80 场景 / 49 份脚本 / 6 批**（HANDOFF 记的 75/47 是旧数，仓库长了）。
  更要紧的是**批数封顶够不着**：批闭合的条件是 `used + n > BATCH_SCRIPT_BYTES(90_000)`
  且单份 `n <= MAX_SCRIPT_BYTES(18_000)`，所以每个闭合批 `used > 72_000`；
  凑 8 批要求前 7 批合计 `> 504_000`，而 `take_scripts` 把全域合计钉死在
  `TOTAL_SCRIPT_BYTES = 480_000`。**504_000 > 480_000 ⇒ 8 批不可达，`break` 是死代码。**
  已验三遍：解析式推导、20000 次随机搜索（最大 7 批）、定向构造最坏情况（7 批要 432_007 字节，
  放得进；8 批要 504_008 字节，`take_scripts` 放不进）。
  AC 原本要一个域码列表 —— **答案是空列表，而空列表本身就是结论。**

### Epic 0 的副产物：量的时候撞出来的四条（都有原始数据）

### Epic 1 实现记录（2026-08-28 已落代码）— 三处偏离本文的写法

**E1-1 · `completeness` 的形状：不是 `batchesIncomplete: [批次号]`，是每批一个态的 map。**

**这条 Story 的整个重量压在一个区分上：「没探到」不是「看不见」。**
两种错的代价差一个量级，所以三件事写在一个模块里、不许拆：

- 「看不见」当成「没探到」 ⇒ 少一条候选，人工照旧能发现。
- 「没探到」当成「看不见」 ⇒ **凭空产出一条越权候选**。这是本模块唯一会
  *无中生有造出结论* 的错。SEC 那边查空两次，这份清单以后就没人看了。

而假象是**常态不是边角**：浅扫只跑前 `SHALLOW_MAX_PAGES` 页，
「这个角色在第 41 页看不见任何东西」每一趟都必然发生。`UNPROBED`
是**独立第三态**，不是「暂时当看不见」——所以 `unprobed` 的格子在候选推导里
**整格排除**，不是当成 0 参与运算；照后者算，每趟都能吐出成百条假候选。

**六处偏离本文的写法：**

1. **并集从爬虫的内联循环挪进纯模块。** 原来那段是「拿主爬那份当底、浅扫只做标注」，
   三个缺陷：① 主爬角色自己不进 `roles_visible`，于是只有主爬看得见的控件落成
   `roles_visible == []` —— **和「一个角色都没探过它」在产物上一模一样**，
   而这两件事的结论正好相反；② 只有浅扫角色看得见的 key 整行消失，
   而「低权角色看得见、主爬这个只读账号看不见」恰恰是角色维度**唯一有价值的信号**；
   ③ 没有 per-role 的「真正走到了哪些页」，第三态根本无从判起。
2. **空页也要记进 `pagesProbed`。** 只在「这一页抓到了控件」时记账的话，
   一个真的什么都没有的页面会退回未探测 —— **空页恰恰是「探过了，确实看不见」**，
   那是可比的格子。少记它，就把最硬的那种 `invisible` 证据丢了。
3. **同一个分片里重复的 key 不许合并。** `(survey_id, key)` 撞库是故意的：
   它是锚点推断塌掉的探测器。在并集里顺手去个重，那个探测器永远不会响，
   而 diff 会开始无缘无故地报「新增 40 项」。跨分片的同 key 才是并集要合的。
4. **越权候选不进枚举产物。** 它是**推断**，混进 `items` 就会被当成页面事实
   往下游传。每条自带 `basis`（「由可见性矩阵推导，不是实测越权结果」）+ `SEC 域候选`
   标记 —— 写在**每一条**上，不是页面上补一句：出口不止一个（页面、MCP、导出的文档），
   少带一个出口就会有人把候选当结论转出去。
5. **返回值里没有任何一个布尔放行位，`head` 永远不写「没有越权漏洞」。**
   这份东西看的是「哪些控件在页面上露给了谁」，它**连一次越权请求都没发过**。
   候选为 0 只说明这一趟观测里没撞见那个形状。所以计数（尤其是未探测那格）
   跟结论**焊在同一句话里**：单独一个「0 条候选」被截出去，就变成了一个绿勾。
   配了一条验收测试直接扫返回值全文，`没有越权漏洞` / `无越权` / `安全` 一个都不许出现。
6. **门槛故意保守**（支撑 ≥ 5、例外 ≤ 3）。例外超了就不是「超集带几个例外」，
   那两个角色只是**菜单不同**，硬报出来全是噪声 —— 同 S7.1 第 2 条：
   凭空造出来的缺口比漏掉的贵。

**六处偏离本文的写法：**

1. **`survey_key` 缺一格返回 `None`，不是拿空串凑一个键。** 凑了的话
   「指纹没量到」和「指纹跟上次一样」会哈希到**同一个值** —— 一趟没量到构建的运行
   命中上一趟的缓存，「我们没能确认构建没变」被记成了「构建没变」。**这正是洞四的形状。**
2. **`route_table_hash` 拉不到返回 `None`，不是「空表的哈希」。** 空表的哈希是个
   合法值，它跟上一轮"也没拉到"的那个**相等** —— 连着两轮拉不到，会推出
   「路由表没变，不用重算」，而事实是这两轮**谁都没看过路由表**。
   拉到了确实是空表则照常出哈希：**那是观测到的事实，不是缺信号。**
3. **逐段带长度前缀再哈希**（`f"{len(p)}:{p}\x1f"`）。直接拼的话
   `("a","","b")` 和 `("a","b","")` 是同一串，两个不同的（项目,环境,指纹）共用一个键。
   路由行的三格也各自摘要再合，**不许拼成一句** —— 组名里带空格是常态（「AI 网关」），
   拼了之后 `group="a b"/method="c"` 和 `group="a"/method="b c"` 撞键。

4. **`KEY_SPEC` 折进每一个键。** 键的定义一改，旧缓存里那些**长得一样合法**，

5. **返回值里一个布尔都没有。** `{"cached": true}` 一旦存在，页面上就会有人只渲染它,

   `summary` 把「哪一趟 + 什么时候 + 什么指纹 + 什么终态」焊进同一句话。
6. **`partial` 在可复用之列，但复用它必须在结论里带上终态。** 排除它的代价是
   一个角色少配凭证的环境**永远命不中缓存**，于是每次对账都去重爬别人的环境 ——
   那是朝错误方向的保守。

#### S8.2 · dim 按数组分白名单（commit 见下）— 三处偏离本文的写法

**E8-1 · 白名单写成"每个维度登记自己能落哪边"，不是"脚本那边 = 全部减 coverage"。**
本文的措辞（「`scriptGaps` 八个合法 dim（**不含 `coverage`**）」）读起来像个减法，
照着写就是 `DIM_KEYS - {"coverage"}`。那样写今天完全正确，**明天 S8.3 加两个维度时
它们会自动在脚本侧合法** —— 而 S8.3 加的 `blind`(G2) 正是只该归清单侧的。
派生的白名单不会报错，它会**静默地放行**。

> **勘误（S8.3 落代码时发现，原文这里写错了一半）**：本条初稿写的是
> 「`claimed`(G3) / `blind`(G2) 两个都是覆盖面的事、都该只归清单侧」。

> 论点（派生白名单会静默放行新维度）不受影响，例子换成 `blind` 才成立。
所以落成了逐维登记的 `DIM_SIDE`，并用 `test_每个维度都得说清自己能落哪个数组`
钉死 `set(DIM_SIDE) == set(DIM_KEYS)`：漏登记的维度两边都非法、整片被改判成「其它」，
**当场红**。比"没登记就默认放行"好，因为默认放行的漏登记查不出来。

**E8-2 · 越界一律落「其它」，不往最近的合法维度上靠，原话留 `dimRaw`。**
`coverage` 落进 `scriptGaps` 时，"最近的合法维度"是 `both` 或 `skip`，靠过去页面上就
是一条正常的脚本缺口 —— **猜对和猜错长得一模一样**，而这一格正是要交给人去修
提示词还是修白名单的线索。所以只落「其它」，原话原样留在 `dimRaw`。
配套：**`dimCoerced` 从行本身数**（扫 `dimRaw` 那一格），不收模型报的那个数、
也不各批各报一份再相加 —— 同 `evidence_stats` 的纪律，两条路径哪天分歧了没人
看得出是哪边错。这个数**必须露在报告里**（`to_markdown` 多一句话）：
一个不报数的 coerce 就是新造的静默行为，正是这套表要堵的那种。

**E8-3 · 「模型压根没给维度」不算越界。**
空维度 rollup 自己会归进「其它」，在 coerce 这儿也记一笔的话，`dimCoerced`

所以丢掉的行**整条**进 `droppedNoAnchor`，页面和 markdown 都摊开、划掉；
计数 `len(dropped)` **从行本身数**，不接受另给一个数（同 `evidence_stats` / `dimCoerced`）。

**E8-10 · 端点层白名单落成 `EDGE_SOURCES` + `edge_ok()`，`static` fail-closed。**

落成 `qa_coverage_reconcile.py` 顶上的
`EDGE_SOURCES = ("observed", "aborted", "static")` 加一个 `edge_ok(ep, build_fingerprint)`：

- **没写 `source` 的一律不算数，不默认成 `observed`。** 默认放行等于这道闸门不存在：
  以后任何一条新造边的路径，只要"忘了"写来源就自动被采信 —— 而这里防的恰恰是忘。
- `aborted` 算数，因为 **L1 的拦截既是闸门也是事实来源**：拦下来的那一刻，

  连"源码里写着"都不成立 —— 那是另一个版本的源码。今天没有任何调用方传指纹，

### 验收记录 · S6（§9 的 F 条）—— 2026-08-29 实测

**范围说明：不是 24 个域，是 3 个（MCP / TEM / AUT）。** 跑的是别人的测试环境

落码：`qa_catalog_review.repeat_key` / `repeatability`（纯函数、8 条哨兵）
+ `backend/scripts/qa_review_repeatability.py`（实测脚本，可复跑）。
PRD 说的「新增一条实测脚本」做成脚本而不是 pytest，因为它要真发两趟模型调用才有意义，
而那个既慢又花钱、还依赖 QA 仓和网关都活着。

**跨趟的键必须跟同批去重那个键分开。** Epic 0 副-C 已经量过：拿 `_gap_key`
（带 `problem`/`why` 全文）跨趟比是 **0%** —— 两趟抓的是同几条，只是措辞不一样。
所以另立 `repeat_key`，**只认 `id` + `path`，两个都得有**，缺一个返回 `None`
不参与比对。不许拿 `"|path"` 这种半截键去配：那会把同一份脚本里几条不同的发现
合成一条，然后两趟都"命中"。

**实测（TEM，两趟同 `commitSha 173af7aa87`、同环境）：**

| | A（先，`9f01ff24`） | B（后，`07610021`） |
|---|---|---|
| scriptGaps | 14（唯一键 12） | 16（唯一键 13） |
| 没 id/path | 0 | 0 |
| 同键并掉 | 2 | 3 |

两趟都抓到 **11** 条 → **Jaccard 79%**（A 侧命中 92%，B 侧命中 85%）。
**S6 阈值 70%：过。** 只有 A 抓到的 1 条 `TEM-03`，只有 B 抓到的 2 条
`TEM-08` / `TEM-12`（都在 `team-budget-provider.sh`）。

**三处值得记下来的：**

1. **报三个数，不报"一个分"。** 只报一个的话，挑哪个报本身就是结论 ——
   两趟一趟 20 条一趟 4 条、4 条全在里面，「B 侧命中 100%」是真的，
   而它想说的"稳"是假的。Jaccard 当口径，两个方向的命中率一并给出。

2. **`unmeasurable` 是独立的一档，不是 0 也不是 1。** 两边都没有 `scriptGaps`
   时交集÷并集是 0/0：写 1.0 = 从零份数据里读出满分，写 0.0 = 编一个"完全不稳"。
   跟本模块其它三态一个规矩 —— **缺信号不是一个结论**。
   脚本那边同理：只找到一趟 done 时说「比不了」并**非零退出**，不许装作量过了。

3. **⚠ 第一版把「没法比」算错了，是自己的仪表先露的馅。**
   原写法 `unkeyed = 总条数 − 唯一键数`，实测 TEM 报「5 条没 id/path」，
   逐条去找**一条都找不出来** —— 全是同一条场景被写成两条发现
   （一条 `depth` 一条 `expect`），键相同并成了一条。那个减法把
   「模型漏填字段」和「正常的同键合并」并进了一个数，**而这两件事要做的处理相反**。
   现在分开数：`unkeyed` 只数 `repeat_key` 返回 `None` 的，`dup` 单独报。
   —— 这正是这个模块存在的意义要抓的那类错，它自己又犯了一次
   （上一次是洞四：`split_batches` 静默丢脚本而 `scriptsRead` 照数）。
