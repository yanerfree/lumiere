## Epic 0 — 量一下现在够不够（不落代码）

**这一步不产代码，产两个数。** 没有这两个数，Epic 2 的 `MAX_OUTPUT_TOKENS`
和能力位 `timeout_seconds` 就只能拍脑袋 —— 而 `qa_catalog_review.py` 的既有规矩是
「先量再定，把量到的数写进注释」（那份文件里已经有一段"2026-08-27 真去量了一遍"）。

- **S0.1 ✅ 已完成（2026-08-28）· 两个数都出来了，而且当前 `max_tokens` 明确不够。**
  UAG/`MCP`（80 场景 / 49 脚本 / 6 批，单批 prompt 最大 73882 字），去掉提示词那行
  「每一项最多 6 条」，`max_tokens=16000`，跑了 **两轮共 12 次调用，12 次全成功**。

  | 量的东西 | 实测 | 定成 |
  |---|---|---|
  | 单批正文长度 | 6717 – **10217** 字符（12 次） | — |
  | 折算输出 token | 最大 ≈ **6386**（JSON+中文混排，保守 /1.6） | `MAX_OUTPUT_TOKENS = 10000`（×1.5 上取千） |
  | 单批墙钟 | 237 – **404** s（并发 6） | 能力位 `timeout_seconds = 1020`（×2.5 上取） |
  | 每批 `finish_reason` | 12/12 = `'stop'` | 见 S0.2 —— 这个值是假的 |
  | 每批 `usage` | 12/12 全 0 | 同上 |

  **结论一：现在的 `max_tokens=2400` 只够装 38%。** 模型自然想写 ≈6386 token，
  被 2400 砍掉的是后 60%。这不是"偶尔超一点"，是**常态性截断** ——
  正是 Epic 1 三态要抓的那件事，而它现在一声不响。
  （注：CLI 通道忽略 `max_tokens`，所以**只有网关那条路真的在砍**。见 S0.2。）

  **结论二：`timeout_seconds` 只管主路，降级那条是硬编码的 600。**
  `_get_timeout()` 取的是能力位的 `timeout_seconds`（现值 **120**），
  而 `llm_client._PROXY_TIMEOUT = 600` 写死在模块里。第一次量的时候我把 endpoint
  旁路到 proxy 却没换 timeout，**6 批整整齐齐全在 120.1s 超时** —— 生产里跑得通
  纯粹是因为降级路吃的是那个 600。把 `timeout_seconds` 提到 1020 只解决主路。

  **结论三（写进 Epic 2 的 AC）：提 `max_tokens` 会把主路撞穿，③ 和 ④ 必须同批落地。**
  实测单批 237–404s，但那是**走 claude-proxy 量的**（`_PROXY_TIMEOUT = 600` 写死在模块里）；
  网关主路吃的是能力位 `timeout_seconds`，现值 **120s**。
  提到 `max_tokens=10000` ⇒ 输出约 4 倍长 ⇒ **主路上会整整齐齐全在 120.1s 超时**
  （Epic 0 已经这么撞过一次，见结论二）。而各批耗时相近 ⇒ **不是丢一批，是 6 批一起挂**
  ⇒ `if not good: raise` ⇒ **整个域的评审直接没了**。
  所以「④ 是 DB 配置改动、写进上线步骤就行」这个定性偏轻了：
  **只做 ③ 不做 ④ 比现状更差**，跟只删 ①② 不做 ③ 是同一类错。

  ⚠ **勘误（2026-08-28 当天查回来的）：这跟 `arq` 的 `job_timeout = 600` 无关。**
  本条最初写成「arq 的 600 会先撞上」，是错的 —— 域评审走的是
  `qa_catalog_review.spawn()` 里的 `asyncio.create_task`，**跑在 API 进程内**；
  `engine/worker.py::functions` 只注册了 `run_git_sync` / `run_automated_execution`。
  那个 600 管的是 Epic 7 的爬虫（Q2-H 的分片方案仍然照旧），管不到域评审。
  记这一条不只是订正一个数：**它正是本模块要治的病的又一个样本** ——
  「worker 全局的 600」是个真事实，被搬到了一个它不适用的地方，
  而搬过去之后**读起来一样有据**。查法就一句 `grep functions app/engine/worker.py`。

  ⚠ 顺带一条不在 Epic 2 范围、但被它放大的：`asyncio.create_task` 起的活
  **不会因为超时被谁杀掉，但会因为后端重启被杀掉**，而 `finish()` 只在异常路径上跑 ——
  进程被杀不是异常 ⇒ 那条 review 永远停在 `running`（没有任何 reaper 扫它），
  正是 `execute()` docstring 自己警告的「页面上一条 running 永远转下去」。
  批次变长 ⇒ 窗口变宽。**本 Epic 不修**，单列在建议开发顺序表后面。
  ⚠ 临时脚本 **cwd 必须是 `backend/`**，否则静默丢 `.env`，429 降级通道消失（本次撞了一次，
  症状正如 CLAUDE.md 所写：静默，12 发全 429 且不降级）。
  ⚠ **Bash 工具的 cwd 在两次调用之间不保留** —— 每条命令都得自带 `cd .../backend &&`。
- **S0.2 ✅ 已完成（2026-08-28）· 两个凭据都不给，而且 `unknown` 是主路不是边角料。**
  强制打 claude-proxy(:38210)，`max_tokens=64`，要它「把 1 数到 500，每个数占一行」：

  - `finish_reason` = **恒 `'stop'`**（键在，值是常量）
  - `usage` = **恒 `{"prompt_tokens":0,"completion_tokens":0,"total_tokens":0}`**
  - `content` = **1891 字，1→500 全数完了** ⇒ **这条通道压根不理 `max_tokens`**

  三条推论，每条都改设计：

  1. **「`completion_tokens` 撞上限」这条判据在 CLI 通道上是死的**，因为它恒为 0。
     三态判定不能建在它上面。
  2. **CLI 通道上"按上限截断"这件事根本不会发生**（它忽略上限）。所以截断只发生在
     网关那条路 —— 而网关路才会给真的 `finish_reason='length'`。
     两条通道的失效模式完全不同，三态必须**按通道分**，不能一套判据打两条路。
  3. **`unknown` 是常态。** 实测期间网关持续 429（`GW-2006`，后转
     `no upstream tokens available · resets 09:59` —— 是**额度耗尽**不是并发限流），
     12/12 次调用全走 CLI 通道。**S1.3 的渲染必须当主路设计**，
     不能做成"极少数情况下的灰色小字"。

  **纯代码的检测法（S1.1 照这个实现）**：`prompt_tokens == 0` 而 prompt 非空，
  是个**可证伪的假值** —— 12/12 命中。比"看键在不在"强：键是在的，值才是假的。
  ⚠ 所以 S1.1 原本打算改 `LLMResponse` 默认值（`"stop"` / `0`）的做法**不够** ——
  改了默认值也区分不出「通道没报」和「通道报了个常量假值」。
  必须新增一个字段（例：`usage_trustworthy` / `reported: set[str]`）由 `complete()`
  按原始 JSON 填。爆破半径已核：`complete().finish_reason` **零消费方**，
  `completion_tokens` 两处记账（`usage.py:53` 用 `or 0`、`llm_structured.py:146` 是 `+=`）。
- **S0.3 ✅ 已完成（2026-08-28）· 结论推翻了洞四的「线上」定性，见下方 Epic 1。**
  跑了两个配了 `qa_repo` 的项目全部 38 个域（网关管理系统 14 + UAG 24），
  逐域比 `len(scripts)` vs `sum(len(b) for b in batches)`：
  **撞 `MAX_BATCHES` 的域 = 0 个，每个域都是「进批 == 读到」。**
  最大的域是 UAG/`MCP`：**80 场景 / 49 份脚本 / 6 批**（HANDOFF 记的 75/47 是旧数，仓库长了）。
  更要紧的是**批数封顶够不着**：批闭合的条件是 `used + n > BATCH_SCRIPT_BYTES(90_000)`
  且单份 `n <= MAX_SCRIPT_BYTES(18_000)`，所以每个闭合批 `used > 72_000`；
  凑 8 批要求前 7 批合计 `> 504_000`，而 `take_scripts` 把全域合计钉死在
  `TOTAL_SCRIPT_BYTES = 480_000`。**504_000 > 480_000 ⇒ 8 批不可达，`break` 是死代码。**
  已验三遍：解析式推导、20000 次随机搜索（最大 7 批）、定向构造最坏情况（7 批要 432_007 字节，
  放得进；8 批要 504_008 字节，`take_scripts` 放不进）。
  AC 原本要一个域码列表 —— **答案是空列表，而空列表本身就是结论。**

### Epic 0 的副产物：量的时候撞出来的四条（都有原始数据）

### Epic 1 实现记录（2026-08-28 已落代码）— 三处偏离本文的写法

**E1-1 · `completeness` 的形状：不是 `batchesIncomplete: [批次号]`，是每批一个态的 map。**

   然后连真缺口一起没人看了。出路是 S6.5 的 `status='gap'` 待整改队列，
   不是把整趟结果标脏。用 `test_锚不住不算缺口不降级` 钉住。
4. **`pagesFailed` 从 `f"{path}: {err}"` 改成结构化一条**（S6.3 落的是拼好的串）。
   它现在是 diff 规则的**输入**：拼串下游就得反解析，而路径里本来就可能带 `": "`
   （查询串、带冒号的模块名），切一刀就切歪 —— 那一页于是不算失败页，
   它的 item 立刻变成 `removed`。封样不写格式警察，直接拿一个带冒号的真路径去撞。
5. **多了一条本文没提的规则：整趟不可比（`is_wholly_unreliable`）。**
   本文的降级规则是**逐页**的，而分片死掉时账本里**一页都没记**（`crawl_role` 整个抛了），
   逐页规则于是 fails open：上一趟的每一行都变成 `removed`。
   这是最响的一种假缺口 —— 一次网络抖动报出「这个域的功能全没了」。
6. **落库失败落 `failed`，并保留 `crawlStatus`。** 爬完了但没存下来 ≠ 这一趟成功：
   对下游它等于没发生过，可它**已经真的去访问过别人的环境了**。两件事都得说出来，
   否则页面上会出现一趟"成功但查不到结果"的枚举。

**AC 的「两趟 diff 稳定」没有靠真跑两趟证明** —— 爬虫仍未对 138 真跑过（要单独批准）。
换成两条更强的、不依赖环境的：① 同一批 item **打乱顺序**跑 diff，`added`/`removed`
必须一个字不动（锚点是 testid/id/文案，不是序号）；② **每条降级规则都配一条反向锚点**
（真删了照样报 `removed`、真新增照样报 `added`）—— 否则「一律 unknown」也能让全部测试变绿，
而那是个把这个模块变成哑巴的实现。

**踩到一次自指封样陷阱，值得记**：先写的 `test_落库不许静默去重` 是扫 `save_survey`
源码找 `on_conflict` 这个词 —— 它**被自己那份文档字符串满足了**（docstring 里正写着
"不许 `on_conflict_do_nothing`"），红了一次才发现。封样测试写在被它守护的源码旁边时，
**一句注释就能把它骗过去，也能把它误伤**。改成真库里的行为封样：一趟里塞两个同 key
